# Заняття 17. Потокова обробка. Частина 2: обчислення над потоками

## Про що це заняття

Брокер подій розв'язує задачу транспорту: події надійно приймаються, зберігаються й доставляються. Наступна задача — **обчислювати над ними**. І тут виникають проблеми, яких у пакетній обробці не існує в принципі.

У пакеті набір даних скінченний: можна відсортувати, порахувати точний `COUNT DISTINCT`, зробити join із повною таблицею. У потоці набір нескінченний. `COUNT(*)` над нескінченним потоком не має відповіді. Сортування неможливе. Join двох потоків вимагає зберігати стан невизначено довго. Події приходять не в тому порядку, у якому сталися, і невідомо, скільки ще чекати на запізнілі.

Це заняття — про те, як ці проблеми розв'язуються: через **вікна** (перетворення нескінченного потоку на скінченні порції), **час події проти часу обробки**, **watermark** (формальна межа терпіння до запізнень), **стан і checkpoint** (відмовостійкість обчислення, а не тільки даних) і **режими виведення** (що саме потрапляє в приймач при кожному оновленні).

Після заняття ви зможете: пояснити відмінність event time від processing time і чому вона фундаментальна; спроєктувати віконну агрегацію під конкретну задачу; налаштувати watermark, розуміючи компроміс між затримкою й повнотою; описати, що зберігається в checkpoint і чому його не можна видаляти; обґрунтувати вибір режиму виведення; порівняти архітектури Lambda й Kappa.

## Що треба знати заздалегідь

- Брокери подій: топіки, партиції, offset, групи споживачів, гарантії доставки.
- DataFrame API Spark: агрегації, join-и, віконні функції.
- Модель виконання Spark: партиції, shuffle, стан у пам'яті executor-а.
- Транзакційні table format-и: атомарний коміт, ідемпотентний запис.

## Основний матеріал

### 1. Дві моделі обчислень

#### 1.1 Що змінюється принципово

| | Пакетна обробка | Потокова обробка |
|---|---|---|
| Набір даних | Скінченний, відомий наперед | Нескінченний, невідомий |
| Момент запуску | За розкладом або тригером | Постійно |
| Завершення | Є | Немає |
| Повнота даних | Гарантована на момент запуску | Ніколи не гарантована |
| Стан | У межах одного запуску | Живе між обробками нескінченно |
| Помилка | Перезапустити з нуля | Відновитися з позиції й зі стану |
| Затримка | Хвилини–години | Мілісекунди–секунди |
| Порядок | Можна відсортувати все | Тільки часткові гарантії |

Ключова відмінність не в швидкості, а в **невизначеності**. Пакетна задача знає, що всі дані на місці. Потокова ніколи цього не знає: подія за 10:59 може прийти о 11:07 через мережевий збій, ретрай або офлайн-режим мобільного застосунку. Кожне рішення в потоковій системі — це рішення про те, **скільки чекати**.

#### 1.2 Модель мікробатчів проти справжнього потоку

**Мікробатчі** (Spark Structured Streaming за замовчуванням): потік розбивається на маленькі пакети, кожен обробляється як звичайний DataFrame-запит. Затримка — від сотень мілісекунд до секунд. Плюс — той самий движок, той самий код і ті самі оптимізації, що в пакеті.

**Обробка запис за записом** (Apache Flink, Kafka Streams): кожна подія обробляється одразу після надходження. Затримка — одиниці мілісекунд. Плюс — мінімальна затримка й багатша модель роботи з часом і станом.

Spark має і режим **Continuous Processing** (експериментальний, затримка ~1 мс), і **Real-time Mode** у нових версіях, але основний робочий режим — мікробатчі. Для переважної більшості аналітичних задач затримка в 1–5 секунд є цілком прийнятною, і виграш від єдиної кодової бази з пакетом переважує.

### 2. Structured Streaming: потік як нескінченна таблиця

#### 2.1 Центральна абстракція

Ключова ідея Structured Streaming: **потік — це таблиця, до якої безперервно дописуються рядки**.

![Потік як нескінченна таблиця](https://spark.apache.org/docs/latest/img/structured-streaming-stream-as-a-table.png)

*Вхідний потік трактується як таблиця без кінця: кожна нова подія — новий рядок. Джерело: [Spark Structured Streaming Programming Guide](https://spark.apache.org/docs/latest/structured-streaming-programming-guide.html)*

З цього випливає головна практична перевага: **запит до потоку пишеться так само, як запит до таблиці**. Ті самі `select`, `filter`, `groupBy`, `join`, ті самі функції, той самий Catalyst.

![Модель програмування Structured Streaming](https://spark.apache.org/docs/latest/img/structured-streaming-model.png)

*Модель виконання: з кожним інтервалом тригера нові рядки вхідної таблиці обробляються, оновлюючи таблицю результату, з якої формується вивід у приймач. Джерело: [Spark Structured Streaming Programming Guide](https://spark.apache.org/docs/latest/structured-streaming-programming-guide.html)*

![Приклад інкрементального виконання](https://spark.apache.org/docs/latest/img/structured-streaming-example-model.png)

*Інкрементальне обчислення: движок не перераховує весь потік — він оновлює результат, використовуючи збережений стан попередніх батчів. Джерело: [Spark Structured Streaming Programming Guide](https://spark.apache.org/docs/latest/structured-streaming-programming-guide.html)*

Движок гарантує, що результат буде **таким самим, як якби той самий запит виконали над повною таблицею** в пакетному режимі. Це і є сенс формулювання «streaming as an incremental batch query».

#### 2.2 Джерела

```python
# Kafka
stream = (spark.readStream
    .format("kafka")
    .option("kafka.bootstrap.servers", "broker:9092")
    .option("subscribe", "trips")
    .option("startingOffsets", "latest")     # latest | earliest | {"topic":{"0":123}}
    .option("maxOffsetsPerTrigger", 100_000) # обмеження обсягу батча
    .load())

# Файли в директорії
stream = (spark.readStream
    .schema(schema)                          # схема ОБОВ'ЯЗКОВА для файлових джерел
    .option("maxFilesPerTrigger", 10)
    .json("s3://lake/incoming/"))

# Таблиця table format (Iceberg / Delta)
stream = spark.readStream.format("iceberg").load("db.events")

# Для тестів
stream = spark.readStream.format("rate").option("rowsPerSecond", 100).load()
```

Kafka-джерело повертає фіксовану схему: `key`, `value` (обидва `binary`), `topic`, `partition`, `offset`, `timestamp`, `timestampType`. Корисне навантаження потребує розбору:

```python
parsed = (stream
    .select(F.from_json(F.col("value").cast("string"), event_schema).alias("e"),
            F.col("timestamp").alias("kafka_ts"))
    .select("e.*", "kafka_ts"))
```

**Схему для файлових джерел треба задавати явно.** Інференс над нескінченним потоком неможливий: система не може прочитати «всі файли», щоб вивести типи.

#### 2.3 Приймачі та тригери

```python
query = (result.writeStream
    .format("parquet")
    .outputMode("append")
    .option("path", "s3://lake/out/")
    .option("checkpointLocation", "s3://lake/_checkpoints/job1/")   # ОБОВ'ЯЗКОВО
    .trigger(processingTime="30 seconds")
    .start())

query.awaitTermination()
```

| Приймач | Особливості |
|---|---|
| `kafka` | Запис у топік; підтримує ідемпотентність через транзакції |
| `parquet` / `json` / `csv` | Файли; тільки `append` |
| `iceberg` / `delta` | Транзакційний запис; підтримує `append` і `complete`, доступний MERGE |
| `console` | Вивід у stdout — тільки для налагодження |
| `memory` | Тимчасова таблиця в пам'яті driver-а — тільки для тестів |
| `foreachBatch` | Довільна логіка над кожним мікробатчем як над звичайним DataFrame |

**`foreachBatch` — найважливіший приймач на практиці.** Він дає доступ до мікробатча як до звичайного статичного DataFrame, тобто дозволяє все, що недоступне потоковому API: MERGE у таблицю, запис у кілька приймачів, JDBC, довільні side-effects.

```python
def upsert(batch_df, batch_id):
    batch_df.createOrReplaceTempView("updates")
    batch_df.sparkSession.sql("""
        MERGE INTO silver.trips t USING updates u ON t.trip_id = u.trip_id
        WHEN MATCHED THEN UPDATE SET *
        WHEN NOT MATCHED THEN INSERT *
    """)

query = result.writeStream.foreachBatch(upsert).option("checkpointLocation", ck).start()
```

`batch_id` монотонно зростає і використовується для ідемпотентності: якщо приймач запам'ятовує оброблені `batch_id`, повторна обробка того самого батча після збою буде проігнорована.

**Тригери:**

| Тригер | Поведінка |
|---|---|
| За замовчуванням | Наступний мікробатч одразу після завершення попереднього |
| `processingTime="30 seconds"` | Фіксований інтервал |
| `availableNow=True` | Обробити все накопичене й зупинитися — «пакетний запуск потокового запиту» |
| `continuous="1 second"` | Експериментальний режим наднизької затримки |

`availableNow` — важливий режим: він дозволяє запускати потоковий конвеєр за розкладом (наприклад, щогодини з Airflow), зберігаючи всю логіку відстеження позиції й стану. Це компроміс між вартістю постійно працюючого кластера й затримкою.

### 3. Час події проти часу обробки

#### 3.1 Два часи

- **Event time** — коли подія **сталася**. Записаний у самій події джерелом.
- **Ingestion time** — коли подія потрапила в брокер.
- **Processing time** — коли система її **обробила**.

Ці часи не збігаються, і розрив між ними непередбачуваний: мобільний застосунок був офлайн три години, сервіс ретраїв відправив пачку через 20 хвилин, брокер накопичив backlog після інциденту.

#### 3.2 Чому агрегувати треба за event time

```python
# Неправильно: результат залежить від того, коли система встигла обробити
df.groupBy(F.window("processing_time", "1 hour")).count()

# Правильно: результат детермінований і відтворюваний
df.groupBy(F.window("event_time", "1 hour")).count()
```

Агрегація за processing time дає **невідтворювані** результати: перезапуск конвеєра з іншою швидкістю дасть інший розподіл подій по годинах. Агрегація за event time дає той самий результат незалежно від того, коли й з якою швидкістю ви обробляли дані. Це властивість, без якої неможливе ані перепрораховування історії, ані порівняння потокового результату з пакетним.

Ціна: система мусить якось вирішувати, коли вікно можна вважати закритим. Саме цю задачу розв'язує watermark.

### 4. Вікна

#### 4.1 Навіщо

Агрегація над нескінченним потоком не має сенсу без обмеження області. **Вікно** розбиває нескінченний потік на скінченні порції за часом, до кожної з яких агрегація застосовна.

![Віконна агрегація за часом події](https://spark.apache.org/docs/latest/img/structured-streaming-window.png)

*Агрегація в перекривних вікнах за часом події: одна подія може належати кільком вікнам одночасно. Джерело: [Spark Structured Streaming Programming Guide](https://spark.apache.org/docs/latest/structured-streaming-programming-guide.html)*

#### 4.2 Типи вікон

**Tumbling (перекидні)** — неперекривні вікна фіксованої довжини. Кожна подія потрапляє рівно в одне вікно.

```python
df.groupBy(F.window("event_time", "10 minutes"), "zone_id").count()
```
```
|--10 min--|--10 min--|--10 min--|
```
Застосування: регулярні звіти за період — «кількість подій за кожні 10 хвилин».

**Sliding (ковзні)** — вікна фіксованої довжини з кроком, меншим за довжину. Вікна перекриваються, подія потрапляє в кілька.

```python
df.groupBy(F.window("event_time", "10 minutes", "5 minutes"), "zone_id").count()
```
```
|-----10 min-----|
     |-----10 min-----|
          |-----10 min-----|
```
Застосування: плавні ковзні метрики — «середнє за останні 10 хвилин, оновлюване кожні 5». Ціна: обсяг стану зростає пропорційно `довжина / крок`.

**Session (сеансові)** — динамічна довжина: вікно триває, доки події надходять із паузою меншою за заданий проміжок бездіяльності.

```python
df.groupBy(F.session_window("event_time", "15 minutes"), "user_id").count()
```
Застосування: аналіз сеансів користувача, де тривалість заздалегідь невідома.

#### 4.3 Структура результату

`F.window(...)` повертає структуру з полями `start` і `end`:

```python
(df.groupBy(F.window("event_time", "10 minutes"), "zone_id")
   .agg(F.count("*").alias("trips"))
   .select(F.col("window.start").alias("window_start"),
           F.col("window.end").alias("window_end"),
           "zone_id", "trips"))
```

Межі: `start` включно, `end` виключно.

### 5. Watermark і пізні дані

#### 5.1 Проблема

Вікно `10:00–10:10` треба колись закрити й видалити його стан із пам'яті. Але подія з `event_time = 10:07` теоретично може прийти будь-коли — через хвилину, через годину, через добу. Тримати стан усіх вікон вічно неможливо: пам'ять скінченна.

#### 5.2 Визначення

**Watermark** — формальне твердження системи: «події, старіші за (максимальний побачений event_time − поріг), більше не приймаються».

```python
(df.withWatermark("event_time", "10 minutes")
   .groupBy(F.window("event_time", "5 minutes"), "zone_id")
   .count())
```

Механіка:
```
Максимальний побачений event_time:  11:30
Поріг (watermark delay):            10 хвилин
Поточний watermark:                 11:20

→ Вікна, що повністю завершилися до 11:20, закриваються;
  їхній стан звільняється.
→ Подія з event_time = 11:05, що прийшла зараз, ВІДКИДАЄТЬСЯ.
```

![Обробка пізніх даних](https://spark.apache.org/docs/latest/img/structured-streaming-late-data.png)

*Пізня подія, що прийшла після просування watermark, не оновлює вже закрите вікно. Джерело: [Spark Structured Streaming Programming Guide](https://spark.apache.org/docs/latest/structured-streaming-programming-guide.html)*

Watermark рухається **тільки вперед** і оновлюється за максимальним побаченим event time, а не за годинником системи. Це означає, що в потоці без нових подій watermark стоїть на місці, і вікна не закриваються.

#### 5.3 Компроміс

Поріг watermark — це прямий обмін між трьома величинами:

| Поріг | Затримка результату | Повнота | Обсяг стану |
|---|---|---|---|
| Малий (1 хв) | Низька | Багато пізніх подій втрачається | Малий |
| Великий (24 год) | Висока | Майже нічого не втрачається | Дуже великий |

Правильне значення визначається **емпірично**: виміряйте фактичний розподіл затримок `ingestion_time − event_time` у ваших даних і візьміть, скажімо, 99-й перцентиль. Довільно обране «10 хвилин» — це або втрата даних, або марна витрата пам'яті.

**Дуже пізні дані не зникають безслідно**, якщо джерело — Kafka з довгим утриманням: їх можна дообробити окремим пакетним конвеєром, що періодично перераховує старі вікна. Це один із мотивів гібридних архітектур (розділ 8).

#### 5.4 Взаємодія з режимами виведення

![Watermark у режимі update](https://spark.apache.org/docs/latest/img/structured-streaming-watermark-update-mode.png)

*Режим update: результат вікна публікується щоразу, коли він змінюється, включно з оновленнями від пізніх подій, які ще потрапили в межі watermark. Джерело: [Spark Structured Streaming Programming Guide](https://spark.apache.org/docs/latest/structured-streaming-programming-guide.html)*

![Watermark у режимі append](https://spark.apache.org/docs/latest/img/structured-streaming-watermark-append-mode.png)

*Режим append: результат вікна публікується лише один раз — коли watermark пройшов його межу і вікно більше не може змінитися. Звідси затримка публікації, що дорівнює порогу watermark. Джерело: [Spark Structured Streaming Programming Guide](https://spark.apache.org/docs/latest/structured-streaming-programming-guide.html)*

### 6. Режими виведення

**Output mode** визначає, що саме записується в приймач на кожному тригері.

| Режим | Що пишеться | Обмеження |
|---|---|---|
| **`append`** | Тільки нові рядки, які більше ніколи не зміняться | Для агрегацій **обов'язковий** watermark; результат вікна з'являється із затримкою |
| **`update`** | Рядки, що змінилися з попереднього тригера | Приймач має підтримувати оновлення (Kafka з ключем, `foreachBatch` із MERGE) |
| **`complete`** | Уся таблиця результату повністю | Тільки для агрегацій; стан ніколи не звільняється — придатний лише для малої кардинальності |

#### 6.1 Як обирати

```
Чи є агрегація?
├── Ні  → append (єдиний доступний)
└── Так → Чи потрібні проміжні оновлення вікна?
          ├── Ні, потрібен фінальний результат
          │     → append + withWatermark
          │       (файловий приймач, Iceberg/Delta)
          ├── Так, потрібно бачити оновлення
          │     → update + приймач з upsert
          └── Потрібен повний знімок і результат маленький
                → complete (дашборд, топ-N, мала кардинальність)
```

Найпоширеніша помилка новачків — `complete` для агрегації з високою кардинальністю: стан росте нескінченно, і застосунок помирає з OOM через кілька годин.

### 7. Стан, checkpoint і відмовостійкість

#### 7.1 Що таке стан

Потокові операції поділяються на дві категорії:

**Stateless (без стану):** `select`, `filter`, `withColumn`, `explode`. Кожна подія обробляється незалежно; нічого запам'ятовувати не треба.

**Stateful (зі станом):** віконні агрегації, `dropDuplicates`, join-и потоків, `flatMapGroupsWithState`. Потребують збереження проміжних даних між мікробатчами.

Стан зберігається в **State Store** — сховищі на executor-ах, партиційованому за ключем. Реалізації: HDFSBackedStateStore (за замовчуванням, у пам'яті з бекапом у файли) і RocksDBStateStore (на диску з кешем у пам'яті — краще для великого стану, менше навантаження на GC).

#### 7.2 Checkpoint

**Checkpoint** — каталог у надійному сховищі, у якому Spark зберігає все, що потрібно для відновлення потокового запиту:

```
checkpointLocation/
    metadata          ← ідентифікатор запиту
    offsets/          ← до якого offset-у прочитано з джерела (write-ahead log)
    commits/          ← які батчі повністю завершені
    sources/          ← метадані джерел
    state/            ← знімки State Store по батчах і партиціях
```

Це не опція. Без `checkpointLocation` потоковий запит із агрегацією не запуститься.

#### 7.3 Як працює відновлення

```
1. Прочитати останній завершений batch_id з commits/
2. Прочитати з offsets/ діапазон, який мав оброблятися далі
3. Відновити стан із state/ на цей момент
4. Продовжити обробку з тієї самої точки
```

Механізм дає **exactly-once щодо стану**: агрегати не будуть пораховані двічі навіть після аварійного перезапуску. Але щодо **приймача** гарантія залежить від самого приймача: файловий приймач Spark використовує журнал комітів, транзакційні таблиці — атомарний коміт, а довільний зовнішній сервіс у `foreachBatch` потребує власної ідемпотентності (тут і використовується `batch_id`).

#### 7.4 Правила експлуатації

**Checkpoint не можна видаляти між запусками** — це втрата позиції й стану. Перезапуск із порожнім checkpoint означає або повторну обробку всієї історії, або пропуск даних, залежно від `startingOffsets`.

**Кожен запит — власний checkpoint.** Два різні запити з одним каталогом зіпсують стан один одному.

**Не всі зміни коду сумісні з наявним checkpoint.** Безпечно: змінити фільтр, додати колонку в проєкцію, змінити параметри приймача. Небезпечно або заборонено: змінити ключі групування, змінити тип вікна, змінити схему стану, змінити перелік стежених джерел. Такі зміни потребують нового checkpoint і, зазвичай, перерахунку.

**Компакція checkpoint.** Каталоги `offsets/` і `commits/` ростуть; Spark періодично зливає їх у файли з суфіксом `.compact`. Для довгих запитів варто стежити за кількістю файлів і розміром стану.

#### 7.5 Обмеження stateful-операцій

- **`dropDuplicates` у потоці** вимагає зберігати всі побачені ключі. Без watermark стан росте нескінченно; з watermark дедублікація гарантована лише в його межах.
- **Join двох потоків** вимагає буферизувати обидві сторони. Watermark обов'язковий для обох, і в умові з'єднання має бути обмеження за часом, інакше стан буде зростати без межі.

```python
(impressions.withWatermark("imp_time", "2 hours")
   .join(clicks.withWatermark("click_time", "3 hours"),
         F.expr("""
             ad_id = click_ad_id AND
             click_time >= imp_time AND
             click_time <= imp_time + interval 1 hour
         """),
         how="leftOuter"))
```

- **Join потоку зі статичною таблицею** значно простіший: стан не потрібен, статична сторона просто підвантажується. Але вона не оновлюється автоматично — для довідників, що змінюються, потрібен окремий механізм перезавантаження.

### 8. Архітектури: Lambda та Kappa

#### 8.1 Lambda

Історично перша відповідь на питання «як поєднати швидкість і точність»: **два паралельні конвеєри над одними джерелами**.

```
                     ┌──► SPEED LAYER (потік) ───► приблизний результат ──┐
джерело подій ───────┤                                                     ├──► serving
                     └──► BATCH LAYER (пакет) ───► точний результат ───────┘
```

- **Speed layer** дає результат негайно, але приблизний: пізні дані ще не враховані.
- **Batch layer** періодично перераховує все з нуля й перезаписує результат точним.
- **Serving layer** об'єднує обидва при відповіді на запит.

Плюс: точність гарантована перерахунком; пізні дані та історичні виправлення враховуються.
Мінус, який і вбив підхід у чистому вигляді: **логіка дублюється у двох кодових базах**. Кожна зміна бізнес-правила вноситься двічі, різними інструментами, і розбіжність між ними — постійне джерело інцидентів.

#### 8.2 Kappa

Відповідь на цю ваду: **один конвеєр, один код**. Немає окремого пакетного шару — є лише потокова обробка. Перерахунок історії робиться **тим самим кодом**, просто перечитуванням логу з початку.

```
джерело подій (лог із довгим утриманням)
        │
        └──► STREAM PROCESSING ───► результат
                    ↑
        перерахунок = перечитати лог з offset 0 новою версією коду
```

Передумови, без яких Kappa не працює:
- Лог подій зберігає достатньо історії (Kafka з довгим retention або tiered storage в object storage).
- Обробка ідемпотентна щодо приймача.
- Джерело істини — саме потік подій, а не стан у базі.

Типова процедура зміни логіки: запустити нову версію конвеєра паралельно, дати їй наздогнати історію в окрему таблицю, звірити результати, переключити споживачів, зупинити стару. Це і є перевага єдиної кодової бази.

#### 8.3 Що використовують на практиці

Чиста Lambda сьогодні рідкість. Найпоширеніша конфігурація — **гібрид на спільній кодовій базі**: потоковий конвеєр наповнює таблицю в реальному часі, а періодичний пакетний перерахунок **того самого коду** (наприклад, через `trigger(availableNow=True)` або dbt-модель поверх тих самих джерел) виправляє наслідки пізніх даних. Транзакційні table format-и роблять таке перезаписування партицій безпечним і атомарним.

### 9. Порівняння движків потокової обробки

| | **Spark Structured Streaming** | **Apache Flink** | **Kafka Streams** |
|---|---|---|---|
| Модель | Мікробатчі (є continuous) | Запис за записом | Запис за записом |
| Типова затримка | 0,5–5 с | 10–100 мс | 10–100 мс |
| Форма | Кластерний движок | Кластерний движок | **Бібліотека** всередині вашого застосунку |
| API | DataFrame / SQL | DataStream, Table API, SQL | DSL і Processor API |
| Робота з часом | Watermark, вікна | Найбагатша модель: watermark, тригери, allowed lateness, side outputs | Вікна, grace period |
| Стан | State Store (HDFS / RocksDB) | RocksDB із інкрементальними знімками | RocksDB + changelog-топік |
| Джерела/приймачі | Дуже широкий набір | Широкий набір | Тільки Kafka |
| Спільність із пакетом | Той самий код і движок | Уніфіковане API | Немає |

**Як обирати.** Spark — коли пакетна обробка вже на Spark і затримка в секунди прийнятна: спільна кодова база, спільні навички, спільна інфраструктура. Flink — коли затримка критична або потрібна складна логіка з часом і станом (обробка ускладнених патернів подій, точні тригери, кілька рівнів пізності). Kafka Streams — коли обробка Kafka→Kafka вбудовується прямо в мікросервіс і окремий кластер розгортати не хочеться.

### 10. Експлуатація потокових конвеєрів

#### 10.1 Що моніторити

```python
query.status            # {"message": ..., "isDataAvailable": ..., "isTriggerActive": ...}
query.lastProgress      # метрики останнього мікробатча
query.recentProgress    # історія
```

Ключові метрики з `lastProgress`:

| Метрика | Значення |
|---|---|
| `inputRowsPerSecond` | Швидкість надходження |
| `processedRowsPerSecond` | Швидкість обробки |
| `batchDuration` | Тривалість мікробатча |
| `stateOperators[].numRowsTotal` | Розмір стану |
| `sources[].numInputRows` | Скільки рядків прийнято |
| `durationMs` | Розкладка часу по фазах |

**Головний індикатор здоров'я — співвідношення `inputRowsPerSecond` і `processedRowsPerSecond`.** Якщо перше стабільно більше за друге, конвеєр не встигає, і відставання (lag) зростатиме нескінченно.

**Consumer lag у Kafka** — друга обов'язкова метрика: різниця між останнім offset-ом у партиції та закомітованим offset-ом групи. Зростаючий lag — прямий сигнал, що потрібно збільшувати паралелізм або зменшувати вартість обробки.

#### 10.2 Типові проблеми

| Симптом | Причина | Важіль |
|---|---|---|
| Lag зростає лінійно | Обробка повільніша за надходження | Більше партицій і executor-ів; спростити логіку |
| Стан росте нескінченно | Немає watermark або він занадто великий; `complete` mode | Додати/звузити watermark; змінити режим виведення |
| Батчі різної тривалості | Нерівномірне надходження | `maxOffsetsPerTrigger` для обмеження розміру батча |
| OOM на executor-ах | Великий стан у пам'яті | RocksDB State Store; більше партицій |
| Перезапуск обробляє все заново | Втрачено або змінено checkpoint | Відновити каталог; не змінювати несумісно |
| Багато дрібних файлів на виході | Частий тригер + багато партицій | Рідший тригер; компакція таблиці |

#### 10.3 Дрібні файли

Потокові конвеєри — головне джерело small files problem: кожен мікробатч кожної партиції пише файл. При тригері раз на 10 секунд і 200 партиціях це 1,7 мільйона файлів на добу.

Важелі: рідший тригер, зменшення кількості вихідних партицій (`coalesce` перед записом у `foreachBatch`), і регулярна компакція таблиці окремим процесом обслуговування.

## Ключові терміни

| Термін | Визначення |
|---|---|
| **Unbounded / bounded data** | Нескінченний потік / скінченний набір даних |
| **Micro-batch** | Модель, у якій потік обробляється маленькими пакетами як звичайні запити |
| **Continuous processing** | Обробка запис за записом із наднизькою затримкою |
| **Event time** | Час, коли подія сталася (записаний у самій події) |
| **Ingestion time** | Час потрапляння події в брокер |
| **Processing time** | Час обробки події системою |
| **Tumbling window** | Неперекривні вікна фіксованої довжини |
| **Sliding window** | Перекривні вікна фіксованої довжини з меншим кроком |
| **Session window** | Вікно динамічної довжини, що закривається після паузи бездіяльності |
| **Watermark** | Межа терпіння до запізнень: події, старіші за (max event_time − поріг), відкидаються |
| **Late data** | Події, що прийшли після просування watermark за їхнє вікно |
| **Output mode** | Що записується в приймач: `append`, `update`, `complete` |
| **Trigger** | Коли запускається наступний мікробатч |
| **`availableNow`** | Тригер «обробити все накопичене й зупинитися» — пакетний запуск потокового запиту |
| **`maxOffsetsPerTrigger` / `maxFilesPerTrigger`** | Обмеження обсягу одного мікробатча |
| **Stateless / stateful операції** | Операції без збереження стану між батчами / зі станом |
| **State Store** | Партиційоване сховище стану на executor-ах; HDFSBacked або RocksDB |
| **Checkpoint** | Каталог із offset-ами, комітами й знімками стану для відновлення запиту |
| **`checkpointLocation`** | Обов'язковий параметр потокового запису |
| **Write-ahead log (offsets)** | Журнал того, який діапазон джерела має оброблятися в батчі |
| **`foreachBatch`** | Приймач, що дає мікробатч як звичайний DataFrame для довільної логіки |
| **`batch_id`** | Монотонний ідентифікатор мікробатча; основа ідемпотентності приймача |
| **Stream-stream join** | Join двох потоків; вимагає watermark з обох сторін і часового обмеження в умові |
| **Stream-static join** | Join потоку зі статичною таблицею; без стану, але статична сторона не оновлюється сама |
| **Lambda-архітектура** | Паралельні швидкий і пакетний шари; дублювання логіки |
| **Kappa-архітектура** | Єдиний потоковий конвеєр; перерахунок = перечитування логу з початку |
| **Consumer lag** | Різниця між останнім offset-ом і закомітованим; головна метрика відставання |
| **`inputRowsPerSecond` / `processedRowsPerSecond`** | Швидкість надходження проти швидкості обробки |
| **Apache Flink** | Движок потокової обробки з обробкою запис за записом і багатою моделлю часу |
| **Kafka Streams** | Бібліотека потокової обробки Kafka→Kafka всередині застосунку |
