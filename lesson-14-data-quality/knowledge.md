# Заняття 14. Якість даних та data governance

## Про що це заняття

Конвеєр, який відпрацював без помилок, не означає, що дані правильні. Job завершився зеленим, таблиці записані, дашборд оновився — і при цьому третина рядків втрачена через помилку в межах фільтра, суми подвоєні через join, а колонка `country` містить `"N/A"`, `"n/a"`, `null` і `"—"` як чотири різні значення.

Це заняття — про те, як перевести «дані виглядають нормально» у формальні, автоматично перевірювані твердження, і як вбудувати ці перевірки в конвеєр так, щоб некоректні дані не доходили до споживача.

Матеріал складається з трьох рівнів. **Перший** — вимірювальний: які виміри якості існують і як їх виразити метриками. **Другий** — інженерний: якими інструментами описати очікування, куди в конвеєрі вставити перевірку і що робити при провалі. **Третій** — організаційний: data governance та її місце в DAMA-DMBOK, контракти на дані, походження (lineage), робота з персональними даними, ролі й операційні моделі.

Після заняття ви зможете: розкласти розпливчасте «дані погані» на конкретні виміри й метрики; описати схему та обмеження декларативно; відрізнити детективний контроль від превентивного і побудувати gate за патерном Write-Audit-Publish; сформулювати контракт на дані та пояснити роль lineage; описати компоненти data governance, ролі (Owner / Steward / Custodian) та операційні моделі, і розмістити якість даних у колесі DAMA.

## Що треба знати заздалегідь

- Обробка даних у DataFrame API (Spark) або аналогічному інструменті.
- Шарувата архітектура конвеєра і поняття ідемпотентності.
- Транзакційні table format-и: snapshot, атомарний коміт, rollback.
- Оркестрація: DAG, залежності між задачами, поведінка при провалі.
- SQL на рівні агрегацій і join-ів.

## Основний матеріал

### 1. Виміри якості даних

«Погані дані» — не діагноз. Щоб з проблемою можна було працювати, її треба розкласти на виміри, кожен з яких вимірюється числом.

#### 1.1 Шість основних вимірів

| Вимір | Питання | Приклад метрики |
|---|---|---|
| **Completeness** (повнота) | Чи всі очікувані дані на місці? | Частка не-NULL значень у обов'язковій колонці; кількість рядків проти очікуваної |
| **Validity** (валідність) | Чи відповідають значення формату й домену? | Частка рядків, де `fare >= 0`; відповідність email регулярному виразу |
| **Accuracy** (точність) | Чи відповідають значення реальності? | Частка поїздок із фізично можливою швидкістю; звірка з еталонним джерелом |
| **Consistency** (узгодженість) | Чи не суперечать дані самі собі та іншим таблицям? | `dropoff_ts > pickup_ts`; сума в факті = сума в джерелі; цілісність зовнішніх ключів |
| **Uniqueness** (унікальність) | Чи немає небажаних дублікатів? | `count(*) = count(distinct business_key)` |
| **Timeliness** (своєчасність) | Чи достатньо свіжі дані? | Затримка між подією та її появою в таблиці; вік останнього завантаження |

Часто додають сьомий вимір — **Uniformity / Conformity** (однорідність): чи однакові одиниці виміру, формати дат, кодування категорій. Кілометри в колонці, де решта записів у милях, — це не невалідне значення, а неоднорідне.

#### 1.2 Формалізація: від опису до перевірки

Кожен вимір перетворюється на пару «метрика + поріг».

```python
from pyspark.sql import functions as F

total = df.count()

metrics = df.select(
    # Completeness
    (F.count("trip_id") / F.lit(total)).alias("completeness_trip_id"),

    # Validity
    (F.sum((F.col("fare_amount") >= 0).cast("int")) / F.lit(total)).alias("validity_fare"),

    # Consistency
    (F.sum((F.col("dropoff_ts") > F.col("pickup_ts")).cast("int")) / F.lit(total))
        .alias("consistency_time_order"),

    # Uniqueness
    (F.countDistinct("trip_id") / F.lit(total)).alias("uniqueness_trip_id"),

    # Timeliness
    F.max("ingested_at").alias("last_load_at"),
)
```

Набір таких метрик із порогами й поточними значеннями називають **DQ scorecard**. Його цінність у тому, що він дає **тренд**: одне вимірювання каже мало, а падіння completeness з 99,8 % до 94 % за тиждень — конкретний сигнал.

#### 1.3 Правила проти профілювання

Два принципово різні підходи до виявлення проблем:

**Правила (rule-based).** Ви заздалегідь формулюєте, що вважається правильним: `fare >= 0`, `country IN (...)`, `id IS UNIQUE`. Дає точні, зрозумілі, детерміновані перевірки. Обмеження: ловить тільки те, що ви передбачили.

**Профілювання й аномалії (data profiling / anomaly detection).** Система вимірює статистичні характеристики (розподіл, кардинальність, частку NULL, середнє, квантилі) і сигналізує про відхилення від історичної норми. Ловить непередбачені проблеми — наприклад, різку зміну розподілу після оновлення джерела. Обмеження: хибні спрацювання, потреба в історії, складніша інтерпретація.

Зріла система якості використовує обидва: правила — як жорсткий контракт, профілювання — як сітка безпеки.

### 2. Декларативний опис схеми та обмежень

#### 2.1 Ідея

Замість того щоб писати перевірки як послідовність `if`-ів, схему й обмеження описують **декларативно** — як специфікацію, яку інструмент застосовує до датафрейму. Це дає три переваги: специфікація читається як документація, вона версіонується разом із кодом, і одна й та сама специфікація використовується і як валідатор, і як опис контракту.

#### 2.2 Pandera: схема як типізований клас

**Pandera** — бібліотека валідації датафреймів (pandas, Polars, PySpark). Схема оголошується як клас із типізованими полями й перевірками.

```python
import pandera as pa
from pandera.typing import Series

class TripSchema(pa.DataFrameModel):
    trip_id:     Series[int]   = pa.Field(unique=True, nullable=False)
    pickup_ts:   Series[pa.DateTime] = pa.Field(nullable=False)
    dropoff_ts:  Series[pa.DateTime] = pa.Field(nullable=False)
    zone_id:     Series[int]   = pa.Field(ge=1, le=265)
    fare_amount: Series[float] = pa.Field(ge=0, le=10_000)
    payment:     Series[str]   = pa.Field(isin=["cash", "card", "wallet"])

    @pa.check("dropoff_ts")
    def dropoff_after_pickup(cls, s: Series) -> Series[bool]:
        return s > cls.pickup_ts

    class Config:
        strict = True          # заборонити колонки, яких немає у схемі
        coerce = True          # приводити типи автоматично
```

Застосування:

```python
validated = TripSchema.validate(df)                 # виняток при першій помилці
validated = TripSchema.validate(df, lazy=True)      # зібрати ВСІ порушення одразу
```

`lazy=True` — принципово важливий режим: без нього ви дізнаєтесь про одну проблему, виправите її та отримаєте наступну. З ним отримуєте повний перелік порушень за один прохід.

Pandera також дозволяє відділити коректні рядки від некоректних замість того, щоб падати:

```python
try:
    clean = TripSchema.validate(df, lazy=True)
except pa.errors.SchemaErrors as err:
    bad_idx = err.failure_cases["index"].unique()
    quarantine = df.loc[bad_idx]
    clean = df.drop(index=bad_idx)
```

**Ніша Pandera:** легка, вбудовується прямо у функції трансформації, чудова для юніт-тестів і для валідації на межах модулів. Не має вбудованої звітності та історії запусків.

#### 2.3 Great Expectations: набір очікувань і звітність

**Great Expectations (GX)** — повноцінна платформа валідації. Її одиниця — **expectation**: іменоване, параметризоване твердження про дані.

![Робочий процес Great Expectations](https://docs.greatexpectations.io/assets/images/gx_workflow_steps_and_components-a1511e31cccadb7158f1e8665cc90628.png)

*Компоненти GX і порядок роботи: підключення до джерела → визначення набору очікувань → запуск валідації → аналіз результатів. Джерело: [Great Expectations Docs](https://docs.greatexpectations.io/docs/core/introduction/gx_overview)*

```python
import great_expectations as gx

context = gx.get_context()
suite = context.suites.add(gx.ExpectationSuite(name="trips_suite"))

# Completeness
suite.add_expectation(gx.expectations.ExpectColumnValuesToNotBeNull(column="trip_id"))

# Validity
suite.add_expectation(gx.expectations.ExpectColumnValuesToBeBetween(
    column="fare_amount", min_value=0, max_value=10_000))
suite.add_expectation(gx.expectations.ExpectColumnValuesToBeInSet(
    column="payment", value_set=["cash", "card", "wallet"]))

# Uniqueness
suite.add_expectation(gx.expectations.ExpectCompoundColumnsToBeUnique(
    column_list=["trip_id", "pickup_ts"]))

# Обсяг
suite.add_expectation(gx.expectations.ExpectTableRowCountToBeBetween(
    min_value=1_000_000, max_value=5_000_000))
```

Ключові поняття GX:

| Поняття | Роль |
|---|---|
| **Expectation** | Одне твердження про дані |
| **Expectation Suite** | Іменований набір очікувань для датасету |
| **Data Source / Asset / Batch** | Звідки беруться дані та який їх зріз перевіряється |
| **Validation Definition** | Зв'язка «цей batch перевіряється цим suite» |
| **Checkpoint** | Запуск валідації з набором дій за результатом (сповіщення, збереження) |
| **Data Docs** | Згенерований HTML-звіт із результатами |

Важлива властивість: майже кожне очікування підтримує параметр **`mostly`** — частку рядків, які мають його задовольнити.

```python
gx.expectations.ExpectColumnValuesToNotBeNull(column="tip_amount", mostly=0.95)
```

Це відображає реальність: вимога «жодного NULL» часто занадто жорстка, а «не більше 5 % NULL» — робочий поріг, що не породжує постійних хибних тривог.

#### 2.4 Soda: чеки як YAML і SQL

**Soda Core** відрізняється від Pandera і GX не набором правил, а **місцем виконання**. Pandera і GX працюють у Python-процесі над датафреймом — дані спершу треба підняти в пам'ять. Soda описує правила в **YAML (SodaCL)**, компілює їх у **SQL** і виконує **у самому сховищі**; назад повертаються лише метрики. Для таблиці на мільярд рядків це різниця між «неможливо» і «кілька секунд».

Конфігурація складається з двох файлів. `configuration.yml` описує підключення:

```yaml
data_source taxi:
  type: duckdb
  path: dq.duckdb
```

`checks.yml` описує самі правила:

```yaml
checks for silver_yellow_trips:
  # Completeness
  - missing_count(fare_amount) = 0
  # Validity
  - invalid_count(PULocationID) = 0:
      valid min: 1
      valid max: 265
  # Поріг із двома рівнями серйозності
  - invalid_percent(passenger_count):
      valid min: 1
      valid max: 9
      warn: when > 2 %
      fail: when > 5 %
  # Uniqueness за складеним ключем
  - duplicate_count(tpep_pickup_datetime, PULocationID, fare_amount) = 0
  # Consistency: довільний SQL
  - failed rows:
      name: total_amount дорівнює сумі компонентів
      fail query: |
        SELECT * FROM silver_yellow_trips
        WHERE abs(total_amount - (fare_amount + extra + mta_tax + tip_amount)) > 0.01
```

Дві властивості, яких немає в Pandera і GX:

**Два рівні серйозності.** `warn` і `fail` розділені: `warn` фіксує деградацію, але не зупиняє конвеєр, `fail` — зупиняє. У GX є `mostly`, але він дає лише бінарний результат; окремого стану WARN немає.

**Exit code як інтерфейс.** `soda scan` — це передусім CLI: `0` — усі чеки пройшли, `2` — є FAIL, `3` — є WARN або помилка. Тому gate в оркестраторі будується без жодного Python-коду: `BashOperator` з `soda scan` впаде сам. Прапорець `--scan-results-file` додатково віддає машиночитний JSON для дашборду.

Практичне застереження щодо встановлення: `soda-core` залежить від `minimal-snowplow-tracker`, який займає той самий модуль `snowplow_tracker`, що й `dbt-core`. В одному оточенні вони не співіснують, тому Soda ставлять окремим venv-ом або контейнером. Це типово для DQ-інструментів: їх ізолюють від оточення самого конвеєра.

#### 2.5 Порівняння підходів

| | Pandera | Great Expectations | Тести dbt | Soda |
|---|---|---|---|---|
| Форма опису | Python-клас | Suite очікувань | YAML + SQL | YAML (SodaCL) |
| Де виконується | У процесі обробки | Окремий крок або в процесі | У сховищі | У сховищі |
| Звітність | Мінімальна | Data Docs, історія | Логи запуску | Дашборд, історія |
| Профілювання | Ні | Так | Ні | Так |
| Поріг «mostly» | Через власні перевірки | Вбудований (`mostly`) | Через `config.severity` і власні тести | Вбудований (`warn` / `fail`) |
| Найкраще для | Валідація всередині коду й тестів | Контроль на межах шарів зі звітністю | Перевірки моделей сховища | Моніторинг якості як сервіс |

Ці інструменти не взаємовиключні. Типова конфігурація: Pandera — на межах функцій у коді; тести dbt — на моделях сховища; GX або Soda — як gate між шарами й джерело звітності.

### 3. Куди вставити перевірку: детективний і превентивний контроль

#### 3.1 Дві стратегії

**Detective (детективний контроль)** — перевірка виконується **після** запису. Дані вже в цільовій таблиці; перевірка виявляє проблему й повідомляє про неї.

```
трансформація → ЗАПИС у Gold → перевірка → alert
                     ↑
            споживач уже може це прочитати
```

- Плюси: просто реалізувати, не блокує конвеєр, дає моніторинг і тренд.
- Мінуси: некоректні дані **вже видимі** споживачам. Дашборд уже показав неправильну цифру.

**Preventive (превентивний контроль, gate)** — перевірка виконується **до** публікації. Якщо вона не пройдена, дані не потрапляють до споживача.

```
трансформація → запис у СТЕЙДЖ → перевірка → ✔ публікація
                                            → ✘ зупинка + alert
```

- Плюси: некоректні дані ніколи не доходять до споживача.
- Мінуси: складніша реалізація, потрібен проміжний стан, конвеєр зупиняється.

#### 3.2 Де що доречно

| Точка конвеєра | Тип контролю | Що перевіряється |
|---|---|---|
| Приймання від джерела | Detective | Наявність файлів, обсяг, свіжість, відповідність схеми |
| Bronze → Silver | Preventive | Схема, типи, обов'язкові поля, дублікати |
| Silver → Gold | Preventive | Бізнес-правила, узгодженість між шарами, референційна цілісність |
| Gold-вітрини | Detective | Аномалії метрик, порівняння з історією, свіжість |

Загальний принцип: **чим ближче до споживача, тим суворіший контроль**. Пропустити сумнівний рядок у Bronze — прийнятно (він потрібен для розслідування). Пропустити його у вітрину, яку читає керівництво, — ні.

#### 3.3 Що робити при провалі

Провал перевірки не завжди означає «зупинити все». Розумна система розрізняє рівні:

| Рівень | Дія |
|---|---|
| `info` | Зафіксувати метрику, нічого не робити |
| `warn` | Продовжити, надіслати сповіщення, позначити таблицю прапорцем |
| `error` | Не публікувати, зупинити гілку конвеєра, повідомити відповідального |

Окремий патерн — **quarantine**: некоректні рядки не відкидаються, а відводяться в окрему таблицю з причиною відхилення. Це дає можливість розібратися й перезалити їх пізніше, замість того щоб втратити назавжди.

### 4. Write-Audit-Publish

#### 4.1 Патерн

**Write-Audit-Publish (WAP)** — канонічна реалізація превентивного контролю. Три фази:

```
┌─ WRITE ──────────────────────────────────────────────┐
│ Записати результат у місце, невидиме для споживачів:  │
│ окрему гілку таблиці, стейдж-таблицю або snapshot,    │
│ на який ще не переведено вказівник                    │
└──────────────────────┬───────────────────────────────┘
                       ▼
┌─ AUDIT ──────────────────────────────────────────────┐
│ Виконати перевірки якості РІВНО над цими даними       │
│ (не над джерелом і не над старою версією)             │
└──────────────────────┬───────────────────────────────┘
              ┌────────┴────────┐
        пройдено            не пройдено
              ▼                 ▼
┌─ PUBLISH ─────────┐  ┌─ ABORT ─────────────────────┐
│ Атомарно зробити  │  │ Нічого не публікувати       │
│ дані видимими:    │  │ Споживач бачить попередню   │
│ переключити гілку │  │ коректну версію             │
│ або вказівник     │  │ Сповістити відповідального  │
└───────────────────┘  └─────────────────────────────┘
```

Ключова вимога — **атомарність публікації**. Якщо «публікація» означає копіювання тисячі файлів, вона не атомарна, і споживач може прочитати проміжний стан. Тому WAP природно лягає на транзакційні table format-и, де публікація — це зміна одного вказівника.

#### 4.2 Реалізації

**Через гілки (Iceberg branching):**

```sql
-- WRITE: пишемо в гілку, а не в main
ALTER TABLE gold.fact_trip CREATE BRANCH etl_run_2026_08_12;
-- (writer записує з посиланням на гілку)

-- AUDIT: перевіряємо саме цю гілку
SELECT count(*) FROM gold.fact_trip VERSION AS OF 'etl_run_2026_08_12'
WHERE fare_amount < 0;

-- PUBLISH: атомарно переносимо main на перевірену гілку
CALL system.fast_forward('gold.fact_trip', 'main', 'etl_run_2026_08_12');
```

**Через стейдж-таблицю та обмін іменами:**

```sql
CREATE TABLE gold.fact_trip__staging AS SELECT ...;
-- перевірки над __staging
ALTER TABLE gold.fact_trip RENAME TO gold.fact_trip__old;
ALTER TABLE gold.fact_trip__staging RENAME TO gold.fact_trip;
```

**Через оркестратор:** три окремі задачі в DAG — `build_staging` → `run_quality_checks` → `publish`, де третя виконується тільки за успіху другої. Це найпростіший варіант, доступний у будь-якому стеку.

#### 4.3 Аудит-запити, які варто мати завжди

Незалежно від інструменту, є набір перевірок, які ловлять більшість реальних аварій:

```sql
-- 1. Різка зміна обсягу відносно попереднього запуску
SELECT count(*) AS rows_now FROM staging;
-- порівняти з історією; відхилення >20% — привід зупинитися

-- 2. Дублікати за бізнес-ключем
SELECT business_key, count(*) FROM staging
GROUP BY business_key HAVING count(*) > 1;

-- 3. Узгодженість агрегату з джерелом (перевірка на розмноження рядків)
SELECT (SELECT sum(amount) FROM staging) - (SELECT sum(amount) FROM source) AS diff;

-- 4. Референційна цілісність
SELECT count(*) FROM staging f
LEFT ANTI JOIN dim_zone d ON f.zone_id = d.zone_id;

-- 5. Відсутність «дірок» у часовому ряді
SELECT event_date FROM expected_dates
LEFT ANTI JOIN (SELECT DISTINCT event_date FROM staging) s USING (event_date);
```

П'ята перевірка — найнедооціненіша. Втрата цілої доби через помилку в межах фільтра не порушує жодного правила про NULL, унікальність чи домен значень, і без явної перевірки повноти покриття залишається непоміченою.

### 5. Контракти на дані

#### 5.1 Проблема

Команда, що виробляє дані, і команда, що їх споживає, не мають спільної формальної домовленості. Продюсер перейменовує колонку — у споживача ламається дашборд. Продюсер змінює одиниці виміру — у споживача мовчки псуються цифри. Проблема не технічна, а координаційна.

**Data contract** — формалізована, версіонована угода між постачальником і споживачем даних: що саме постачається, у якому вигляді, з якими гарантіями.

#### 5.2 Зміст контракту

```yaml
dataset: gold.fact_trip
version: 2.1.0
owner: data-platform-team
description: Одна поїздка = один рядок

schema:
  - name: trip_id
    type: bigint
    required: true
    unique: true
  - name: pickup_ts
    type: timestamp
    required: true
    description: Час початку поїздки, UTC
  - name: fare_amount
    type: decimal(10,2)
    required: true
    unit: USD
    constraints: { min: 0, max: 10000 }
  - name: payment
    type: string
    enum: [cash, card, wallet]

guarantees:
  freshness:      { max_delay: 2h }
  completeness:   { min_ratio: 0.99 }
  uniqueness:     { key: [trip_id] }
  availability:   { sla: 99.5% }

change_policy:
  additive_changes:   notify              # додати колонку — просто повідомити
  breaking_changes:   30_days_notice      # видалити/перейменувати — попередити заздалегідь
  deprecation_period: 90_days
```

Три частини, які роблять контракт корисним:

1. **Схема** — не лише типи, а й одиниці виміру, часові зони, семантика полів.
2. **Гарантії** — свіжість, повнота, унікальність, доступність, виражені числами.
3. **Політика змін** — що вважається сумісною зміною, а що — ламкою, і скільки часу мають споживачі на адаптацію.

#### 5.3 Контракт як виконуваний артефакт

Контракт, який лежить у Confluence, — документація. Контракт, з якого генеруються перевірки, — механізм.

```
data_contract.yaml
   ├─► генерація схеми читання (StructType / DDL)
   ├─► генерація перевірок якості (GX suite / тести dbt)
   ├─► перевірка сумісності змін у CI (порівняння з попередньою версією)
   └─► документація в каталозі даних
```

Ключова інтеграція — **перевірка в CI**: pull request, який змінює модель так, що порушується контракт, не проходить збірку. Це переносить виявлення проблеми з продакшену на етап код-рев'ю.

### 6. Lineage: походження даних

#### 6.1 Навіщо

**Data lineage** — граф походження: які джерела, через які трансформації, у які цільові об'єкти перетворюються.

![Граф походження даних](https://raw.githubusercontent.com/datahub-project/static-assets/main/imgs/lineage/lineage-view-v3.png)

*Граф lineage у каталозі даних: видно ланцюг від джерел через задачі обробки до кінцевих вітрин і дашбордів. Джерело: [DataHub Docs](https://datahubproject.io/docs/features/feature-guides/lineage)*

Три задачі, які без lineage розв'язуються вручну й довго:

- **Аналіз впливу (impact analysis).** «Ми змінюємо схему цієї таблиці — що зламається?» Без графа відповідь шукається пошуком по репозиторіях.
- **Аналіз першопричини (root cause).** «У дашборді неправильна цифра — де саме вона зіпсувалася?» Граф дозволяє йти вгору по ланцюгу.
- **Комплаєнс.** «Де в системі присутні персональні дані цього користувача?» Без lineage відповісти на запит про видалення даних неможливо гарантовано.

#### 6.2 Рівні деталізації

| Рівень | Що відстежується | Складність |
|---|---|---|
| **Таблиця → таблиця** | Які таблиці читає й пише задача | Низька |
| **Колонка → колонка** | Яка вихідна колонка з яких вхідних обчислена | Висока |
| **Рядок / значення** | Походження конкретного запису | Дуже висока, рідко реалізується |

![Lineage на рівні колонок](https://raw.githubusercontent.com/datahub-project/static-assets/main/imgs/lineage/column-level-lineage-v3.png)

*Lineage на рівні колонок: показує, з яких саме полів джерела обчислено кожне поле результату. Джерело: [DataHub Docs](https://datahubproject.io/docs/features/feature-guides/lineage)*

#### 6.3 Способи отримання

- **Декларативний.** Залежності оголошені в коді — наприклад, через `ref()` у dbt. Граф будується автоматично й завжди актуальний. Найнадійніший спосіб.
- **Розбір запитів.** Парсер SQL (SQLGlot, sqllineage) аналізує запити й витягує таблиці й колонки. Працює для наявного коду без переписування.
- **Інструментація рантайму.** Движок сам повідомляє про прочитані й записані датасети. Стандарт для цього — **OpenLineage**: специфікація подій, яку підтримують Spark, Airflow, dbt, Flink. Події збирає сервер (Marquez, DataHub, OpenMetadata).
- **Ручний.** Записаний людиною. Швидко застаріває.

### 7. Персональні дані та безпека

#### 7.1 Класифікація

**PII (Personally Identifiable Information)** — дані, що ідентифікують конкретну людину. Регулюються GDPR у ЄС, CCPA у Каліфорнії та аналогічними нормами.

- **Прямі ідентифікатори:** ім'я, email, номер телефону, паспортні дані, номер картки.
- **Квазі-ідентифікатори:** окремо нікого не ідентифікують, але **в комбінації** — так. Класичний результат досліджень: поштовий індекс + дата народження + стать унікально ідентифікують більшість населення. Тому «ми видалили ім'я, отже дані анонімні» — хибне твердження.
- **Чутливі категорії:** здоров'я, релігія, політичні погляди, біометрія — окремий, суворіший режим.

#### 7.2 Технічні заходи

| Метод | Опис | Оборотність |
|---|---|---|
| **Маскування** | Часткове приховування: `j***@example.com` | Ні |
| **Хешування** | `sha256(email + salt)` — дозволяє з'єднувати за ключем без зберігання значення | Ні (за наявності солі) |
| **Токенізація** | Заміна на випадковий токен із таблицею відповідності в захищеному сховищі | Так, для власника таблиці |
| **Шифрування** | Симетричне/асиметричне, з керуванням ключами | Так, за наявності ключа |
| **Узагальнення** | Дата народження → рік; точна адреса → місто | Ні |
| **k-анонімність** | Гарантія, що кожна комбінація квазі-ідентифікаторів зустрічається щонайменше в k записів | Ні |

Організаційні заходи не менш важливі: **мінімізація** (не збирати те, що не потрібно), **обмеження терміну зберігання** (автоматичне видалення за політикою), **розмежування доступу** (рольова модель, маскування на рівні представлень).

#### 7.3 Право на видалення

GDPR дає право вимагати видалення персональних даних. У аналітичній платформі це нетривіально: дані розмножені по шарах, копіях, бекапах і snapshot-ах table format-у.

Практичні наслідки для архітектури:
- Персональні дані варто **ізолювати** в мінімальній кількості таблиць, а решту конвеєра будувати на псевдонімізованих ключах.
- Політика утримання snapshot-ів має враховувати вимогу видалення: якщо time travel зберігає 90 днів історії, видалені дані фізично існують ще 90 днів.
- Потрібен lineage, щоб знати повний перелік місць.

### 8. Data governance

#### 8.1 Що це і чим відрізняється від data management

**Data governance** — система прийняття рішень щодо даних: хто має право визначати правила, хто відповідає за їх виконання, за якими процесами вирішуються суперечки й зміни. Це не інструмент і не окрема команда, а набір **політик, ролей і процесів**, що роблять роботу з даними передбачуваною й підзвітною.

DAMA формулює це так: governance — це *здійснення повноважень і спільного контролю (планування, моніторинг, забезпечення виконання) над управлінням даними як активами*.

| | Data **management** | Data **governance** |
|---|---|---|
| Питання | Як зробити | Хто вирішує, за якими правилами, хто відповідає |
| Приклад | Побудувати конвеєр Bronze→Silver, почистити дублікати | Визначити, що таке «чисто», хто власник Silver, як узгоджується зміна схеми |
| Природа | Виконавча | Наглядова, координаційна |

Симптоми відсутності governance: та сама метрика по-різному рахується в трьох звітах; ніхто не знає, чи можна видаляти таблицю; на запит регулятора «де персональні дані цієї людини» немає гарантованої відповіді; кожна команда веде власний глосарій термінів.

#### 8.2 Компоненти governance-програми

| Компонент | Зміст |
|---|---|
| **Політики (policies)** | Високорівневі правила: «персональні дані шифруються в спокої», «кожен продакшн-датасет має власника», «retention за замовчуванням — 400 днів» |
| **Стандарти (standards)** | Конкретизація політик: конвенція іменування таблиць, обов'язкові теги класифікації, дозволені типи для часових полів, формат data contract |
| **Процеси (processes)** | Як вноситься зміна схеми, як надається доступ, як реєструється новий датасет, як ескалюється й закривається DQ-інцидент |
| **Ролі та форуми** | Хто які рішення ухвалює (розділ 8.3) |
| **Бізнес-глосарій (business glossary)** | Узгоджені визначення бізнес-термінів: «активний клієнт», «виручка», «поїздка» — одне визначення на всю організацію, прив'язане до конкретних колонок |
| **Метрики governance** | Частка датасетів із власником, із контрактом, покритих DQ-перевірками; медіанний час закриття DQ-інциденту |
| **Інструментальна опора** | Каталог даних, lineage, DQ-платформа, IAM — те, чим governance-рішення втілюються технічно |

#### 8.3 Ролі та форуми

| Роль / форум | Рівень | Відповідальність |
|---|---|---|
| **Chief Data Officer (CDO)** | організація | Власник governance-програми, бюджет, стратегія, звітність перед топменеджментом |
| **Data Governance Council / Board** | організація | Міжфункційний форум: ухвалює політики, розв'язує міждоменні суперечки, затверджує зміни стандартів |
| **Data Owner** | домен | Бізнес-**підзвітний** (accountable) за домен: визначає правила, погоджує доступ, приймає рішення про прийнятну якість і про breaking changes |
| **Data Steward** | домен | Операційно **відповідальний** (responsible): підтримує метадані й глосарій, стежить за метриками якості, веде розслідування інцидентів |
| **Data Custodian / Producer** | технічний | Команда платформи/інженерії: експлуатує сховище й конвеєри, реалізує контроль доступу й шифрування, дотримується контракту |
| **Data Consumer** | домен | Формулює вимоги до контракту, повідомляє про проблеми |

Розмежування Owner/Steward зручно класти на RACI: **Owner — accountable** (одна людина, ухвалює рішення), **Steward — responsible** (виконує щоденну роботу). Найпоширеніша організаційна проблема якості — **orphan-таблиця**: нею користуються п'ять команд, власника немає, при інциденті нема кому виправляти.

#### 8.4 Операційні моделі

| Модель | Як влаштовано | Компроміс |
|---|---|---|
| **Централізована** | Одна governance-команда на всю організацію задає й виконує правила | Узгодженість висока, швидкість низька, команда стає вузьким місцем |
| **Децентралізована** | Кожен домен визначає власні правила | Швидко й контекстно, але стандарти й визначення розходяться між доменами |
| **Федеративна** | Центр задає глобальні політики й спільну платформу; домени володіють своїми даними й виконують правила локально | Баланс; стандарт для великих організацій. Це ж — управлінська основа **data mesh** |

#### 8.5 DAMA-DMBOK

**DAMA-DMBOK** (*Data Management Body of Knowledge*, DAMA International) — довідковий звід практик управління даними, галузевий орієнтир для побудови governance-програми й для сертифікації (CDMP).

Друге видання (DMBOK2) організує дисципліну навколо **колеса DAMA (DAMA Wheel)**: одинадцять областей знань, у **центрі — Data Governance**, бо саме вона координує решту.

| Область (DAMA Wheel) | Про що |
|---|---|
| **Data Governance** *(центр)* | Політики, ролі, процеси, нагляд — координує всі інші області |
| **Data Architecture** | Цільова модель даних організації, стандарти інтеграції |
| **Data Modeling & Design** | Проєктування схем, нормалізація, dimensional modeling |
| **Data Storage & Operations** | Бази, фізичне зберігання, бекапи, продуктивність |
| **Data Security** | Класифікація, контроль доступу, шифрування, приватність, аудит |
| **Data Integration & Interoperability** | ETL/ELT, реплікація, стрімінг, обмін через API |
| **Document & Content Management** | Неструктуровані дані, документи, records management |
| **Reference & Master Data** | Довідники, master data management, «золотий запис» сутності |
| **Data Warehousing & BI** | Сховища, вітрини, звітність, аналітичне споживання |
| **Metadata** | Технічні, бізнесові й операційні метадані; каталог; lineage |
| **Data Quality** *(тема цього заняття)* | Виміри, метрики, профілювання, покращення якості |

DMBOK також описує наскрізні контексти навколо колеса: **люди й ролі**, **процеси**, **організаційна культура**, і **технології** — governance є обгорткою над усіма чотирма.

Практичні тези DMBOK, що стосуються цього заняття:
- Якість даних — це **програма, а не проєкт**: разова чистка деградує без постійного нагляду; governance — те, що підтримує її живою.
- Governance — **обов'язок кожного, але з явною підзвітністю**: без призначеного Owner/Steward «спільна відповідальність» перетворюється на «нічия».
- Контракт на дані (розділ 5), lineage (розділ 6) і робота з PII (розділ 7) — це governance-артефакти й governance-можливості; DQ-інструменти з розділів 1–4 — його **виконавчий механізм**.

#### 8.6 Каталог даних

**Data catalog** — реєстр датасетів із метаданими: опис, схема, власник, теги класифікації, метрики якості, lineage, статистика використання, посилання на глосарій. Приклади: DataHub, OpenMetadata, Amundsen, Unity Catalog, AWS Glue Data Catalog у зв'язці з Lake Formation.

Каталог — головний інструмент governance у щоденній роботі: розв'язує **discovery** («чи є вже таблиця з такими даними?») і **довіру** («чи можна цим користуватися, наскільки свіже, хто відповідає?»).

#### 8.7 Спостережуваність даних

**Data observability** — розширення ідеї моніторингу на дані. П'ять «стовпів»:

1. **Freshness** — коли дані оновлювалися востаннє.
2. **Volume** — чи очікуваний обсяг рядків.
3. **Schema** — чи не змінилася структура несподівано.
4. **Distribution** — чи в межах норми розподіли значень.
5. **Lineage** — звідки прийшло й куди пішло.

Відмінність від правил у тому, що спостережуваність працює **без явно сформульованих очікувань**: система вивчає нормальну поведінку й сигналізує про відхилення. Це доповнення до контрактів і governance-процесів, а не заміна.

### 9. Ландшафт інструментів

| Категорія | Інструменти | Ніша |
|---|---|---|
| Валідація в коді | Pandera, Pydantic, Cerberus | Перевірка на межах функцій, юніт-тести |
| Платформи якості | Great Expectations, Soda, Deequ / PyDeequ | Suite-и, звітність, профілювання |
| Тести всередині трансформацій | тести dbt, dbt-expectations, SQLMesh audits | Перевірки моделей сховища |
| Спостережуваність | Monte Carlo, Bigeye, Elementary, Datafold | Аномалії, freshness, регресії між версіями |
| Каталог і governance | DataHub, OpenMetadata, Amundsen, Unity Catalog | Discovery, lineage, класифікація, доступи |
| Стандарти lineage | OpenLineage, Marquez | Уніфікований збір подій походження |

Практична порада щодо вибору: почніть із того, що вже вбудоване у ваш стек (тести dbt, вбудовані обмеження table format-у), додайте окремий інструмент валідації лише тоді, коли вбудованого не вистачає, і не впроваджуйте платформу спостережуваності, поки немає базового набору правил — інакше вона генеруватиме шум.

## Ключові терміни

| Термін | Визначення |
|---|---|
| **Completeness** | Повнота: чи всі очікувані дані присутні |
| **Validity** | Валідність: відповідність формату й домену значень |
| **Accuracy** | Точність: відповідність значень реальності |
| **Consistency** | Узгодженість: відсутність суперечностей усередині та між таблицями |
| **Uniqueness** | Унікальність: відсутність небажаних дублікатів за бізнес-ключем |
| **Timeliness** | Своєчасність: свіжість даних відносно моменту події |
| **Uniformity / Conformity** | Однорідність одиниць виміру, форматів і кодувань |
| **DQ scorecard** | Набір метрик якості з порогами й історією значень |
| **Rule-based перевірка** | Явно сформульоване правило, що вважається правильним |
| **Data profiling** | Вимірювання статистичних характеристик даних |
| **Anomaly detection** | Виявлення відхилень від історичної норми без явних правил |
| **Pandera** | Бібліотека декларативної валідації датафреймів як типізованих схем |
| **`lazy=True`** | Режим збору всіх порушень за один прохід замість зупинки на першому |
| **Great Expectations** | Платформа валідації: expectations, suites, checkpoints, Data Docs |
| **Expectation** | Одне іменоване параметризоване твердження про дані |
| **Soda Core / SodaCL** | Чеки якості як YAML, що компілюються в SQL і виконуються у сховищі |
| **Expectation Suite** | Набір очікувань для датасету |
| **Checkpoint** | Запуск валідації з діями за результатом |
| **Data Docs** | Згенерований HTML-звіт GX |
| **`mostly`** | Частка рядків, які мають задовольнити очікування |
| **Detective control** | Перевірка після запису: виявляє, але не запобігає |
| **Preventive control (gate)** | Перевірка до публікації: некоректні дані не доходять до споживача |
| **Quarantine** | Відведення некоректних рядків в окрему таблицю з причиною відхилення |
| **Write-Audit-Publish (WAP)** | Патерн: записати непублічно → перевірити → атомарно опублікувати або скасувати |
| **Branching (Iceberg)** | Іменована гілка таблиці; основа атомарної публікації у WAP |
| **Data contract** | Формалізована версіонована угода про схему, гарантії й політику змін |
| **Breaking change** | Зміна, що ламає споживачів (видалення, перейменування, зміна типу/семантики) |
| **Data lineage** | Граф походження даних від джерел до вітрин |
| **Impact analysis** | Аналіз того, що зламається при зміні об'єкта |
| **Root cause analysis** | Пошук місця, де дані зіпсувалися, рухом угору по lineage |
| **Column-level lineage** | Походження на рівні окремих колонок |
| **OpenLineage** | Відкритий стандарт подій походження даних |
| **PII** | Дані, що ідентифікують конкретну людину |
| **Квазі-ідентифікатор** | Атрибут, що ідентифікує лише в комбінації з іншими |
| **Маскування / хешування / токенізація** | Методи приховування персональних даних із різною оборотністю |
| **k-анонімність** | Гарантія, що кожна комбінація квазі-ідентифікаторів зустрічається ≥ k разів |
| **Data governance** | Система політик, ролей і процесів для підзвітного прийняття рішень щодо даних |
| **Data governance vs data management** | Нагляд і повноваження (хто вирішує) проти виконання (як зробити) |
| **Business glossary** | Узгоджені визначення бізнес-термінів, прив'язані до конкретних колонок |
| **Data Owner / Data Steward / Data Custodian** | Підзвітний за домен (accountable) / операційний доглядач (responsible) / технічний виконавець |
| **Data Governance Council** | Міжфункційний форум, що ухвалює політики й розв'язує міждоменні суперечки |
| **Операційна модель governance** | Централізована / децентралізована / федеративна (основа data mesh) |
| **DAMA-DMBOK** | Звід практик управління даними; колесо DAMA — 11 областей знань із Data Governance у центрі |
| **DAMA Wheel** | Governance, Architecture, Modeling, Storage & Ops, Security, Integration, Content, Reference & Master Data, DW & BI, Metadata, Data Quality |
| **Data catalog** | Реєстр датасетів із метаданими, власниками, lineage і метриками якості |
| **Data observability** | Моніторинг freshness, volume, schema, distribution, lineage |
