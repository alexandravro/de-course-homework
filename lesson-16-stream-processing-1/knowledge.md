# Заняття 16. Потокова обробка. Частина 1: брокери подій та Apache Kafka

## Про що це заняття

Пакетна обробка виходить із припущення, що дані є повністю й одразу: файл лежить, таблиця заповнена, ми її читаємо. Потокова обробка виходить із протилежного: дані **надходять безперервно**, повного набору не існує в принципі, і система має видавати результат до того, як «усі дані прийдуть» — бо цей момент не настане ніколи.

Перехід між цими двома світами починається не з обчислень, а з **транспорту**. Перш ніж обробляти потік, його треба кудись прийняти, надійно зберегти й дати кільком незалежним споживачам читати його у власному темпі. Цю задачу розв'язують брокери подій, і галузевим стандартом тут є Apache Kafka.

Це заняття повністю присвячене транспортному рівню: чому лог-орієнтована модель відрізняється від класичної черги, як влаштований кластер Kafka, що таке партиція й offset, як працюють групи споживачів, як забезпечується надійність, як управляти схемами повідомлень і як витягнути потік змін із реляційної бази через CDC.

Після заняття ви зможете: пояснити, чим event streaming відрізняється від message queue; описати архітектуру кластера Kafka та роль KRaft; обґрунтувати вибір ключа й кількості партицій; налаштувати гарантії доставки під конкретну вимогу; пояснити, навіщо потрібен Schema Registry і які бувають режими сумісності схем; описати механізм CDC і чим він кращий за опитування таблиці.

- Базові поняття мережевої взаємодії та контейнеризації.

## Основний матеріал

### 1. Коли потрібна потокова обробка

#### 1.1 Чотири V і чому важлива саме velocity

Класична характеристика великих даних — Volume, Velocity, Variety, Veracity. Пакетні системи добре справляються з обсягом і різноманіттям. Потокова обробка з'являється тоді, коли визначальним стає **velocity** — швидкість, з якою дані надходять і **з якою вони втрачають цінність**.

Ключове поняття тут — **цінність, що згасає з часом**. Виявлення шахрайської транзакції за 200 мілісекунд дозволяє її заблокувати; те саме виявлення наступного дня — це вже звіт про збиток. Рекомендація товару під час сесії користувача працює; та сама рекомендація завтра — марна.

#### 1.2 Коли пакетної обробки достатньо

Потокова обробка складніша в розробці й експлуатації: розподілений стан, обробка пізніх подій, складніша семантика гарантій, важче тестування й налагодження. Її варто впроваджувати не «бо сучасно», а коли є конкретна вимога:

| Вимога | Обробка |
|---|---|
| Звіт за минулий день/місяць | Пакетна |
| Наповнення аналітичного сховища раз на годину | Пакетна або мікробатч |
| Виявлення шахрайства, антифрод | Потокова |
| Моніторинг і сповіщення в реальному часі | Потокова |
| Персоналізація під час сесії | Потокова |
| Синхронізація між системами (CDC) | Потокова |
| Складне перепрораховування історії | Пакетна |

### 2. Черга повідомлень проти лога подій

#### 2.1 Класична черга

У традиційній черзі (RabbitMQ, ActiveMQ, Amazon SQS) повідомлення — це **завдання, яке треба виконати**. Модель роботи:

```
Producer → [ QUEUE ] → Consumer
                       (прочитав → підтвердив → повідомлення ВИДАЛЕНО)
```

Властивості:
- Повідомлення **зникає** після підтвердження обробки.
- Кожне повідомлення обробляється **одним** споживачем із групи (конкурентні споживачі розподіляють навантаження).
- Брокер відстежує стан кожного повідомлення й керує повторними спробами.
- Порядок гарантується слабко або ціною втрати паралелізму.
- Історії немає: обробили — забули.

Це правильна модель для розподілу задач: розіслати листи, згенерувати документи, обробити платежі.

#### 2.2 Лог подій

Kafka побудована навколо іншої абстракції. Повідомлення — це **факт, що стався**, а сховище — **впорядкований журнал, доступний лише для дописування**.

```
Producer → [ append-only LOG ]
              0 1 2 3 4 5 6 7 8 ...
                    ↑         ↑
              Consumer A   Consumer B
              (offset 3)   (offset 8)

Дані НЕ видаляються після читання.
Кожен споживач має власну позицію й читає у своєму темпі.
```

Відмінності, з яких випливає все інше:

| | Черга | Лог подій (Kafka) |
|---|---|---|
| Що таке повідомлення | Завдання | Факт |
| Після читання | Видаляється | Залишається |
| Позицію відстежує | Брокер (per-message) | Споживач (один offset) |
| Скільки споживачів | Один із групи отримує | Скільки завгодно незалежних груп, кожна читає все |
| Повторне читання | Неможливе | Тривіальне — перемотати offset |
| Порядок | Слабкі гарантії | Суворий у межах партиції |
| Зберігання | Тимчасове | За політикою: години, роки або назавжди |

Наслідок, який змінює архітектуру: **дані в Kafka не належать конкретному споживачу**. Одну й ту саму подію незалежно читають сервіс аналітики, сервіс сповіщень, конвеєр завантаження у сховище й система антифроду — і жоден не заважає іншим. Додати нового споживача можна пізніше, і він прочитає всю історію з нуля.

#### 2.3 RabbitMQ проти Kafka: коли що обирати

RabbitMQ і Kafka часто порівнюють як взаємозамінні «брокери повідомлень», хоча це системи різного призначення — різниця випливає напряму з моделей у 2.1–2.2: RabbitMQ реалізує **чергу завдань** (протокол AMQP), Kafka — **лог подій**.

| | RabbitMQ | Kafka |
|---|---|---|
| Модель | Task queue: повідомлення розподіляються між споживачами й зникають | Append-only log: подія зберігається, споживачі незалежно рухаються по ньому |
| Маршрутизація | Гнучка, на боці брокера: **exchange** (`direct`, `topic`, `fanout`, `headers`) + **binding** визначають, у яку чергу піде повідомлення | Проста, на боці продюсера: топік і партиція за ключем; складну маршрутизацію брокер не робить |
| Зберігання після читання | Видаляється після `ack` (винятки — TTL, dead-letter exchange) | Зберігається за retention policy незалежно від того, чи хтось уже прочитав |
| Повторне читання | Неможливе без повторної публікації | Тривіальне — перемотати offset |
| Кілька незалежних споживачів одного потоку | Потрібно явно: `fanout`-exchange розсилає копію в окрему чергу для кожного споживача | З коробки: кожна consumer group читає весь топік незалежно від інших груп |
| Пропускна здатність | Тисячі–десятки тисяч msg/s на чергу; оптимізовано під низьку затримку доставки | Мільйони msg/s; оптимізовано під throughput за рахунок послідовного I/O та батчингу |
| Порядок | Строгий FIFO в межах черги за замовчуванням, ламається при кількох конкурентних consumers | Строгий тільки в межах партиції |
| Пріоритети, delayed message, per-message TTL, dead-letter | Є нативно | Немає нативно — доводиться емулювати окремими топіками й логікою повторів |
| Типовий сценарій | Розподіл задач (worker queues, RPC), складна маршрутизація повідомлень між мікросервісами | Event streaming, event sourcing, CDC, аналітика в реальному часі, кілька незалежних читачів одного потоку |

**Як обирати.** Якщо повідомлення — це **завдання**, яке має виконатися рівно один (чи майже один) раз, і потрібна гнучка маршрутизація без додаткової інфраструктури (пріоритети, затримка, dead-letter) — RabbitMQ доречніший і простіший в експлуатації. Якщо повідомлення — це **факт**, який повинен пережити конкретного споживача, читатися кількома незалежними системами або відтворюватися заново (replay) — потрібна Kafka. Інколи використовують обидва разом: Kafka як магістраль подій між сервісами, RabbitMQ — там, де конкретному сервісу треба розподілити роботу між власними воркерами.

### 3. Архітектура Kafka

#### 3.1 Загальна схема

![Кластер Kafka](https://kafka.apache.org/images/kafka_diagram.png)

*Кластер Kafka: продюсери пишуть у топіки, розподілені по брокерах партиціями; консюмери об'єднані в групи й читають незалежно. Джерело: [Apache Kafka Documentation](https://kafka.apache.org/documentation/)*

Компоненти:

- **Broker** — сервер Kafka. Зберігає партиції, обслуговує запити на запис і читання. Кластер складається з кількох брокерів.
- **Topic** — іменована категорія подій. Логічна одиниця, аналог таблиці.
- **Partition** — фізична одиниця. Топік складається з однієї або кількох партицій; партиція — це і є впорядкований лог на диску.
- **Producer** — клієнт, що пише події.
- **Consumer** — клієнт, що читає.
- **Consumer Group** — набір консюмерів, що спільно читають топік.

#### 3.2 KRaft: керування метаданими

Історично Kafka залежала від зовнішнього кластера **ZooKeeper**, який зберігав метадані (перелік топіків, конфігурації, ACL, стан контролера) і забезпечував вибір лідера. Це означало **дві розподілені системи** в експлуатації: два кластери, два набори конфігурацій, два джерела відмов.

**KRaft (Kafka Raft)** — вбудований механізм консенсусу, що усунув цю залежність. Частина брокерів отримує роль **controller** і утворює кворум, який реплікує метадані за протоколом Raft. Самі метадані зберігаються як **внутрішній топік Kafka** — тобто система керує собою власними примітивами.

Переваги: одна система замість двох, значно швидший старт кластера й перевибір лідера, підтримка мільйонів партицій. ZooKeeper видалено з Kafka 4.0; KRaft — єдиний режим.

#### 3.3 Топіки, партиції та offset

![Анатомія логу топіка](https://kafka.apache.org/images/log_anatomy.png)

*Топік складається з партицій; кожна партиція — це впорядкований лог, доступний лише для дописування, у якому кожен запис має послідовний номер (offset). Джерело: [Apache Kafka Documentation](https://kafka.apache.org/documentation/)*

**Партиція — одиниця паралелізму й одиниця порядку.**

- Порядок гарантується **тільки в межах партиції**. Між партиціями порядку немає взагалі.
- Один offset — це позиція в **одній** партиції. Offset 42 у партиції 0 і offset 42 у партиції 1 — різні події.
- Кількість партицій визначає максимальний паралелізм читання: у групі не може бути більше активних консюмерів, ніж партицій. Зайві простоюватимуть.

**Як обирається партиція при записі:**

| Ситуація | Правило |
|---|---|
| Ключ заданий | `partition = hash(key) % num_partitions` — усі події з однаковим ключем ідуть в одну партицію |
| Ключ не заданий | Sticky-розподіл: продюсер пише пачку в одну партицію, потім перемикається |
| Партиція вказана явно | Використовується вказана |

**Вибір ключа — головне проєктне рішення.** Ключ визначає, які події гарантовано впорядковані між собою. Якщо потрібен порядок подій для одного замовлення — ключ `order_id`. Якщо потрібен порядок операцій одного рахунку — ключ `account_id`.

Ціна помилки — перекіс: якщо 40 % подій мають один ключ, відповідна партиція стане вузьким місцем, і додавання брокерів не допоможе.

**Кількість партицій.** Збільшити можна будь-коли, **зменшити — ні**. Збільшення ламає прив'язку «ключ → партиція» для нових повідомлень, тому порядок для конкретного ключа порушується на межі зміни. Планують із запасом, але не надмірним: кожна партиція — це файлові дескриптори, пам'ять і час на перевибір лідера.

#### 3.4 Читання й offset-и

![Позиції споживачів у логу](https://kafka.apache.org/images/log_consumer.png)

*Кожна група споживачів має власну позицію в кожній партиції; читання одної групи не впливає на іншу. Джерело: [Apache Kafka Documentation](https://kafka.apache.org/documentation/)*

Позиції зберігаються у внутрішньому топіку `__consumer_offsets` — тобто Kafka знову використовує власний примітив.

Ключове поняття — **коміт offset-у**: явна фіксація того, що група обробила події до певної позиції.

```python
consumer = KafkaConsumer(
    "trips",
    bootstrap_servers="localhost:9092",
    group_id="analytics",
    auto_offset_reset="earliest",   # earliest | latest — з чого почати, якщо offset-у немає
    enable_auto_commit=False,       # комітити вручну після обробки
)

for msg in consumer:
    process(msg.value)
    consumer.commit()
```

**`auto_offset_reset`** застосовується лише коли збереженого offset-у немає (нова група або старий offset уже видалено за політикою утримання): `earliest` — читати з початку топіка, `latest` — тільки нові події.

**Автокоміт (`enable_auto_commit=True`) небезпечний:** він фіксує позицію за таймером, незалежно від того, чи справді оброблено події. Якщо консюмер упаде між автокомітом і завершенням обробки, події будуть втрачені (їх ніхто вже не прочитає). Ручний коміт **після** успішної обробки — правильний варіант за замовчуванням.

#### 3.5 Групи споживачів

![Групи споживачів](https://kafka.apache.org/images/consumer-groups.png)

*Партиції розподіляються між учасниками групи; кожна партиція в кожен момент читається рівно одним консюмером групи. Різні групи читають незалежно. Джерело: [Apache Kafka Documentation](https://kafka.apache.org/documentation/)*

Правила:
- **Одна партиція → рівно один консюмер у межах групи.** Це гарантує, що подія не буде оброблена двічі паралельно всередині групи.
- **Один консюмер може читати кілька партицій.**
- **Консюмерів більше, ніж партицій** — надлишкові простоюють.
- **Різні групи повністю незалежні** — кожна отримує всі події.

**Rebalance** — перерозподіл партицій між учасниками. Спрацьовує при приєднанні або виході консюмера, при його «зависанні» (не встиг надіслати heartbeat або перевищив `max.poll.interval.ms`) і при зміні кількості партицій.

Класична пастка: обробка одного повідомлення триває довше за `max.poll.interval.ms` (за замовчуванням 5 хвилин). Брокер вважає консюмера мертвим, запускає rebalance, консюмер тим часом завершує обробку й намагається закомітити offset — і отримує помилку. Утворюється цикл. Лікується збільшенням таймауту, зменшенням `max.poll.records` або винесенням важкої обробки в окремий пул.

Сучасні стратегії призначення (`CooperativeStickyAssignor`) роблять rebalance інкрементальним: перерозподіляються тільки ті партиції, які дійсно змінюють власника, замість зупинки всієї групи.

#### 3.6 Реплікація та надійність

Кожна партиція має **replication factor** — кількість копій на різних брокерах. Одна репліка є **лідером** (обслуговує всі читання й записи), решта — **послідовниками** (тягнуть дані з лідера).

**ISR (In-Sync Replicas)** — набір реплік, що не відстають від лідера більше за поріг. Лідер може бути обраний тільки з ISR — інакше буде втрачено підтверджені записи.

Продакшн-конфігурація надійності:

```properties
# Тема
replication.factor=3
min.insync.replicas=2          # запис підтверджується лише за наявності 2 синхронних реплік

# Продюсер
acks=all                       # чекати підтвердження від усіх ISR
enable.idempotence=true        # захист від дублікатів при повторній спробі
retries=Integer.MAX_VALUE
max.in.flight.requests.per.connection=5
```

Комбінація `replication.factor=3` + `min.insync.replicas=2` + `acks=all` дає стійкість до відмови **одного** брокера без втрати даних і без зупинки записів. Якщо брокерів вибуває два, записи почнуть відхилятися — це свідомий вибір консистентності над доступністю.

**`unclean.leader.election.enable=false`** (за замовчуванням) забороняє обирати лідером репліку поза ISR. Увімкнення цієї опції означає доступність ціною можливої мовчазної втрати даних.

#### 3.7 Зберігання та політики утримання

Kafka зберігає дані як **сегменти** — файли фіксованого розміру з індексами. Читання послідовне, що дозволяє використовувати `sendfile` і page cache операційної системи; саме звідси висока пропускна здатність.

Дві політики очищення:

**`delete` (за замовчуванням)** — сегменти видаляються за віком або сумарним розміром:
```properties
retention.ms=604800000        # 7 днів
retention.bytes=-1            # без обмеження за розміром
```

**`compact`** — для кожного ключа зберігається **останнє** значення; старіші записи з тим самим ключем видаляються. Топік перетворюється на «знімок поточного стану».
```properties
cleanup.policy=compact
```
Це основа таких патернів, як зберігання довідників у Kafka, відновлення стану сервісу з топіка й фінальний стан рядка в CDC. Значення `null` для ключа в compacted-топіку означає **tombstone** — маркер видалення.

Політики комбінуються: `cleanup.policy=compact,delete`.

### 4. Продюсер: що відбувається при записі

#### 4.1 Життєвий цикл повідомлення

```
send() → серіалізація ключа й значення
       → визначення партиції (partitioner)
       → накопичення в буфері (RecordAccumulator)
       → формування батча
       → стиснення
       → мережевий запит до лідера партиції
       → очікування acks
       → callback
```

`send()` **асинхронний**: він додає повідомлення в буфер і повертає future. Реальна відправка відбувається окремим потоком, коли зібрано батч або минув час очікування.

#### 4.2 Ключові параметри

| Параметр | Роль |
|---|---|
| `acks` | `0` — не чекати; `1` — чекати лідера; `all` — чекати всі ISR |
| `enable.idempotence` | Дедублікація повторних спроб на боці брокера |
| `linger.ms` | Скільки чекати, накопичуючи батч (більше → кращий throughput, гірша latency) |
| `batch.size` | Максимальний розмір батча в байтах |
| `compression.type` | `none`, `gzip`, `snappy`, `lz4`, `zstd` — стиснення на боці продюсера |
| `max.in.flight.requests.per.connection` | Скільки непідтверджених запитів дозволено |
| `retries`, `delivery.timeout.ms` | Поведінка при збоях |

**Компроміс latency/throughput** керується парою `linger.ms` + `batch.size`. `linger.ms=0` дає мінімальну затримку й найгіршу пропускну здатність (кожне повідомлення — окремий запит). `linger.ms=20` збирає батчі й багаторазово збільшує throughput ціною 20 мс затримки.

**Стиснення застосовується до батча цілком**, тому воно ефективніше при більших батчах. `zstd` зазвичай дає найкраще співвідношення ступеня стиснення до навантаження на CPU.

### 5. Гарантії доставки

#### 5.1 Три рівні

| Гарантія | Означає | Як досягається | Ціна |
|---|---|---|---|
| **At most once** | Кожна подія доставлена нуль або один раз; можлива втрата | `acks=0` або коміт offset-у **до** обробки | Найшвидше, дані втрачаються |
| **At least once** | Кожна подія доставлена щонайменше раз; можливі дублікати | `acks=all` + коміт **після** обробки | Стандарт за замовчуванням |
| **Exactly once** | Кожна подія врахована рівно раз | Ідемпотентний продюсер + транзакції | Складніше, повільніше |

#### 5.2 Чому «exactly once» — не магія

Мережа ненадійна принципово: продюсер надіслав повідомлення, брокер його записав, але підтвердження загубилося. Продюсер не може відрізнити «не дійшло» від «дійшло, але ack втрачено», тому повторює — і виникає дублікат.

Kafka вирішує це двома механізмами:

**Ідемпотентний продюсер.** Кожен продюсер отримує `producer_id`, і кожне повідомлення в партиції — послідовний номер. Брокер відкидає повторення з номером, який уже бачив. Це усуває дублікати **на записі**, у межах сесії продюсера й однієї партиції.

**Транзакції.** Дозволяють атомарно записати повідомлення в кілька партицій **і** закомітити offset-и споживання в одній транзакції:

```
transaction.begin()
   read from topic A
   process
   write to topic B
   commit consumer offsets for A
transaction.commit()
```

Це дає exactly-once для патерну **consume-transform-produce** всередині Kafka. Споживач має бути налаштований на `isolation.level=read_committed`, щоб не бачити незавершених транзакцій.

**Важливе обмеження:** гарантія діє в межах Kafka. Якщо ваш споживач пише результат у зовнішню базу, exactly-once там не з'явиться сам собою — потрібна ідемпотентність на боці приймача (upsert за ключем, дедублікація за унікальним ідентифікатором події, транзакційне збереження offset-у разом із даними).

Практичний висновок: у більшості конвеєрів дешевше й надійніше побудувати **at-least-once + ідемпотентний приймач**, ніж намагатися отримати наскрізний exactly-once.

### 6. Схеми повідомлень і Schema Registry

#### 6.1 Проблема

Топік Kafka не має схеми: це байти з ключем. Якщо продюсер пише JSON, а споживач очікує певні поля, договір існує лише в головах розробників. Продюсер перейменував поле — споживачі зламалися в рантаймі, кожен по-своєму, у продакшені.

Друга проблема — обсяг: JSON повторює назви полів у кожному повідомленні. Для потоку в мільйони подій на секунду це помітні витрати мережі й диска.

#### 6.2 Avro

**Apache Avro** — бінарний формат серіалізації зі схемою. Схема описується у JSON, а дані кодуються компактно, **без назв полів** — читач бере їх зі схеми.

```json
{
  "type": "record",
  "name": "Order",
  "namespace": "com.example.commerce",
  "fields": [
    {"name": "order_id",    "type": "long"},
    {"name": "created_ts",  "type": {"type": "long", "logicalType": "timestamp-millis"}},
    {"name": "customer_id", "type": "int"},
    {"name": "amount",      "type": "double"},
    {"name": "payment",     "type": {"type": "enum", "name": "Payment",
                                     "symbols": ["CASH", "CARD", "WALLET"]}},
    {"name": "discount",    "type": ["null", "double"], "default": null}
  ]
}
```

Зверніть увагу на останнє поле: `["null", "double"]` — це union-тип, а `"default": null` робить поле необов'язковим і, як наслідок, сумісним при еволюції.

Альтернативи: **Protobuf** (компактний, поширений у gRPC) і **JSON Schema** (людиночитабельний, без виграшу в розмірі).

**Як саме кодуються дані.** Avro пише лише **значення**, у порядку полів схеми — без назв полів і без роздільників. Цілі числа (`int`, `long`) кодуються **varint** зі **zigzag**-перетворенням (від'ємні числа теж займають мало байтів); рядки — довжина-префікс plus UTF-8 байти; `union`-тип (наприклад `["null", "double"]`) кодується індексом варіанта (0 або 1), а потім самим значенням. Без схеми ці байти нечитабельні в принципі — читач мусить знати порядок і типи полів, щоб їх розібрати. Це і дає компактність, і робить схему **обов'язковою**, а не опціональною документацією.

**Два способи донести схему до читача:**

| | Object Container File (`.avro`) | Kafka wire format (зі Schema Registry) |
|---|---|---|
| Де лежить схема | У заголовку самого файлу (JSON) | У Schema Registry; в повідомленні — лише `schema_id` |
| Коли платите за схему | Один раз на файл | 4 байти на кожне повідомлення |
| Коли доречно | Файл «у спокої»: експорт, архів, обмін між системами без спільного реєстру | Потік дрібних повідомлень: платити повну схему на кожне — марнотратно |
| Хто читає без зовнішніх запитів | Будь-який Avro-читач — схема вже у файлі | Тільки якщо consumer має доступ до того самого Registry |

Обидва механізми несуть ту саму інформацію, просто по-різному амортизують її вартість. У Kafka-контексті це і є причина, чому Schema Registry взагалі існує: вкладати повну схему в кожне повідомлення в потоці мільйонів подій на секунду — це та сама вартість, помножена на кожне повідомлення; винести її в окремий сервіс і передавати тільки `schema_id` — набагато дешевше.

#### 6.3 Schema Registry

**Schema Registry** — окремий сервіс, що зберігає схеми й видає їм числові ідентифікатори.

```
Producer:  серіалізує → реєструє/знаходить схему → у повідомлення пишеться
           [magic byte][schema_id (4 байти)][дані Avro]

Consumer:  читає schema_id → запитує схему з Registry (з кешем) → десеріалізує
```

Схема **не передається з кожним повідомленням** — лише її 4-байтовий ідентифікатор. Це і дає компактність.

Схеми групуються в **subject-и**, зазвичай `<topic>-value` і `<topic>-key`, і мають версії.

#### 6.4 Режими сумісності

Registry перевіряє, чи можна зареєструвати нову версію схеми, за налаштованим режимом:

| Режим | Правило | Що дозволено |
|---|---|---|
| **BACKWARD** (за замовчуванням) | Новою схемою можна прочитати дані, записані старою | Видалити поле; додати **необов'язкове** поле |
| **FORWARD** | Старою схемою можна прочитати дані, записані новою | Додати поле; видалити **необов'язкове** поле |
| **FULL** | Обидва напрямки | Тільки додавання/видалення необов'язкових полів |
| **NONE** | Без перевірок | Будь-що (і будь-які поломки) |
| `*_TRANSITIVE` | Те саме, але проти **всіх** попередніх версій, а не лише останньої | — |

**Як обирати.** BACKWARD доречний, коли ви оновлюєте споживачів раніше за продюсерів (нові споживачі мають розуміти старі дані — це типово, бо в топіку лежить історія). FORWARD — коли продюсери оновлюються першими. FULL — найбезпечніший і найобмеженіший.

Практичне правило еволюції: **додавайте поля з `default` і ніколи не змінюйте семантику наявного поля**. Зміна одиниць виміру в полі `amount` із доларів на центи пройде будь-яку перевірку сумісності й зламає всіх споживачів мовчки.

### 7. Kafka Connect і Change Data Capture

#### 7.1 Kafka Connect

**Kafka Connect** — фреймворк для інтеграції Kafka із зовнішніми системами без написання коду. Конектор описується конфігурацією.

- **Source connector** — тягне дані із зовнішньої системи в Kafka.
- **Sink connector** — вивантажує з Kafka у зовнішню систему.

Connect працює як окремий кластер воркерів, забезпечує розподіл задач, відстеження позиції, повторні спроби й масштабування. Це знімає потребу писати й супроводжувати сотні однотипних інтеграційних сервісів.

#### 7.2 Чому опитування таблиці не працює

Найочевидніший спосіб дізнатися про зміни в базі — періодично виконувати запит:

```sql
SELECT * FROM orders WHERE updated_at > :last_seen;
```

Проблеми цього підходу:

| Проблема | Наслідок |
|---|---|
| **Видалення невидимі** | Рядок зник — запит його не поверне, і споживач ніколи не дізнається |
| **Проміжні стани губляться** | Рядок змінився тричі між опитуваннями — ви побачите тільки останній стан |
| **Навантаження на базу** | Регулярні сканування конкурують із робочим навантаженням |
| **Компроміс за затримкою** | Частіше опитування — більше навантаження; рідше — більша затримка |
| **Потрібна колонка `updated_at`** | Її може не бути, і вона може не оновлюватися при всіх змінах |
| **Гонки за часом** | Транзакція, що почалася до, а закомітилася після зрізу, буде пропущена |

#### 7.3 CDC із журналу транзакцій

**Change Data Capture (CDC)** розв'язує задачу принципово інакше: замість опитування таблиці читається **журнал транзакцій** бази — WAL у PostgreSQL, binlog у MySQL, redo log в Oracle.

Журнал уже містить усе, що потрібно: кожну операцію INSERT/UPDATE/DELETE, у порядку комітів, зі старим і новим станом рядка. База й так його пише для власного відновлення й реплікації — CDC просто підключається як ще один споживач реплікації.

Переваги: видно **всі** зміни включно з видаленнями, видно **кожну** проміжну версію, порядок гарантований порядком комітів, навантаження на базу мінімальне (послідовне читання логу), затримка — мілісекунди.

#### 7.4 Debezium

![Архітектура Debezium](https://debezium.io/documentation/reference/stable/_images/debezium-architecture.png)

*Debezium як source-конектор Kafka Connect: читає журнал транзакцій бази й публікує події змін у топіки Kafka, звідки їх споживають довільні системи. Джерело: [Debezium Documentation](https://debezium.io/documentation/reference/stable/architecture.html)*

**Debezium** — набір CDC-конекторів для PostgreSQL, MySQL, MongoDB, SQL Server, Oracle, Db2, Cassandra.

Конфігурація для PostgreSQL:

```json
{
  "name": "orders-cdc",
  "config": {
    "connector.class": "io.debezium.connector.postgresql.PostgresConnector",
    "database.hostname": "postgres",
    "database.dbname":   "shop",
    "plugin.name":       "pgoutput",
    "slot.name":         "debezium_slot",
    "publication.name":  "debezium_pub",
    "table.include.list":"public.orders,public.customers",
    "topic.prefix":      "shop"
  }
}
```

Структура події зміни:

```json
{
  "before": { "id": 42, "status": "pending", "amount": 100.00 },
  "after":  { "id": 42, "status": "paid",    "amount": 100.00 },
  "source": { "db": "shop", "table": "orders", "lsn": 24023192, "ts_ms": 1723459200000 },
  "op": "u",
  "ts_ms": 1723459200123
}
```

Поле `op`: `c` — create, `u` — update, `d` — delete, `r` — read (початковий знімок).

Наявність **`before` і `after`** — те, чого опитування не дає в принципі. Це дозволяє будувати SCD 2, обчислювати дельти й реагувати саме на перехід стану («замовлення перейшло з `pending` у `paid`»), а не на факт зміни рядка.

**Початковий знімок (snapshot).** При першому запуску конектор читає поточний вміст таблиць і публікує їх із `op: "r"`, а потім переходить до читання логу. Так споживач отримує повний стан, а не тільки зміни з моменту підключення.

**Експлуатаційні застереження для PostgreSQL.** Debezium використовує слот логічної реплікації. Якщо конектор зупинено, а слот залишився, PostgreSQL **не видалятиме WAL-сегменти**, чекаючи на споживача — диск заповниться й база зупиниться. Моніторинг відставання слота (`pg_replication_slots`) обов'язковий.

**Outbox pattern.** Пряме читання журналу таблиць застосунку жорстко прив'язує споживачів до її внутрішньої схеми. Альтернатива — сервіс у тій самій транзакції записує подію в спеціальну таблицю `outbox`, а Debezium читає лише її. Так публікується стабільний контракт події, а не деталі реалізації.

|---|---|---|
| Приклади | Kafka у Docker/Kubernetes, Strimzi | Confluent Cloud, Amazon MSK, Aiven, Redpanda Cloud |
| Хто оновлює й балансує | Ви | Провайдер |
| Контроль над конфігурацією | Повний | Обмежений |
| Вартість | Залізо + інженерний час | Плата за пропускну здатність і зберігання |
| Коли доречно | Локальна розробка, специфічні вимоги, on-premise | Продакшн без окремої команди платформи |

Окремо варто знати про **альтернативні реалізації протоколу Kafka**: Redpanda (C++, без JVM і без ZooKeeper), WarpStream (зберігання безпосередньо в object storage замість локальних дисків). Вони сумісні з клієнтами Kafka, але мають інший профіль вартості й експлуатації.

#### 8.3 Мінімальний локальний стек

Для розробки типовий набір — Kafka у режимі KRaft, Schema Registry, Kafka Connect із Debezium і база-джерело, підняті одним `docker compose`. Це дозволяє відтворити повний шлях «зміна в базі → подія в топіку → споживач» на одній машині.

## Ключові терміни

| Термін | Визначення |
|---|---|
| **Event streaming** | Модель, у якій повідомлення — факт, а сховище — впорядкований лог, доступний для дописування |
| **Message queue** | Модель, у якій повідомлення — завдання, що зникає після підтвердження обробки |
| **RabbitMQ** | Класичний AMQP-брокер черг: exchange + binding для маршрутизації, повідомлення видаляється після `ack` |
| **Broker** | Сервер Kafka, що зберігає партиції й обслуговує клієнтів |
| **Topic** | Іменована категорія подій |
| **Partition** | Фізичний лог; одиниця паралелізму та єдина область гарантії порядку |
| **Offset** | Порядковий номер запису в межах партиції |
| **Producer / Consumer** | Клієнт запису / читання |
| **Consumer group** | Набір консюмерів, між якими розподіляються партиції топіка |
| **Rebalance** | Перерозподіл партицій між учасниками групи |
| **`max.poll.interval.ms`** | Максимальний час між викликами poll; перевищення спричиняє rebalance |
| **`__consumer_offsets`** | Внутрішній топік, де зберігаються позиції груп |
| **`auto_offset_reset`** | Звідки читати, якщо збереженого offset-у немає: `earliest` / `latest` |
| **Коміт offset-у** | Фіксація того, що група обробила події до певної позиції |
| **KRaft** | Вбудований консенсус Kafka на базі Raft; замінив ZooKeeper |
| **Controller** | Брокери, що утворюють кворум керування метаданими |
| **Replication factor** | Кількість копій партиції на різних брокерах |
| **Leader / Follower** | Репліка, що обслуговує запити / репліка, що тягне дані з лідера |
| **ISR (In-Sync Replicas)** | Репліки, що не відстають від лідера понад поріг; лише з них обирається лідер |
| **`min.insync.replicas`** | Мінімум синхронних реплік для підтвердження запису |
| **`acks`** | Скільки підтверджень чекає продюсер: `0`, `1`, `all` |
| **Unclean leader election** | Вибір лідером репліки поза ISR; доступність ціною втрати даних |
| **Segment** | Файл, у який фізично записується частина логу партиції |
| **Retention policy** | `delete` за віком/розміром або `compact` за ключем |
| **Log compaction** | Збереження лише останнього значення для кожного ключа |
| **Tombstone** | Запис зі значенням `null` у compacted-топіку — маркер видалення ключа |
| **`linger.ms` / `batch.size`** | Параметри батчингу продюсера; компроміс latency проти throughput |
| **Ідемпотентний продюсер** | Дедублікація повторних спроб за `producer_id` і послідовним номером |
| **Транзакції Kafka** | Атомарний запис у кілька партицій разом із комітом offset-ів |
| **`read_committed`** | Рівень ізоляції споживача, за якого незавершені транзакції не видимі |
| **At most once / at least once / exactly once** | Три рівні гарантій доставки |
| **Avro** | Бінарний формат серіалізації зі схемою; дані кодуються без назв полів |
| **Schema Registry** | Сервіс зберігання схем; у повідомлення пишеться лише `schema_id` |
| **Subject** | Одиниця версіонування схем, зазвичай `<topic>-value` |
| **BACKWARD / FORWARD / FULL** | Режими перевірки сумісності схем при реєстрації нової версії |
| **Kafka Connect** | Фреймворк інтеграції: source- і sink-конектори за конфігурацією |
| **CDC (Change Data Capture)** | Захоплення змін із журналу транзакцій бази |
| **WAL / binlog** | Журнал транзакцій PostgreSQL / MySQL |
| **Debezium** | Набір CDC-конекторів для Kafka Connect |
| **`before` / `after` / `op`** | Поля події зміни: стан до, стан після, тип операції |
| **Initial snapshot** | Початкове вивантаження поточного стану таблиць перед читанням логу |
| **Replication slot** | Механізм PostgreSQL, що утримує WAL для споживача; вимагає моніторингу |
| **Outbox pattern** | Публікація подій через окрему таблицю замість прямого читання таблиць застосунку |
| **MirrorMaker 2** | Реплікація топіків між кластерами |
| **Kafka Streams / ksqlDB** | Бібліотека потокової обробки / SQL-інтерфейс до потоків |
