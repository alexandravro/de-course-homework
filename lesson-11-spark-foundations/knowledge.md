# Заняття 11. Apache Spark: архітектура та модель виконання

## Про що це заняття

Apache Spark — уніфікований движок для розподіленої обробки даних. Він займає в сучасній дата-інженерії те саме місце, що PostgreSQL в операційних системах обліку: це не єдиний варіант, але це варіант за замовчуванням, який треба знати обов'язково. На Spark побудовані Databricks, AWS Glue etc.

Це заняття — **повністю про архітектуру та внутрішній устрій**. Не про перелік методів DataFrame API, а про те, **що відбувається всередині**, коли ви пишете рядок коду й натискаєте Enter:

- З яких процесів складається Spark-застосунок і хто з них що робить.
- Чому нічого не виконується до моменту, коли ви попросите результат.
- Як логічний план перетворюється на фізичний і хто його оптимізує.
- Як job розпадається на stage-и, stage — на task-и, і чому саме shuffle є межею між ними.
- Як влаштована пам'ять executor-а і що відбувається, коли її не вистачає.
- Як прочитати Spark UI і побачити там усе вищеперелічене.

Розуміння цих механізмів — різниця між «мій job чомусь працює 4 години» і «мій job працює 4 години, бо ось цей shuffle перекидає 300 ГБ через мережу, і ось що з цим робити».

## Що треба знати заздалегідь

- Базові поняття розподілених обчислень: вузол, кластер, мережевий обмін, відмовостійкість.
- Колонкові формати зберігання (Parquet) і поняття predicate/projection pushdown.
- Python на рівні впевненого користувача; знайомство з SQL.

## Основний матеріал

### 1. Що таке Spark і яку проблему він вирішує

#### 1.1 Визначення й позиціонування

**Apache Spark** — це розподілений обчислювальний движок загального призначення з in-memory моделлю обробки. Три слова в цьому визначенні важливі:

- **Розподілений** — робота виконується на багатьох машинах паралельно, з автоматичним відновленням після відмов.
- **Загального призначення** — це не тільки SQL. Один движок покриває batch ETL, SQL-аналітику, потокову обробку, машинне навчання і графові алгоритми.
- **In-memory** — проміжні результати за можливості тримаються в оперативній пам'яті, а не скидаються на диск після кожного кроку.

Чим Spark **не є**: це не сховище даних (він нічого не зберігає — читає з S3, HDFS, Kafka, JDBC), не база даних (немає власного постійного стану, індексів, транзакцій), не планувальник (для розкладів потрібен Airflow чи аналог) і не менеджер ресурсів (для цього є YARN або Kubernetes).

#### 1.2 Історія в чотирьох датах

- **2009** — Матей Захарія починає роботу над Spark в AMPLab Каліфорнійського університету в Берклі. Мова реалізації — **Scala** (JVM).
- **2010** — відкритий вихідний код; 2012 — стаття «Resilient Distributed Datasets», що описує ключову абстракцію.
- **2013** — проєкт передано в Apache Software Foundation; засновано компанію Databricks.
- **2014** — Spark стає top-level проєктом Apache і встановлює рекорд Daytona GraySort: 100 ТБ відсортовано за 23 хвилини на 206 вузлах — утричі швидше за попередній рекорд MapReduce на вдесятеро меншій кількості машин.

Далі — Spark 1.3 (DataFrame API), 1.6 (Dataset API, Tungsten optimizator), 2.0 (Structured Streaming, whole-stage codegen), 3.0 (Adaptive Query Execution, dynamic partition pruning), 3.4+ (Spark Connect), 4.0 (подальший розвиток Connect).

**Наслідок реалізації на Scala/JVM, який відчувається щодня:** Spark — це JVM-система. PySpark не переписує Spark на Python; він керує JVM-процесом ззовні. Тому трасування помилок у PySpark майже завжди містить Java-стек.

#### 1.3 Обмеження MapReduce, від яких відштовхувався Spark

Класична MapReduce-модель зберігає результат **кожного** кроку в надійне сховище (HDFS), перш ніж почати наступний:

```
Крок 1:  read(disk) → map    → write(disk)
                 ↓ shuffle через мережу ↓
Крок 2:  read(disk) → reduce → write(disk)
Крок 3:  read(disk) → map    → write(disk)
   …
```

Це давало чудову відмовостійкість (упав вузол — перечитали проміжний результат із диска) ціною продуктивності. Конкретні болі:

- **Матеріалізація між кроками.** ETL із 10 операцій — це 10 читань і 10 записів усього набору даних.
- **Катастрофа на ітеративних алгоритмах.** Градієнтний спуск, PageRank, k-means роблять десятки й сотні проходів по **тому самому** датасету. Кожен прохід — повне читання з диска заново.
- **Дорогий старт.** Кожен крок — окремий job із власною ініціалізацією JVM-процесів.
- **Бідна модель програмування.** Усе треба виразити через пару map/reduce. Join двох таблиць — це кілька job-ів, склеєних вручну.

#### 1.4 Відповідь Spark: RDD і збереження проміжного стану в пам'яті

Ключова абстракція — **RDD (Resilient Distributed Dataset)**, розподілена незмінна колекція, яку можна **закешувати в пам'яті кластера** і перевикористати для наступних операцій.

```
MapReduce:  read(disk) → op → write(disk) → read(disk) → op → write(disk) → …
Spark:      read(disk) → op → [RAM] → op → [RAM] → op → [RAM] → … → write(disk)
```

Для ітеративних алгоритмів датасет читається з диска **один раз**, а всі 100 ітерацій працюють із пам'яті. Звідси й характерні цифри прискорення: **10–100× на ітеративних задачах** і скромніші **2–5× на однопрохідному ETL**, де диск усе одно доведеться читати й писати.

**Важливе застереження, щоб не було ілюзій.** «In-memory» — це стратегія, а не гарантія:

- Якщо дані не вміщаються в пам'ять, Spark **скидає їх на диск** (spill).
- **Shuffle завжди пише на локальний диск** — проміжні файли між stage-ами матеріалізуються.
- Читання джерела й фінальний запис — це завжди I/O.

Spark швидший не тому, що «магічно все в RAM», а тому що уникає **зайвої** матеріалізації там, де її можна уникнути, і додає повноцінний оптимізатор запитів.

### 2. Архітектура Spark-застосунку

Це найважливіший розділ заняття. Spark-застосунок — це набір процесів на різних машинах із чітко розділеними ролями.

![Архітектура кластера Spark](https://spark.apache.org/docs/latest/img/cluster-overview.png)

*Компоненти Spark-застосунку: SparkContext у driver-програмі домовляється з cluster manager про ресурси, отримує executor-и на worker-вузлах, розсилає їм код застосунку й потім — task-и. Джерело: [Spark Cluster Mode Overview](https://spark.apache.org/docs/latest/cluster-overview.html)*

│  │  ├─ TaskScheduler: розсилка task-ів на executor-и   │  │
│  │  ├─ BlockManager (master): облік кешу й shuffle     │  │

#### 2.2 Driver: координатор

**Driver** — процес, у якому виконується ваш `main()` і живе `SparkSession`. Це «мозок» застосунку. Він:

1. **Приймає ваш код** і будує з нього логічний план операцій.
2. **Оптимізує план** через Catalyst і перетворює на фізичний план виконання.
3. **Розбиває фізичний план на stage-и** (`DAGScheduler`), а кожен stage — на набір task-ів за кількістю партицій.
4. **Домовляється з cluster manager** про ресурси і отримує executor-и.
5. **Розсилає task-и** на executor-и (`TaskScheduler`), намагаючись врахувати локальність даних.
6. **Відстежує прогрес**, перезапускає task-и, що впали, обробляє відмови executor-ів.
7. **Збирає результати** дій на кшталт `collect()` або `count()`.
8. **Обслуговує Spark UI** на порту 4040.

Три властивості driver-а, які треба пам'ятати:

- **Driver — єдина точка відмови застосунку.** Executor може впасти — Spark перезапустить його task-и на іншому. Впав driver — весь застосунок мертвий, бо втрачено весь стан планування.
- **Driver може стати вузьким місцем.** Планування тисяч task-ів, збір метрик, широкомовна розсилка (broadcast) — усе це навантажує один процес. Дуже великі плани (тисячі партицій, глибокі DAG) сповільнюють саме driver.
- **`collect()` тягне дані в пам'ять driver-а.** Це найпоширеніша причина `OutOfMemoryError` у новачків: `df.collect()` на таблиці в 50 ГБ намагається зібрати 50 ГБ у один процес.

`SparkSession` — єдина точка входу до всіх API (SQL, DataFrame, streaming). Історично існували окремі `SparkContext`, `SQLContext`, `HiveContext`; з версії 2.0 вони об'єднані в `SparkSession`, а `SparkContext` доступний як `spark.sparkContext` для низькорівневих операцій із RDD.

#### 2.3 Executor: виконавець

**Executor** — JVM-процес на worker-вузлі, що живе від старту застосунку до його завершення. Кожен executor:

- Виконує призначені йому **task-и** у власному пулі потоків. Кількість одночасних task-ів дорівнює `spark.executor.cores` — «ядро» тут означає слот під потік, а не обов'язково фізичне ядро.
- Тримає **закешовані дані** (`cache()`/`persist()`) у своєму `BlockManager`.
- Зберігає **shuffle-файли**, які потім читають task-и наступного stage з інших executor-ів.
- Звітує driver-у про статус task-ів і метрики.

Executor-и **не спілкуються з driver-ом заради даних** — між собою вони обмінюються напряму (при shuffle і при читанні віддаленого кешу). Driver отримує лише керуючий трафік і фінальні результати.

**Ключові налаштування:**

| Параметр | Значення |
|---|---|
| `spark.executor.instances` | Скільки executor-ів запустити (без динамічної алокації) |
| `spark.executor.cores` | Скільки task-ів executor виконує одночасно |
| `spark.executor.memory` | Розмір JVM-heap executor-а |
| `spark.executor.memoryOverhead` | Позаheap-пам'ять: Python-процеси, native-бібліотеки, мережеві буфери |
| `spark.dynamicAllocation.enabled` | Автоматично додавати й прибирати executor-и за навантаженням |

**Компроміс «багато маленьких vs мало великих executor-ів».** Занадто маленькі (1–2 ядра) — багато процесів, дублювання broadcast-даних, погана утилізація. Занадто великі (32 ядра, 200 ГБ) — довгі паузи GC, груба гранулярність при відмові, обмеження HDFS-клієнта на паралельні потоки. Практичний орієнтир — **4–5 ядер і 16–32 ГБ на executor**.

#### 2.4 Cluster manager: розподільник ресурсів

Cluster manager відповідає на питання «на яких машинах і з якими квотами запустити executor-и». Spark працює з кількома:

| Режим | Опис |
|---|---|
| **local[N]** | Driver і executor у **одному** JVM-процесі; N потоків. `local[*]` — за кількістю ядер машини. Для розробки й тестів |
| **Standalone** | Вбудований менеджер Spark: Master + Worker-и. Просто розгортається, мінімум залежностей |
| **YARN** | Стандарт для Hadoop-кластерів (EMR, Cloudera). ResourceManager + NodeManager + ApplicationMaster |
| **Kubernetes** | Driver і executor-и — це pod-и. Домінуючий вибір у сучасних cloud-native стеках |
| **Mesos** | Історичний варіант, deprecated з Spark 3.2 |

Важливо: Spark **не залежить** від конкретного менеджера — це підключуваний компонент. Той самий код працює локально і на кластері з 500 вузлів; змінюється лише `--master`.

#### 2.5 Deploy mode: client vs cluster

Окреме питання — **де фізично запускається driver**.

- **Client mode.** Driver працює на машині, з якої ви запустили `spark-submit` (ваш ноутбук, edge-вузол, контейнер Airflow). Логи й Spark UI під рукою; інтерактивна робота (`spark-shell`, ноутбуки) можлива тільки так. Мінус: якщо ця машина вимкнеться або втратить мережу — застосунок помре. Плюс мережевий трафік між driver-ом і кластером ходить назовні.
- **Cluster mode.** Driver запускається **всередині кластера** як ще один контейнер/pod. Стійко до відключення клієнтської машини, менша мережева затримка до executor-ів. Так запускають продакшн-джоби. Логи треба збирати з кластера.

#### 2.6 Spark як MPP-система

За природою Spark — **MPP (Massively Parallel Processing)**: дані розбиваються на **партиції**, кожна обробляється незалежно, без координації між партиціями. Одна партиція → один task → один слот-ядро executor-а.

Координація потрібна лише на межах stage-ів — там, де відбувається shuffle. Усе між ними — чистий паралелізм без спільного стану.

Це та сама модель, що в MPP-сховищах (Teradata, Greenplum, Vertica), але реалізована як універсальний движок, а не як SQL-база: партиції не приварені до вузлів назавжди, а перерозподіляються між кроками.

### 3. RDD: фундаментальна абстракція

Навіть коли ви пишете виключно DataFrame-код, під ним усе одно виконуються RDD. Розуміння цієї абстракції пояснює відмовостійкість і модель виконання Spark.

#### 3.1 П'ять властивостей RDD

RDD — **незмінна розподілена колекція записів**, що описується п'ятьма характеристиками:

1. **Список партицій** — на скільки незалежних частин розбито дані.
2. **Функція обчислення партиції** — як отримати вміст конкретної партиції.
3. **Список залежностей від батьківських RDD** — lineage (родовід).
4. **(Опційно) Partitioner** — правило розподілу ключів по партиціях для pair-RDD (hash, range).
5. **(Опційно) Preferred locations** — де дані лежать фізично, для планування з урахуванням локальності.

**Незмінність** — не примха, а основа моделі. Оскільки RDD не можна змінити, будь-яка «трансформація» створює **новий** RDD, що посилається на попередній. Виникає граф походження.

#### 3.2 Lineage і відмовостійкість

Spark **не реплікує проміжні дані**. Замість цього він зберігає **lineage** — рецепт, як ці дані обчислити заново:

```
textFile ──map──► rdd1 ──filter──► rdd2 ──reduceByKey──► rdd3
```

Якщо executor із партицією №17 rdd2 впав, Spark не панікує: він знає, що партиція №17 rdd2 = filter(map(партиція №17 вихідного файлу)) — і просто перераховує саме її на іншому вузлі. Решта партицій не зачеплена.

Це принципово дешевше за реплікацію: замість того щоб зберігати три копії кожного проміжного результату, зберігається кілька кілобайтів опису.

**Обмеження підходу:** дуже довгий lineage робить відновлення дорогим (треба перерахувати весь ланцюг) і роздуває план. Тому існує **checkpointing** — примусова матеріалізація RDD у надійне сховище з обрізанням lineage. Це особливо важливо для ітеративних алгоритмів і streaming, де ланцюг росте нескінченно.

#### 3.3 Narrow і wide dependencies

Це поділ, з якого безпосередньо випливають stage-и.

**Narrow dependency (вузька залежність)** — кожна партиція батька використовується **щонайбільше однією** партицією нащадка.

```
батько:   [P0] [P1] [P2] [P3]
             │    │    │    │
нащадок:  [P0] [P1] [P2] [P3]
```

Приклади: `map`, `filter`, `flatMap`, `mapPartitions`, `union`, `coalesce`. Обчислюються **локально**, без мережевого обміну, і можуть бути злиті в один конвеєр: partition → filter → map → нова partition за один прохід у пам'яті.

**Wide dependency (широка залежність, shuffle dependency)** — партиція нащадка залежить від **багатьох** партицій батька.

```
батько:   [P0]  [P1]  [P2]  [P3]
            ╲ ╲  │ ╲  ╱ │  ╱ ╱
             ╲ ╲ │  ╳   │ ╱ ╱      ← дані летять через мережу
              ╲ ╲│ ╱ ╲  │╱ ╱
нащадок:      [P0]      [P1]
```

Приклади: `groupByKey`, `reduceByKey`, `join`, `distinct`, `repartition`, `sortBy`. Вимагають **shuffle** — перерозподілу даних по мережі.

Правило: **межа stage = wide dependency**. Усе, що можна зробити без перемішування даних, злипається в один stage.

#### 3.4 Persistence: кешування

Оскільки RDD за замовчуванням не матеріалізуються, кожен action перераховує весь ланцюг з нуля. Якщо той самий проміжний результат потрібен двічі — його рахують двічі.

`cache()` / `persist(level)` каже Spark зберегти результат після першого обчислення.

| Рівень | Де зберігається |
|---|---|
| `MEMORY_ONLY` | Тільки в пам'яті (за замовчуванням для RDD). Що не влізло — перераховується |
| `MEMORY_AND_DISK` | У пам'яті; що не влізло — на локальний диск. За замовчуванням для DataFrame |
| `MEMORY_ONLY_SER` / `MEMORY_AND_DISK_SER` | Серіалізовано — компактніше, але потрібен CPU на десеріалізацію |
| `DISK_ONLY` | Тільки диск |
| `*_2` | Той самий рівень із дворазовою реплікацією між вузлами |

Практика: кешуйте тільки те, що справді читається **більше одного разу**, і викликайте `unpersist()`, коли дані більше не потрібні — інакше кеш витісняє пам'ять, потрібну для самих обчислень.

### 4. Lazy evaluation: трансформації та дії

#### 4.1 Загальний принцип

**Lazy evaluation** (відкладене обчислення) — стратегія, за якої вираз не обчислюється в момент написання, а лише в момент, коли результат справді потрібен. Протилежність — eager evaluation.

Ідея не унікальна для Spark. Вона є ядром Haskell, зустрічається у вигляді генераторів у Python, у short-circuit-логіці (`False and expensive()` не викликає `expensive()`), у lazy-режимі Polars.

#### 4.2 Як це працює у Spark

У Spark лінивість — **архітектурне рішення, а не оптимізація**. Кожен виклик трансформації лише дописує вузол до логічного плану в пам'яті driver-а:

```python
df       = spark.read.parquet("s3://lake/trips/")   # трансформація
filtered = df.filter(df.fare_amount > 0)            # трансформація
grouped  = filtered.groupBy("zone_id").count()      # трансформація
# Досі не прочитано жодного байта. Є лише дерево операцій у driver-і.

grouped.show(10)      # ДІЯ → тільки тут запускається виконання
```

**Трансформації** повертають новий DataFrame/RDD і нічого не виконують:
`select`, `filter`, `withColumn`, `groupBy`, `join`, `union`, `orderBy`, `repartition`, `distinct`.

**Дії (actions)** запускають виконання і повертають результат у driver або пишуть у сховище:
`show`, `count`, `collect`, `take`, `first`, `foreach`, `write.save`, `toPandas`.

Просте евристичне правило: **повертає DataFrame → трансформація; повертає число, список, нічого або пише на диск → дія**.

#### 4.3 Що дає лінивість

1. **Глобальна оптимізація.** Оптимізатор бачить **увесь** ланцюг, а не окремі кроки, тому може переставляти операції: посунути `filter` до самого читання (predicate pushdown), викинути невикористані колонки (column pruning), об'єднати кілька `filter` в один.
2. **Конвеєризація.** Кілька вузьких трансформацій виконуються за один прохід по даних, без матеріалізації між ними.
3. **Уникнення зайвої роботи.** `df.filter(...).limit(5).show()` не читатиме весь датасет.

**Зворотний бік, який треба знати:** кожна дія запускає виконання **заново**. Код нижче читає джерело три рази:

```python
df = spark.read.parquet("...").filter(...).groupBy(...).agg(...)
df.count()          # прохід 1
df.show()           # прохід 2
df.write.parquet()  # прохід 3
```

Саме тут доречний `cache()`.

Ще один наслідок: **помилки з'являються не там, де ви їх написали**. Друкарська помилка в назві колонки в `filter` вилетить лише під час виклику `show()` — Catalyst аналізує план у момент дії.

### 5. Від коду до виконання: Catalyst і Tungsten

#### 5.1 Чотири фази Catalyst

**Catalyst** — оптимізатор запитів Spark SQL, побудований на деревах і правилах їх перетворення. Він проганяє ваш запит через чотири фази:

![Фази оптимізатора Catalyst](https://www.databricks.com/wp-content/uploads/2015/04/Screen-Shot-2015-04-12-at-8.11.11-AM.png)

*Конвеєр Catalyst: SQL-запит або DataFrame → unresolved logical plan → analysis (за каталогом) → logical optimization → physical plans → вибір за cost model → code generation → RDD. Джерело: [Databricks — Deep Dive into Spark SQL's Catalyst Optimizer](https://www.databricks.com/blog/2015/04/13/deep-dive-into-spark-sqls-catalyst-optimizer.html)*

**Фаза 1. Analysis.**
На вході — *unresolved logical plan*: дерево операцій, у якому імена колонок і таблиць — просто рядки. Catalyst звіряється з **каталогом** (метадані таблиць) і розв'язує посилання: чи існує колонка `zone_id`, якого вона типу, до якого відношення належить. На виході — *analyzed logical plan*. Саме тут виникають помилки `AnalysisException: cannot resolve column`.

**Фаза 2. Logical optimization.**
До дерева застосовуються правила перетворення, доки план не перестане змінюватися. Основні:

| Правило | Що робить |
|---|---|
| **Predicate pushdown** | Переміщує `filter` якомога ближче до джерела — аж до передачі предиката в Parquet-reader або в JDBC-запит |
| **Column (projection) pruning** | Викидає читання колонок, які ніде не використовуються |
| **Constant folding** | Обчислює константні вирази під час компіляції: `WHERE x > 2 + 3` → `WHERE x > 5` |
| **Boolean simplification** | Спрощує логічні вирази |
| **Filter/Project collapsing** | Зливає послідовні фільтри й проєкції |
| **Null propagation** | Спрощує вирази з відомо-null операндами |
| **Join reordering** | Змінює порядок join-ів за оцінками кардинальності (за наявності статистики) |

Predicate pushdown і column pruning — головні джерела прискорення на колонкових форматах: зазвичай вони скорочують обсяг прочитаних байтів на порядок.

**Фаза 3. Physical planning.**
Логічний план описує *що* робити, фізичний — *як*. Для кожної логічної операції існує кілька фізичних стратегій, і Catalyst генерує кілька планів-кандидатів, а потім обирає за **cost model**.

Найпоказовіший приклад — join:

| Стратегія | Коли обирається | Механіка |
|---|---|---|
| **Broadcast Hash Join** | Одна сторона менша за `spark.sql.autoBroadcastJoinThreshold` (10 МБ за замовчуванням) | Маленька таблиця розсилається на всі executor-и цілком; **shuffle не потрібен** — найшвидший варіант |
| **Shuffle Hash Join** | Обидві сторони великі, одна помітно менша | Обидві сторони шафляться за ключем; на кожній партиції будується хеш-таблиця |
| **Sort-Merge Join** | Обидві сторони великі (варіант за замовчуванням) | Обидві сторони шафляться і сортуються за ключем, потім злиття |
| **Broadcast Nested Loop Join** | Немає ключа з'єднання (нерівні умови) | Декартове порівняння — дуже дорого |

**Фаза 4. Code generation (Tungsten).**
Проєкт **Tungsten** займається ефективністю на рівні CPU і пам'яті:

- **Whole-stage code generation** — замість того щоб виконувати кожен оператор окремо через ланцюжок віртуальних викликів, Spark **генерує Java-код** для цілого stage і компілює його на льоту. Отримується щільний цикл без викликів-посередників — по суті, код, який написала б людина вручну.
- **Позаheapова пам'ять і бінарний формат рядків.** Дані зберігаються в компактному бінарному представленні (`UnsafeRow`) поза JVM-heap, тому GC їх не бачить і не сканує.
- **Cache-aware обчислення** — структури даних проєктуються з урахуванням розміру процесорного кеша.
- **Векторизоване читання Parquet/ORC** — колонки читаються пачками, а не рядок за рядком.

#### 5.2 Adaptive Query Execution (AQE)

Проблема класичного cost-based підходу: план обирається **до** виконання, на основі оцінок, які часто хибні (особливо після кількох join-ів і фільтрів).

**AQE** (Spark 3.0+, увімкнений за замовчуванням) переоптимізовує план **під час виконання**, використовуючи реальну статистику завершених stage-ів:

- **Динамічний вибір стратегії join.** Якщо після фільтрації одна сторона виявилася на 8 МБ замість очікуваних 2 ГБ — sort-merge join замінюється на broadcast join прямо на льоту.
- **Динамічне злиття shuffle-партицій.** Замість фіксованих 200 партицій, з яких 190 порожні, AQE склеює їх у розумну кількість за фактичним розміром.
- **Оптимізація перекошених join-ів (skew join).** Якщо одна партиція виявилася в 50 разів більшою за медіанну (класика: 40 % рядків мають `user_id = NULL`), AQE розбиває цю партицію на кілька і обробляє паралельно.

Це усуває значну частину ручного тюнінгу, який раніше був обов'язковим.

#### 5.3 Як подивитися план

```python
df.explain(True)          # усі чотири плани: parsed, analyzed, optimized, physical
df.explain("formatted")   # структурований вивід, зручний для читання
df.explain("cost")        # з оцінками статистики
```

Читати фізичний план треба **знизу вгору**. Головне, на що дивитися: наявність `Exchange` (це shuffle), тип join-у, `PushedFilters` у сканері джерела, `ColumnPruning`.

### 6. Job → Stage → Task: анатомія виконання

#### 6.1 Ієрархія

```
APPLICATION            один SparkSession від старту до spark.stop()
   └── JOB             один на кожну ДІЮ (show, count, write)
         └── STAGE     набір операцій без shuffle між ними
               └── TASK   одна операція над однією партицією
```

- **Job** створюється кожною дією. Три дії — три job-и, навіть якщо код той самий.
- **Stage** — максимальна група трансформацій, яку можна виконати конвеєром без перемішування даних. Межа stage-а — завжди shuffle (`Exchange` у плані).
- **Task** — найдрібніша одиниця роботи: «застосуй код цього stage до партиції №K». Кількість task-ів у stage дорівнює кількості партицій.

```
Stage 0:  scan Parquet → filter → project → map        (200 партицій → 200 task-ів)
             ↓↓↓ SHUFFLE: перерозподіл за zone_id ↓↓↓
Stage 1:  aggregate → sort                             (200 партицій → 200 task-ів)
             ↓↓↓ SHUFFLE: сортування ↓↓↓
Stage 2:  write                                        (N партицій → N task-ів)
```

Якщо в кластері 50 доступних слотів-ядер, а stage має 200 task-ів — вони виконаються чотирма «хвилями».

#### 6.2 Механіка shuffle

Shuffle — найдорожча операція в Spark, і варто розуміти, що саме в ній дорого.

**Map side (кінець попереднього stage):**
1. Кожен task обчислює для кожного запису номер цільової партиції (зазвичай `hash(key) % numPartitions`).
2. Записи сортуються/групуються за цільовою партицією.
3. Результат **пишеться на локальний диск** у shuffle-файл разом з індексом.

**Reduce side (початок наступного stage):**
4. Кожен task наступного stage **тягне по мережі** свої шматки з shuffle-файлів **усіх** map-task-ів.
5. Отримані дані зливаються, за потреби зі spill на диск.

Витрати: серіалізація, запис на диск, мережевий трафік «всі до всіх», десеріалізація, можливий spill. Тому головні правила оптимізації Spark формулюються навколо shuffle:

- **Зменшуйте кількість shuffle-ів.** Кожен `groupBy`, `join`, `distinct`, `repartition` — це shuffle.
- **Зменшуйте обсяг shuffle.** Фільтруйте й відкидайте колонки **до** shuffle, а не після.
- **Уникайте shuffle взагалі**, коли можна: broadcast join замість sort-merge join.
- **Обирайте агрегації з частковою редукцією.** `reduceByKey` агрегує локально на map-стороні перед пересиланням; `groupByKey` пересилає всі сирі записи. Для DataFrame API Catalyst робить це автоматично.

`spark.sql.shuffle.partitions` — кількість партицій після shuffle, за замовчуванням **200**. Це історична константа, яка майже ніколи не є правильною: для маленького датасету вона породжує 200 крихітних task-ів, для великого — 200 гігантських. AQE значною мірою знімає це питання, коригуючи число динамічно.

#### 6.3 Партиціонування і паралелізм

**Партиція** — незалежний шматок даних. Кількість партицій = максимальний паралелізм. Звідки вони беруться на старті:

- **Читання файлів:** приблизно за `spark.sql.files.maxPartitionBytes` (128 МБ за замовчуванням) з урахуванням структури файлів; один великий Parquet-файл може бути розбитий на кілька партицій, багато дрібних — злиті в одну.
- **Після shuffle:** `spark.sql.shuffle.partitions` (або рішення AQE).
- **Явно:** `repartition(n)` — повний shuffle з рівномірним перерозподілом; `coalesce(n)` — злиття партицій **без** shuffle, тільки для зменшення кількості.

```python
df.rdd.getNumPartitions()          # скільки зараз партицій
df.repartition(400)                # shuffle, рівномірно
df.repartition("zone_id")          # shuffle за колонкою (партиція = значення хешу)
df.coalesce(10)                    # без shuffle, тільки зменшити
```

**Орієнтир:** 2–4 партиції на доступне ядро, розмір партиції — сотні мегабайтів. Замало партицій — простій ядер і spill; забагато — накладні витрати на планування переважають корисну роботу.

**Data skew (перекіс)** — коли розподіл значень ключа нерівномірний і одна партиція отримує непропорційно багато даних. Симптом у Spark UI: 199 task-ів завершилися за 3 секунди, один працює 40 хвилин. Причини — NULL-и, дефолтні значення, «важкі» клієнти. Лікується AQE skew join, сіллю (salting) ключа або фільтрацією проблемних значень окремою гілкою.

#### 6.4 Спекулятивне виконання і повторні спроби

- **Retry.** Task, що впав, перезапускається до `spark.task.maxFailures` (за замовчуванням 4) разів, за можливості на іншому вузлі. Оскільки трансформації детерміновані й дані незмінні, повторне виконання безпечне.
- **Speculative execution.** Якщо task виконується помітно довше за медіанний у своєму stage, Spark може запустити його **дубль** на іншому вузлі й узяти результат того, хто фінішує першим. Захист від «повільного вузла» (деградований диск, перевантажений сусід). Вмикається `spark.speculation=true`; не допомагає проти skew, бо там повільна не машина, а обсяг даних.

### 7. Модель пам'яті executor-а

Розуміння того, як executor витрачає пам'ять, — необхідна умова для діагностики `OutOfMemoryError` і надмірного spill.

```
┌──────────────── Executor JVM (spark.executor.memory) ────────────────┐
│                                                                       │
│  Reserved Memory (~300 МБ)          службові потреби Spark            │
│  ───────────────────────────────────────────────────────────────────  │
│                                                                       │
│  Unified Memory  (spark.memory.fraction, за замовчуванням 0.6)        │
│  ┌─────────────────────────────────────────────────────────────────┐ │
│  │  Storage Memory                Execution Memory                 │ │
│  │  (кеш, broadcast)      ◄────►  (shuffle-буфери, hash-таблиці    │ │
│  │                                 join-ів, сортування, агрегації) │ │
│  │  spark.memory.storageFraction = 0.5 — М'ЯКА межа:               │ │
│  │  execution може витіснити storage, але не навпаки               │ │
│  └─────────────────────────────────────────────────────────────────┘ │
│                                                                       │
│  User Memory (решта ~40%)                                             │
│  ваші структури даних, UDF, метадані RDD                              │
└───────────────────────────────────────────────────────────────────────┘
              +
   Off-heap Overhead (spark.executor.memoryOverhead)
   Python-процеси PySpark, native-бібліотеки, мережеві буфери
```

Ключові моменти:

- **Storage і Execution ділять спільний пул** із рухомою межею (unified memory management, з Spark 1.6). Якщо кеш не використовується, вся пам'ять доступна обчисленням, і навпаки.
- **Execution має пріоритет.** Під тиском Spark витіснить закешовані блоки, щоб виконати shuffle. Зворотне неможливо — кеш не може «вигнати» активне обчислення.
- **Spill.** Коли execution-пам'яті не вистачає, Spark скидає проміжні структури на локальний диск. Job не падає, але сповільнюється в рази. У Spark UI це видно як «Spill (memory)» і «Spill (disk)» у метриках stage.
- **Overhead окремо.** Для PySpark це критично: Python-процеси живуть **поза** JVM-heap, і їхня пам'ять враховується саме в overhead. Типова помилка — «контейнер вбито YARN за перевищення ліміту пам'яті» при формально вільному heap.

**Найчастіші причини OOM:**

| Де | Причина |
|---|---|
| Driver | `collect()` / `toPandas()` на великому DataFrame; занадто великий broadcast; величезна кількість партицій |
| Executor | Сильний skew (одна партиція не влазить); занадто мало партицій; надто агресивне кешування; важкі Python-UDF |

### 8. Рівні API: RDD, DataFrame, Dataset

#### 8.1 Порівняння

| Властивість | RDD | DataFrame | Dataset |
|---|---|---|---|
| Рівень | Низький | Високий | Високий |
| Схема | Немає (просто об'єкти) | Є | Є |
| Типобезпека на етапі компіляції | Так | Ні (`Row`) | Так |
| Оптимізація Catalyst | **Ні** | Так | Так |
| Tungsten / codegen | Ні | Так | Частково |
| Мови | Scala, Java, Python | Scala, Java, Python, R | Тільки Scala, Java |
| Незмінність, відмовостійкість | Так | Так | Так |

**DataFrame — це `Dataset[Row]`.** У Scala вони об'єднані одним типом; у Python, де немає статичної типізації, доступний лише DataFrame.

#### 8.2 Практичний висновок

**Для дата-інженерії стандарт — DataFrame API (або Spark SQL, що еквівалентний за виконанням).** Причина одна й вирішальна: **RDD не проходить через Catalyst**. Ви пишете імперативний код, і Spark виконує його буквально, без predicate pushdown, без column pruning, без вибору стратегії join, без codegen.

```python
# RDD: ви диктуєте кожен крок; оптимізатор не втручається
result = (rdd
    .filter(lambda r: r["fare_amount"] > 0)
    .map(lambda r: (r["zone_id"], (r["fare_amount"], 1)))
    .reduceByKey(lambda a, b: (a[0] + b[0], a[1] + b[1]))
    .mapValues(lambda v: v[0] / v[1]))

# DataFrame: ви описуєте результат; план обирає Catalyst
result = (df
    .filter(F.col("fare_amount") > 0)
    .groupBy("zone_id")
    .agg(F.avg("fare_amount").alias("avg_fare")))
```

Другий варіант не просто коротший — він читатиме з Parquet **тільки дві колонки** й **тільки ті row groups**, де `fare_amount` може бути додатним, а потім виконає агрегацію в згенерованому Java-коді на бінарних рядках.

**Коли RDD усе ще доречний:** робота з неструктурованими даними, для яких немає схеми; потреба у власному partitioner-і; операції, відсутні в DataFrame API; налагодження низькорівневої поведінки. У щоденній практиці — рідко.

#### 8.3 PySpark і Py4J: як Python керує JVM

Spark виконується в JVM. PySpark — це **обгортка**, що керує JVM ззовні через бібліотеку **Py4J**:

```
   Python-процес (driver)                     JVM-процес (driver)
┌───────────────────────┐                ┌─────────────────────────┐
│ df.filter(...)        │  ── Py4J ───►  │  будує logical plan     │
│ df.groupBy(...)       │   (сокет)      │  Catalyst → physical    │
│ df.show()             │  ◄── результат │  DAGScheduler → task-и  │
└───────────────────────┘                └──────────┬──────────────┘
                                                     │
                                          розсилка task-ів на executor-и
```

**Ключовий момент:** коли ви пишете DataFrame-код, **через Py4J передається лише опис плану**, а не самі дані. Обчислення повністю відбувається в JVM. Накладні витрати мізерні.

Ситуація радикально змінюється з **Python UDF**:

```
Executor JVM  ──серіалізація рядків──►  Python worker (окремий процес)
              ◄──десеріалізація────────  виконання вашої функції
```

Кожен рядок серіалізується, пересилається в окремий Python-процес, обробляється, повертається назад. До цього додається: Catalyst не бачить середини UDF і не може її оптимізувати; predicate pushdown крізь UDF не працює; пам'ять Python-процесів йде в overhead.

**Ієрархія вибору, від найшвидшого до найповільнішого:**

1. **Вбудовані функції `pyspark.sql.functions`** — виконуються нативно в JVM з codegen. Завжди перший вибір.
2. **Pandas UDF (vectorized UDF)** — дані передаються пачками через **Apache Arrow** у колонковому форматі, функція отримує `pandas.Series`. У 10–100 разів швидше за звичайні UDF.
3. **Звичайні Python UDF** — рядок за рядком. Останній засіб.

```python
# Погано: Python UDF там, де є вбудована функція
@F.udf("double")
def double_fare(x):
    return x * 2

# Добре
df.withColumn("double_fare", F.col("fare_amount") * 2)

# Коли справді потрібна Python-логіка — pandas UDF
@F.pandas_udf("double")
def custom(s: pd.Series) -> pd.Series:
    return s.apply(complex_python_logic)
```

**Spark Connect** (з версії 3.4) змінює цю картину: клієнт передає план як gRPC-повідомлення, driver живе окремо на сервері. Це розв'язує клієнт і кластер, дозволяє легкі клієнти без локальної JVM і кілька одночасних сесій до одного кластера.

### 9. Spark UI: як прочитати те, що відбувається

Spark UI доступний на **http://localhost:4040** під час роботи застосунку (порт зсувається на 4041, 4042… якщо кілька застосунків), а після завершення — через History Server. Це основний інструмент діагностики.

#### 9.1 Вкладка Jobs

![Вкладка Jobs у Spark UI](https://spark.apache.org/docs/latest/img/AllJobsPage.png)

*Список job-ів застосунку: кожна дія породжує окремий job зі своїм статусом, тривалістю і кількістю виконаних task-ів. Джерело: [Spark Web UI](https://spark.apache.org/docs/latest/web-ui.html)*

Тут видно: скільки job-ів породив ваш код (кожен = одна дія), скільки часу зайняв кожен, скільки stage-ів у ньому. Timeline подій показує, коли додавалися й прибиралися executor-и.

Перше, що варто перевірити: **чи не породив ваш код більше job-ів, ніж ви очікували**. Зайві job-и — зазвичай ознака того, що один і той самий ланцюг обчислюється повторно й напрошується `cache()`.

#### 9.2 DAG-візуалізація

![Візуалізація DAG job-а](https://spark.apache.org/docs/latest/img/JobPage.png)

*Сторінка job-а з візуалізацією DAG: прямокутники — stage-и, стрілки між ними — shuffle-межі. Джерело: [Spark Web UI](https://spark.apache.org/docs/latest/web-ui.html)*

Найнаочніше представлення всього, що описано в розділі 6: видно, скільки stage-ів, які операції злиплися в один stage і де саме проходять shuffle-межі.

#### 9.3 Вкладка Stages

![Вкладка Stages](https://spark.apache.org/docs/latest/img/AllStagesPage.png)

*Усі stage-и застосунку зі статусами, тривалістю, кількістю task-ів і обсягами shuffle read/write. Джерело: [Spark Web UI](https://spark.apache.org/docs/latest/web-ui.html)*

Ключові колонки: **Shuffle Read** і **Shuffle Write** — скільки даних реально перекидається по мережі. Це головна метрика вартості вашого job-а.

![Деталі stage-а з розподілом метрик по task-ах](https://spark.apache.org/docs/latest/img/StagePage.png)

*Сторінка окремого stage-а: summary-метрики по task-ах (min / 25% / медіана / 75% / max), розподіл тривалості, обсягів вводу-виводу і spill. Джерело: [Spark Web UI](https://spark.apache.org/docs/latest/web-ui.html)*

**Це найважливіша сторінка для діагностики.** Дивіться на розподіл: якщо медіанний task триває 2 секунди, а max — 25 хвилин, у вас **data skew**. Якщо ненульові значення в рядках Spill (memory) / Spill (disk) — не вистачає execution-пам'яті.

#### 9.4 Вкладка SQL

![DAG плану SQL-запиту](https://spark.apache.org/docs/latest/img/webui-sql-dag.png)

*Візуалізація фізичного плану запиту з метриками кожного оператора: кількість рядків на виході, обсяг shuffle, час. Джерело: [Spark Web UI](https://spark.apache.org/docs/latest/web-ui.html)*

Тут фізичний план показується графом із **реальними метриками на кожному операторі**: скільки рядків вийшло зі скану, скільки залишилося після фільтра, який тип join обрано, скільки даних пройшло через `Exchange`. Це найпряміший спосіб перевірити, чи спрацював predicate pushdown і чи обрано очікувану стратегію join.

#### 9.5 Вкладки Executors і Storage

![Вкладка Executors](https://spark.apache.org/docs/latest/img/webui-exe-tab.png)

*Executor-и застосунку: використання пам'яті, дискова активність, кількість активних і завершених task-ів, час GC. Джерело: [Spark Web UI](https://spark.apache.org/docs/latest/web-ui.html)*

Дивіться на **GC Time** відносно Task Time: якщо збирач сміття з'їдає більше 10 % часу, executor-ам бракує пам'яті або вони занадто великі. Також помітно, чи рівномірно розподілена робота між executor-ами.

![Вкладка Storage](https://spark.apache.org/docs/latest/img/webui-storage-tab.png)

*Закешовані датасети: рівень persistence, скільки партицій у пам'яті проти диска, реальний обсяг. Джерело: [Spark Web UI](https://spark.apache.org/docs/latest/web-ui.html)*

Перевірка, чи справді ваш `cache()` спрацював: якщо «Fraction Cached» помітно менша за 100 %, дані не вміщаються, і кеш може приносити більше шкоди, ніж користі.

#### 9.6 Порядок діагностики повільного job-а

1. **Jobs** — який job довгий і чи немає зайвих повторних job-ів.
2. **Stages** — який stage довгий; подивитися Shuffle Read/Write.
3. **Деталі stage** — розподіл task-ів: skew? spill?
4. **SQL** — чи спрацював pushdown; чи правильна стратегія join; скільки рядків реально прочитано.
5. **Executors** — GC Time, рівномірність навантаження, наявність втрачених executor-ів.

### 10. Екосистема та місце Spark серед альтернатив

#### 10.1 Компоненти Spark

```
┌──────────┬───────────────┬────────┬────────┬──────────────┐
│ Spark SQL│  Structured   │ MLlib  │ GraphX │ Spark Connect│
│DataFrames│  Streaming    │        │        │              │
├──────────┴───────────────┴────────┴────────┴──────────────┤
│                      SPARK CORE                            │
│      RDD · DAG-планування · shuffle · пам'ять · відмово-   │
│      стійкість · планування task-ів                        │
├────────────────────────────────────────────────────────────┤
│  Cluster managers: Standalone · YARN · Kubernetes · local  │
├────────────────────────────────────────────────────────────┤
│  Джерела: S3/HDFS · Parquet/ORC/Avro/JSON/CSV ·            │
│  Iceberg/Delta/Hudi · Kafka · JDBC · Cassandra · MongoDB   │
└────────────────────────────────────────────────────────────┘
```

- **Spark SQL / DataFrames** — структуровані дані, SQL, Catalyst. Основний інтерфейс сьогодні.
- **Structured Streaming** — потокова обробка тим самим DataFrame API; потік трактується як нескінченна таблиця, що дописується.
- **MLlib** — розподілене машинне навчання: pipeline-и, класифікація, регресія, кластеризація, рекомендації.
- **GraphX / GraphFrames** — графові алгоритми (PageRank, компоненти зв'язності, найкоротші шляхи).
- **Spark Connect** — тонкий клієнт-серверний протокол на gRPC.

#### 10.2 Сильні й слабкі сторони

**Сильні:**
- Один движок для batch, SQL, streaming, ML — не треба вивчати й експлуатувати чотири різні системи.
- Кілька мов: Scala, Python, Java, R, SQL.
- Величезна кількість конекторів і зріла екосистема.
- Зрілий оптимізатор (Catalyst + AQE) і генерація коду (Tungsten).
- Працює скрізь: локально, YARN, Kubernetes, усі великі хмари.

**Слабкі:**
- **Складне налагодження:** Java-стеки з PySpark, необхідність читати Spark UI, неочевидний зв'язок між рядком коду й фізичним планом.
- **Високі накладні витрати на старт.** Для датасету на 5 ГБ DuckDB чи Polars на одній машині зазвичай будуть швидшими й простішими.
- **Потокова обробка через мікробатчі.** Structured Streaming дає затримки в сотні мілісекунд — секунди; для справжнього sub-millisecond потоку Flink підходить краще.
- **Чутливість до skew і до конфігурації пам'яті** — типовий продакшн-джоб вимагає тюнінгу.

#### 10.3 Альтернативи по нішах

| Ніша | Альтернативи |
|---|---|
| Один вузол, до сотень ГБ | DuckDB, Polars, pandas |
| Інтерактивний SQL по озеру даних | Trino / Presto, Athena, ClickHouse, Dremio |
| Хмарні сховища | Snowflake, BigQuery, Redshift, Databricks SQL |
| Потокова обробка з низькою затримкою | Apache Flink, Kafka Streams |
| Розподілений Python / ML | Ray, Dask |

Головне правило вибору: **розподілена система — не самоціль**. Вона додає складність, затримку й операційні витрати. Spark виправданий, коли дані не вміщаються на одну машину, коли потрібна єдина платформа для різнорідних навантажень, або коли обчислення справді треба масштабувати горизонтально. Для 3 ГБ CSV раз на тиждень DuckDB відпрацює за секунди й не вимагатиме кластера.

## Ключові терміни

| Термін | Визначення |
|---|---|
| **Application** | Один Spark-застосунок: driver + його executor-и, від `SparkSession` до `stop()` |
| **Driver** | Процес, що виконує `main()`, будує й оптимізує план, планує stage-и й task-и, координує executor-и. Єдина точка відмови |
| **Executor** | JVM-процес на worker-вузлі: виконує task-и, тримає кеш і shuffle-файли |
| **Cluster manager** | Компонент, що виділяє ресурси під executor-и: Standalone, YARN, Kubernetes, local |
| **Deploy mode (client / cluster)** | Driver запускається на клієнтській машині / всередині кластера |
| **SparkSession** | Єдина точка входу до всіх API з версії 2.0 |
| **local[N]** | Режим, у якому driver і executor живуть в одному JVM з N потоками |
| **MPP** | Massively Parallel Processing — незалежна паралельна обробка партицій |
| **RDD** | Resilient Distributed Dataset: незмінна розподілена колекція з партиціями, lineage і функцією обчислення |
| **Lineage** | Граф походження RDD; основа відмовостійкості без реплікації |
| **Checkpointing** | Матеріалізація RDD у надійне сховище з обрізанням lineage |
| **Narrow dependency** | Партиція батька використовується однією партицією нащадка; без мережевого обміну |
| **Wide dependency** | Партиція нащадка залежить від багатьох партицій батька; вимагає shuffle |
| **Persist / cache** | Збереження обчисленого датасету в пам'яті або на диску для повторного використання |
| **Lazy evaluation** | Трансформації лише будують план; виконання починається з дії |
| **Transformation** | Ліниво обчислювана операція, що повертає новий DataFrame/RDD |
| **Action** | Операція, що запускає виконання і повертає результат або пише дані |
| **Catalyst** | Оптимізатор запитів: analysis → logical optimization → physical planning → codegen |
| **Predicate pushdown** | Перенесення фільтрів якомога ближче до джерела даних |
| **Column pruning** | Читання лише тих колонок, що реально використовуються |
| **Cost model** | Механізм вибору фізичного плану з кандидатів за оцінками вартості |
| **Broadcast hash join** | Join із розсилкою малої сторони на всі executor-и; без shuffle |
| **Sort-merge join** | Join двох великих сторін через shuffle + сортування; варіант за замовчуванням |
| **Tungsten** | Підсистема ефективності: whole-stage codegen, бінарний формат `UnsafeRow`, off-heap пам'ять |
| **Whole-stage code generation** | Генерація Java-коду для цілого stage замість ланцюга віртуальних викликів |
| **AQE (Adaptive Query Execution)** | Переоптимізація плану під час виконання за реальною статистикою |
| **Job** | Одиниця виконання, що породжується однією дією |
| **Stage** | Група трансформацій без shuffle між ними; межа stage = wide dependency |
| **Task** | Виконання коду stage над однією партицією; найдрібніша одиниця роботи |
| **Partition** | Незалежний шматок даних; одна партиція → один task → один слот-ядро |
| **Shuffle** | Перерозподіл даних між executor-ами по мережі; запис на диск + мережевий обмін |
| **Exchange** | Позначення shuffle у фізичному плані Spark |
| **spark.sql.shuffle.partitions** | Кількість партицій після shuffle; за замовчуванням 200 |
| **repartition / coalesce** | Зміна кількості партицій із shuffle / без shuffle (тільки зменшення) |
| **Data skew** | Нерівномірний розподіл ключів: одна партиція значно більша за інші |
| **Spill** | Скидання проміжних даних на локальний диск через брак пам'яті |
| **Unified memory** | Спільний пул storage і execution пам'яті з рухомою межею; execution має пріоритет |
| **memoryOverhead** | Позаheapова пам'ять executor-а: Python-процеси, native-бібліотеки, буфери |
| **Speculative execution** | Дублювання аномально повільних task-ів на іншому вузлі |
| **DataFrame / Dataset** | Високорівневі API зі схемою й Catalyst; Dataset типобезпечний, тільки Scala/Java |
| **Py4J** | Міст між Python-процесом і JVM, через який PySpark керує Spark |
| **Python UDF / pandas UDF** | Порядкова функція з серіалізацією в Python-процес / векторизована через Arrow |
| **Apache Arrow** | Колонковий формат обміну в пам'яті, що прискорює передачу між JVM і Python |
| **Spark Connect** | Клієнт-серверний протокол на gRPC, що відв'язує клієнта від кластера |
| **Spark UI** | Веб-інтерфейс на порту 4040: Jobs, Stages, SQL, Executors, Storage |
