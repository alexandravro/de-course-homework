# Заняття 10. Розподілені сховища даних: object storage, HDFS та table formats

## Про що це заняття

Будь-яка аналітична платформа стоїть на двох стовпах: **де лежать дані** і **як над ними виконуються обчислення**. Це заняття повністю присвячене першому стовпу.

Ми пройдемо три рівні абстракції, які нашаровуються один на одного:

1. **Фізичний рівень** — як взагалі бувають влаштовані сховища: block, file, object. Чому для аналітики виграв саме object storage.
2. **Рівень розподіленої системи зберігання** — спочатку HDFS як класична відповідь на питання «як зберігати петабайти на дешевому залізі», потім Amazon S3 як те, що прийшло їй на зміну. Порядок тут не хронологічний примх: майже кожне обмеження S3 — це свідома відмова від якоїсь властивості HDFS в обмін на масштаб і ціну, тож із контрастом воно зрозуміліше.
3. **Рівень таблиці** — table format (Apache Iceberg): шар метаданих, який перетворює купу файлів у справжню таблицю з ACID, історією версій і еволюцією схеми.

Після цього заняття ви зможете: обґрунтовано обрати тип сховища під задачу, описати архітектуру HDFS і пояснити, чому вона програє S3 у хмарі, спроєктувати політику тірингу й порахувати, коли вона справді економить, розібрати дерево метаданих Iceberg по рівнях, пояснити, як на сховищі без транзакцій з'являються ACID-транзакції, і назвати операції обслуговування, без яких lakehouse деградує.

## Що треба знати заздалегідь

- Колонковий формат зберігання (Parquet): row groups, column chunks, footer зі схемою і статистикою.
- Базові поняття транзакцій: ACID, MVCC, ізоляція.
- Загальне уявлення про розподілені системи: вузли, реплікація, відмовостійкість.
- SQL на рівні DDL/DML.

## Основний матеріал

### 1. Три типи сховищ: block, file, object

Перед тим як говорити про «сховища даних» у сенсі аналітики, потрібно чітко розрізняти три принципово різні способи, якими взагалі можна віддавати дані споживачу. Вони відрізняються **одиницею адресації** — тим, чим саме оперує клієнт.

#### 1.1 Block storage (блокове сховище)

Найнижчий рівень абстракції. Пристрій віддає назовні лінійний масив **блоків** фіксованого розміру (історично 512 байт, сучасні диски — 4 KB). Кожен блок адресується номером (LBA — Logical Block Address). Пристрій **нічого не знає** про файли, директорії чи їх назви — це просто пронумеровані комірки.

Файлова система (ext4, XFS, NTFS, APFS) — це програмний шар **поверх** блокового пристрою, який вигадує поняття файлу, директорії, прав доступу і зберігає ці структури в тих самих блоках.

- **Приклади:** локальний SSD/NVMe/HDD, Amazon EBS, iSCSI/SAN-масиви, Google Persistent Disk.
- **Одиниця операції:** блок. Можна прочитати або перезаписати **окремий блок** у довільному місці — це і є random I/O.
- **Latency:** десятки–сотні мікросекунд для NVMe, одиниці мілісекунд для мережевого блокового сховища.
- **Масштабування:** переважно вертикальне. Том має фіксований розмір; його можна збільшити, але не «до нескінченності». Один том зазвичай монтується до **однієї** машини.
- **Типові споживачі:** операційна система, реляційні БД (PostgreSQL, MySQL, Oracle пишуть свої data files і WAL саме сюди), віртуальні машини.

Ключова властивість, заради якої існує block storage: **можливість змінити частину файлу на місці (in-place update)**. Саме тому OLTP-бази живуть на ньому — щоб оновити один рядок, СУБД перезаписує одну сторінку (8 KB у PostgreSQL), а не весь файл.

#### 1.2 File storage (файлове/мережеве сховище, NAS)

Рівень вище. Сховище саме реалізує файлову систему і віддає її по мережі одразу кільком клієнтам через протоколи **NFS** (Unix-світ) або **SMB/CIFS** (Windows-світ). Клієнт монтує «шару» і бачить звичну ієрархію директорій.

- **Приклади:** Amazon EFS, Azure Files, Google Filestore, класичні NAS-пристрої (NetApp, Synology), Lustre / FSx for Lustre у HPC.
- **Одиниця операції:** файл або діапазон байтів у файлі, але через мережевий протокол.
- **Latency:** мілісекунди — до вартості диска додається мережевий round-trip.
- **Головна цінність:** **POSIX-семантика для багатьох клієнтів одночасно**. Це означає ієрархію директорій, атомарний `rename()`, блокування файлів (`flock`), права доступу, можливість дописувати в кінець файлу.
- **Типові споживачі:** shared home directories, legacy enterprise-застосунки, які «просто хочуть звичайний диск», CMS з кількома веб-серверами, HPC-кластери.

Обмеження: метадані (дерево директорій) — централізовані, а тому стають вузьким місцем. Мільярд файлів у NAS — операційний біль. Вартість за гігабайт у рази вища за object storage.

#### 1.3 Object storage (об'єктне сховище)

Принципово інша модель. Немає ані блоків, ані файлової системи. Є **пласкій простір імен (flat namespace)**, у якому лежать **об'єкти**. Об'єкт — це трійка:

```
ключ (key)   →   тіло (bytes)   +   метадані (key-value)
```

Доступ — виключно через HTTP REST API: `PUT` (записати об'єкт цілком), `GET` (прочитати цілком або діапазон байтів), `DELETE`, `LIST` (перелічити ключі за префіксом). **Жодного `seek`, `write at offset`, `append` чи `rename`.**

![Високорівнева архітектура object storage](https://upload.wikimedia.org/wikipedia/commons/thumb/5/5d/High_level_object_storage_architecture.svg/960px-High_level_object_storage_architecture.svg.png)

*Високорівнева архітектура об'єктного сховища: клієнти звертаються по HTTP до шару доступу, який розкладає об'єкти по вузлах зберігання. Джерело: [Wikimedia Commons](https://commons.wikimedia.org/wiki/File:High_level_object_storage_architecture.svg)*

- **Приклади:** Amazon S3, Google Cloud Storage, Azure Blob Storage, MinIO, Ceph RADOS Gateway, Backblaze B2, Cloudflare R2.
- **Одиниця операції:** цілий об'єкт (з важливим винятком — range GET, див. нижче).
- **Latency:** десятки–сотні мілісекунд на перший байт. Дуже повільно для одного дрібного запиту, але **величезний агрегований throughput**, якщо запитів багато й вони паралельні.
- **Масштабування:** горизонтальне і практично необмежене. Мільярди й трильйони об'єктів, петабайти й ексабайти.
- **Вартість:** найдешевший з трьох рівнів (порядок $0.02/GB/місяць за «гарячий» клас).

**Директорій не існує.** Ключ `bronze/year=2024/month=01/part-0000.parquet` — це просто рядок із символами `/`. Сховище не має вузла «директорія `bronze/`». Консолі AWS та MinIO малюють «папки», емулюючи їх за спільним префіксом ключа. З цього випливає найважливіший практичний наслідок:

> **Перейменувати «директорію» в object storage не можна.** Операція `mv s3://bucket/a/ s3://bucket/b/` фізично означає: перелічити всі об'єкти з префіксом `a/`, скопіювати кожен на новий ключ, видалити кожен старий. Для мільйона файлів це мільйони HTTP-запитів. У POSIX-системі це був би один атомарний `rename()` за мікросекунди.

Багато старих big-data інструментів (включно з Hadoop) припускали дешевий атомарний rename — і саме тому працюють на object storage повільно й ненадійно, поки не використовують спеціальні committer'и.

#### 1.5 Чому аналітика обрала object storage

Аналітичне навантаження має характерний профіль, який майже ідеально лягає на обмеження object storage:

- Дані **пишуться один раз і читаються багато разів** (write-once-read-many). Неможливість in-place update майже не заважає.
- Читання — **великими послідовними шматками** (сканування колонки Parquet), а не випадковими байтами. Range GET це покриває.
- Запитів багато й вони **паралельні** — тисячі тасок читають тисячі файлів. Висока latency одного запиту компенсується паралелізмом.
- Обсяги ростуть **необмежено**, а бюджет — ні. Ціна за гігабайт стає визначальним фактором.

Плюс архітектурний бонус, який змінив індустрію: **розділення storage і compute**. У класичній MPP-БД (Teradata, Vertica, Greenplum) диски приварені до обчислювальних вузлів — щоб додати місця, треба додати серверів, і навпаки. В object storage дані живуть окремо: можна тримати 500 ТБ і не платити ні цента за compute, поки ніхто не робить запити, а потім підняти 200 воркерів на 20 хвилин. Саме на цьому побудовані Snowflake, BigQuery, Athena, Databricks і будь-який сучасний lakehouse.

### 2. HDFS: класична розподілена файлова система

HDFS (Hadoop Distributed File System) — реалізація ідей Google File System (стаття 2003 року) у складі Hadoop. Історично це перше масове рішення для зберігання петабайтів на дешевому «commodity»-залізі, і саме воно задало словник, яким галузь користується досі: блок, реплікація, data locality, NameNode.

Ми розбираємо його **першим** не з поваги до історії, а тому що object storage найлегше зрозуміти через контраст: майже кожне обмеження S3 — це свідома відмова від якоїсь властивості HDFS в обмін на масштаб і ціну. Сьогодні у хмарі HDFS переважно витіснений, але в on-premise-датацентрах він досі домінує, а його архітектурні рішення повторені в десятках систем.

#### 2.1 Проєктні припущення

HDFS свідомо оптимізований під дуже вузький профіль навантаження, і всі його рішення випливають з чотирьох припущень:

1. **Відмови — норма, а не виняток.** Кластер з тисяч дешевих серверів означає, що щодня щось ламається. Відмовостійкість має бути вбудована, а не додана згори.
2. **Файли великі.** Типовий файл — гігабайти й терабайти. Система не розрахована на мільйони дрібних файлів.
3. **Патерн доступу — write-once, read-many.** Файл записується один раз, потім багато разів читається послідовно. Довільний запис не підтримується.
4. **Дешевше перемістити обчислення до даних, ніж дані до обчислень.** Це принцип **data locality**.

Наслідок: HDFS дає **високу пропускну здатність (throughput)** ціною **високої затримки (latency)**. Він поганий для інтерактивних запитів по одному рядку і чудовий для сканування терабайта.

#### 2.2 Архітектура: NameNode і DataNode

HDFS має класичну **master/slave** архітектуру з жорстким розділенням метаданих і даних.

![Архітектура HDFS](https://hadoop.apache.org/docs/current/hadoop-project-dist/hadoop-hdfs/images/hdfsarchitecture.png)

*Архітектура HDFS: NameNode тримає метадані та мапу блоків, DataNode зберігають самі блоки, клієнт отримує від NameNode адреси й читає дані напряму з DataNode. Джерело: [Apache Hadoop HDFS Architecture](https://hadoop.apache.org/docs/current/hadoop-project-dist/hadoop-hdfs/HdfsDesign.html)*

**NameNode (master)** — тримає **всі метадані файлової системи в оперативній пам'яті**:
- Namespace: дерево директорій і файлів, права, власники, timestamps.
- Мапа «файл → список блоків».
- Мапа «блок → на яких DataNode лежать його репліки» (будується з heartbeat-звітів, а не зберігається на диску).

NameNode **ніколи не бачить самих даних** — через нього не проходить жоден байт користувацького контенту. Він лише відповідає клієнту: «блок B123 лежить на DataNode 7, 12 і 31».

Персистентність метаданих забезпечують два артефакти:
- **fsimage** — знімок усього namespace на диску.
- **edit log (journal)** — журнал усіх змін після останнього fsimage.

При старті NameNode читає fsimage і програє поверх нього edit log. **Secondary NameNode** (назва історично невдала — це не резервний вузол) періодично зливає fsimage з edit log у новий fsimage, щоб журнал не ріс нескінченно й старт не тривав годинами.

**DataNode (slave)** — зберігає блоки як звичайні файли на локальній файловій системі. Кожні кілька секунд надсилає NameNode **heartbeat** («я живий») і періодично **block report** («ось повний список блоків, які в мене є»). Якщо heartbeat не приходить понад таймаут (за замовчуванням ~10 хвилин), NameNode оголошує вузол мертвим і запускає ре-реплікацію блоків, що втратили копію.

#### 2.3 Блоки і реплікація

Файл розбивається на **блоки фіксованого розміру** — за замовчуванням **128 МБ** (у ранніх версіях 64 МБ). Останній блок може бути меншим.

Чому блок такий великий, коли у звичайній файловій системі це 4 КБ? Щоб **час пошуку (seek) був мізерним відносно часу передачі**. Якщо seek займає 10 мс, а диск читає 100 МБ/с, то блок на 128 МБ читається ~1,3 с — накладні витрати на позиціонування менші за 1 %.

Кожен блок реплікується — за замовчуванням у **три копії** (`dfs.replication=3`).

![Реплікація блоків HDFS по DataNode](https://hadoop.apache.org/docs/current/hadoop-project-dist/hadoop-hdfs/images/hdfsdatanodes.png)

*Розподіл реплік блоків по DataNode: кожен блок кожного файлу присутній на кількох вузлах. Джерело: [Apache Hadoop HDFS Architecture](https://hadoop.apache.org/docs/current/hadoop-project-dist/hadoop-hdfs/HdfsDesign.html)*

```
Файл /data/events.parquet (500 МБ) → 4 блоки по 128 МБ:

blk_1  →  DataNode 01, DataNode 03, DataNode 07
blk_2  →  DataNode 02, DataNode 05, DataNode 01
blk_3  →  DataNode 04, DataNode 06, DataNode 03
blk_4  →  DataNode 01, DataNode 02, DataNode 08
```

**Rack awareness** — політика розміщення реплік з урахуванням стійок (rack) у датацентрі. За замовчуванням: перша репліка — на вузлі, де виконується запис (або випадковому, якщо клієнт поза кластером); друга — на вузлі в **іншій** стійці; третя — на ще одному вузлі **тієї самої другої** стійки.

Логіка компромісу: щонайменше дві стійки задіяні, тому відмова цілої стійки (комутатора, живлення) не знищує всі копії. Але й не три різні стійки — бо трафік між стійками дорожчий за трафік усередині.

**Erasure coding** (з Hadoop 3) — альтернатива реплікації. Замість 3 копій (200 % надлишку) використовується схема на кшталт RS(6,3): 6 блоків даних + 3 блоки парності, тобто 50 % надлишку при стійкості до втрати трьох будь-яких блоків. Ціна — дорожче відновлення (треба читати кілька блоків і рахувати) і втрата data locality. Використовується для холодних даних.

#### 2.4 Як відбуваються читання і запис

**Читання:**
1. Клієнт → NameNode: «дай локації блоків файлу `/data/events.parquet`».
2. NameNode повертає для кожного блоку список DataNode, **відсортований за мережевою близькістю** до клієнта.
3. Клієнт зв'язується **напряму з DataNode** і тягне блоки. NameNode у передачі даних не бере участі.

**Запис (replication pipeline):**
1. Клієнт → NameNode: «хочу створити файл, дай вузли під перший блок».
2. NameNode перевіряє права, резервує блок і повертає список з 3 DataNode.
3. Клієнт відкриває **конвеєр**: шле пакети першому DataNode, той одночасно пише на диск і пересилає другому, другий — третьому.
4. Підтвердження (ack) йдуть у зворотному напрямку по конвеєру.
5. Коли всі блоки записані — клієнт повідомляє NameNode, і файл стає видимим.

Конвеєрна схема (а не «клієнт шле три копії сам») економить вихідну смугу клієнта втричі.

#### 2.5 Слабкі місця NameNode і як їх лікують

**Проблема 1: NameNode — єдина точка відмови.** Впав NameNode — недоступна вся файлова система, хоча дані цілі.

Рішення — **HDFS High Availability**: два NameNode, active і standby. Обидва читають той самий edit log, який пишеться в кворум **JournalNode** (зазвичай трьох). Автоматичне перемикання координує **ZooKeeper** через ZKFailoverController. Standby одночасно виконує роль checkpoint-вузла (зливає fsimage), тому Secondary NameNode в HA-конфігурації не потрібен.

**Проблема 2: метадані обмежені пам'яттю одного NameNode.** Кожен файл, директорія і блок займають приблизно 150 байтів RAM. Мільйон дрібних файлів з'їдає приблизно стільки ж пам'яті, скільки мільйон великих — але при цьому дає в сотні разів менше корисних даних. Це **small files problem у версії HDFS**: файл на 1 КБ займає повноцінний запис у метаданих і окремий блок-контейнер.

Рішення — **HDFS Federation**: кілька незалежних NameNode, кожен обслуговує свій namespace (`/logs`, `/warehouse`, `/users`), а пул DataNode спільний.

![HDFS Federation](https://hadoop.apache.org/docs/current/hadoop-project-dist/hadoop-hdfs/images/federation.gif)

*HDFS Federation: незалежні namespace-и на різних NameNode поверх спільного пулу block storage з DataNode. Джерело: [Apache Hadoop HDFS Federation](https://hadoop.apache.org/docs/current/hadoop-project-dist/hadoop-hdfs/Federation.html)*

#### 2.6 Data locality

Ключова ідея Hadoop-епохи: **обчислення дешевше перемістити до даних, ніж дані до обчислень**. Планувальник (YARN) намагається запустити таску на тому вузлі, де фізично лежить потрібний блок. Ієрархія переваг:

1. **NODE_LOCAL** — таска на тому самому вузлі, читання з локального диска, нуль мережевого трафіку.
2. **RACK_LOCAL** — таска в тій самій стійці, трафік через один комутатор.
3. **ANY** — довільний вузол, трафік через мережу датацентру.

У 2008 році, коли мережа була 1 Gbps, а диски давали 100 МБ/с, це давало колосальний виграш. У 2020-х ситуація змінилася: мережа в датацентрі — 25–100 Gbps, і вона вже не є вузьким місцем. Це одна з причин, чому індустрія спокійно перейшла на «дані окремо, compute окремо» — і саме з цього моменту починається розділ про S3.

### 3. Amazon S3 як еталон object storage

S3 (Simple Storage Service, запущений у 2006 році) — не просто один із продуктів, а **де-факто стандарт API**. Google Cloud Storage, MinIO, Ceph, Cloudflare R2, Backblaze B2 реалізують S3-сумісний інтерфейс, тому код, написаний під S3, працює з ними майже без змін.

Читаючи цей розділ, зіставляйте кожен пункт із попереднім: там, де HDFS давав ієрархію й атомарний rename, тут буде пласкій namespace; там, де HDFS вимагав живого кластера — тут оплата лише за зберігання.

#### 3.1 Модель даних

```
Account
  └── Bucket  (глобально унікальне ім'я, прив'язаний до регіону)
        ├── Object   key: "bronze/year=2024/month=01/part-00000.parquet"
        │            body: <bytes>
        │            metadata: Content-Type, user-defined tags, ...
        │            versionId, ETag, storage class
        └── Object   key: "bronze/year=2024/month=02/part-00000.parquet"
```

- **Bucket** — контейнер верхнього рівня. Ім'я глобально унікальне серед усіх акаунтів AWS. Бакет прив'язаний до конкретного **регіону** — дані фізично не покидають його, поки ви явно не налаштуєте реплікацію.
- **Key** — повний шлях-рядок, до 1024 байтів UTF-8. Максимальний розмір одного об'єкта — 5 ТБ.
- **ETag** — хеш вмісту (для простого завантаження це MD5). Використовується для перевірки цілісності та **умовних запитів** (розділ 3.6).
- **Метадані** — системні (Content-Type, Content-Encoding) та користувацькі (`x-amz-meta-*`).
- **Теги об'єкта** — до 10 пар ключ-значення, які можна змінювати **не переписуючи об'єкт**. За ними працюють lifecycle-правила, розбивка витрат і політики доступу.

#### 3.2 Операції API, які реально важливі для дата-інженера

| Операція | Що робить | Чому важлива |
|---|---|---|
| `PUT Object` | Записує об'єкт цілком | Єдиний спосіб «змінити» дані — перезаписати |
| `GET Object` | Читає об'єкт цілком | Базове читання |
| **`GET Object` з `Range:`** | Читає **діапазон байтів** | **Основа роботи з Parquet**: спершу читаємо footer, з нього дізнаємось offset потрібного column chunk, потім читаємо тільки його |
| `HEAD Object` | Тільки метадані (розмір, ETag) | Перевірка існування без завантаження |
| `LIST Objects V2` | Перелічує ключі за префіксом | Дорога операція: 1000 ключів за запит, з пагінацією |
| `DELETE Object` | Видаляє об'єкт | — |
| `Multipart Upload` | Заливає великий об'єкт частинами (5 МБ – 5 ГБ кожна) паралельно | Обов'язкове для великих файлів; частина, що не долилась, перезаливається окремо |
| `CopyObject` | Копіювання серверною стороною | Використовується для емуляції rename і для зміни класу зберігання |

**Range GET заслуговує окремої уваги.** Саме він робить колонкові формати ефективними на object storage. Щоб порахувати `SUM(amount)` з Parquet-файлу на 500 МБ, движок:
1. Робить range GET останніх ~64 KB — це footer зі схемою, offsets та min/max статистикою.
2. Дивиться, які row groups взагалі можуть містити потрібні дані.
3. Робить range GET рівно тих байтів, де лежить колонка `amount` у потрібних row groups.

Замість 500 МБ трафіку — 15 МБ. Це і є «projection pushdown» + «predicate pushdown» на рівні сховища.

**LIST — прихований ворог.** Операція перелічення повертає максимум 1000 ключів за запит і оплачується. Таблиця з 200 000 файлів у 5000 «директорій» вимагає сотень LIST-запитів **перед тим, як прочитати хоча б байт даних**. Це одна з ключових причин появи table formats: вони зберігають перелік файлів у власних метаданих і LIST не роблять взагалі.

#### 3.3 Durability і availability

S3 Standard декларує **99,999999999 % durability** (одинадцять дев'яток) на рік. Практично це означає: якщо зберігати 10 мільйонів об'єктів, статистично один об'єкт втрачається раз на 10 000 років. Досягається це синхронною реплікацією щонайменше в три Availability Zone (фізично різні датацентри в межах регіону) плюс постійна фонова перевірка контрольних сум і автоматичне відновлення.

Availability (доступність сервісу) — нижча за durability: 99,99 % для Standard. Дані не втрачені, але сервіс може бути тимчасово недоступним.

Класи з однією зоною (`One Zone-IA`, `Express One Zone`) мають **ту саму заявлену durability**, але не переживають втрати цілої Availability Zone. Це різні властивості, і плутати їх не можна: «одинадцять дев'яток» — про носії, а не про катастрофу в датацентрі.

#### 3.4 Класи зберігання й тіринг

Тіринг — головний важіль вартості озера даних. Ідея проста: дані «холонуть» з часом, і платити за тримісячні логи як за гарячі — марно. Реалізація має неочевидну економіку, і саме в ній ховаються помилки.

**Класи зберігання:**

| Клас | AZ | Мін. термін | Мін. оплачуваний розмір | Плата за отримання | Затримка доступу |
|---|---|---|---|---|---|
| **S3 Express One Zone** | 1 | — | — | Ні | Одиниці мс (до 10× швидше за Standard) |
| **S3 Standard** | ≥3 | — | — | Ні | Мілісекунди |
| **S3 Intelligent-Tiering** | ≥3 | — | — | Ні (є плата за моніторинг) | Мілісекунди |
| **S3 Standard-IA** | ≥3 | 30 днів | 128 КБ | Так | Мілісекунди |
| **S3 One Zone-IA** | 1 | 30 днів | 128 КБ | Так | Мілісекунди |
| **S3 Glacier Instant Retrieval** | ≥3 | 90 днів | 128 КБ | Так | Мілісекунди |
| **S3 Glacier Flexible Retrieval** | ≥3 | 90 днів | +40 КБ накладних | Так | Хвилини–години, потрібен `RestoreObject` |
| **S3 Glacier Deep Archive** | ≥3 | 180 днів | +40 КБ накладних | Так | Години, потрібен `RestoreObject` |

Зверніть увагу, що **Express One Zone — це тір у протилежний бік**: не дешевше зберігання, а нижча затримка (ціною однієї зони й дорожчого зберігання, хоча запити дешевші). Він живе в **directory buckets** — окремому типі бакета з ієрархічним namespace, де директорії справжні, а не емульовані префіксами. Доречний для інтенсивних дрібних читань: shuffle-даних, ML-тренування, інтерактивної аналітики.

**S3 Intelligent-Tiering** переміщує об'єкти автоматично, за фактичним доступом, і **не бере плати за отримання**:

```
Frequent Access  ──30 днів без доступу──►  Infrequent Access
                 ──90 днів без доступу──►  Archive Instant Access
   (опційно, вмикається окремо)
                 ──90 днів──►  Archive Access        (потрібен restore)
                 ──180 днів──► Deep Archive Access   (потрібен restore)
```

Плата — за моніторинг кожного об'єкта. Звідси головне обмеження: **об'єкти менші за 128 КБ не моніторяться й ніколи не переходять** — вони назавжди залишаються у Frequent Access. Для озера з мільйонів дрібних файлів Intelligent-Tiering не дасть нічого, крім рахунку за моніторинг.

**Lifecycle policies** описують переходи правилами:

```json
{
  "Rules": [{
    "ID": "logs-tiering",
    "Filter": { "And": {
      "Prefix": "logs/",
      "ObjectSizeGreaterThan": 131072
    }},
    "Status": "Enabled",
    "Transitions": [
      { "Days": 30,  "StorageClass": "STANDARD_IA" },
      { "Days": 180, "StorageClass": "GLACIER_IR" },
      { "Days": 730, "StorageClass": "DEEP_ARCHIVE" }
    ],
    "Expiration": { "Days": 2555 }
  }]
}
```

**Переходи однонаправлені** — це водоспад:

![Водоспад переходів між класами зберігання S3](https://docs.aws.amazon.com/AmazonS3/latest/userguide/images/lifecycle-transitions-v4.png)

*Підтримувані переходи між класами: рухатися можна лише «вниз», у бік холоднішого й дешевшого. Джерело: [Amazon S3 User Guide — Transitioning objects](https://docs.aws.amazon.com/AmazonS3/latest/userguide/lifecycle-transition-general-considerations.html)*

Повернути об'єкт із Deep Archive у Standard одним lifecycle-правилом **неможливо**: спершу `RestoreObject`, потім `CopyObject` поверх себе з новим класом.

##### Економіка тірингу — п'ять пасток

Це та частина, через яку «оптимізація» регулярно збільшує рахунок замість того, щоб його зменшити.

**1. Мінімальний оплачуваний розмір.** Об'єкт на 10 КБ у Standard-IA тарифікується як 128 КБ — у 12,8 раза більше за фактичний обсяг. Дешевший тариф за гігабайт не рятує, якщо гігабайтів раптом стало більше.

**2. Кожен перехід — платний запит.** Перенесення 50 мільйонів дрібних об'єктів у Glacier — це 50 мільйонів тарифікованих запитів на переходи. Для дрібних файлів **вартість переходу перевищує економію на зберіганні**. Саме тому з вересня 2024 року S3 за замовчуванням **не переносить об'єкти менші за 128 КБ у жоден клас**; щоб змінити цю поведінку, потрібен явний фільтр `ObjectSizeGreaterThan` / `ObjectSizeLessThan` у правилі.

**3. Мінімальний термін зберігання утримується навіть після видалення.** Видалили або перенесли об'єкт із Standard-IA на 5-й день — платите за всі 30. Для Deep Archive це 180 днів. Дані, що живуть тиждень, у холодних класах коштують дорожче, ніж у Standard.

**4. Мінімальний термін обмежує ланцюжок правил.** Не можна написати «у Glacier IR через 4 дні, у Deep Archive через 20» — між ними має пройти щонайменше 90 днів мінімального терміну GIR. Перехід у Deep Archive у цьому прикладі можливий не раніше 94-го дня.

**5. Накладні витрати архівних класів.** Кожен об'єкт у Glacier Flexible Retrieval або Deep Archive додає **40 КБ метаданих**: 32 КБ за тарифом самого Glacier і 8 КБ за тарифом Standard (щоб ім'я об'єкта залишалося видимим у `LIST`). Для об'єкта на 20 КБ накладні витрати вдвічі більші за корисні дані.

**Висновок, який варто зробити один раз і застосовувати завжди:** тіринг вигідний для **великих об'єктів із довгим життям**. Для дрібних файлів правильна відповідь — не архівувати їх, а **об'єднати в більші** (компакція таблиці), і лише потім тірити. Це та сама small files problem, вигляд збоку від рахунку.

##### Чим приймати рішення

Правила писати навмання не варто — є два інструменти:

- **S3 Storage Class Analysis** — аналізує фактичні патерни доступу за префіксом чи тегом і показує, коли дані реально «холонуть». З цього виводиться правильне число днів у правилі.
- **S3 Storage Lens** — панель з розподілом обсягу за класами, віком і префіксами по всій організації; показує, зокрема, скільки місця з'їдають незавершені multipart uploads і неточні версії.

#### 3.5 Модель узгодженості

Історично S3 був **eventually consistent** для перезапису і видалення: після `PUT` поверх наявного ключа читач якийсь час міг отримати стару версію. Це породило цілий клас багів у Hadoop-екосистемі і навіть окремі продукти-костилі (S3Guard).

З грудня 2020 року S3 надає **strong read-after-write consistency** для всіх операцій: після успішного `PUT` або `DELETE` будь-яке наступне читання (`GET`, `LIST`) бачить актуальний стан. Безкоштовно, без налаштувань.

![Модель узгодженості S3: читання після запису](https://docs.aws.amazon.com/images/AmazonS3/latest/userguide/images/consistency1.png)

*Strong read-after-write consistency: запис нового об'єкта одразу видимий для наступного читання. Джерело: [Amazon S3 User Guide](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html)*

**Важливо не переплутати:** сильна узгодженість стосується **одного об'єкта**. Вона нічого не каже про **набір об'єктів**. Якщо ваш процес записує 500 Parquet-файлів, а читач приходить посеред запису, він побачить консистентний стан кожного окремого файлу — але **неповну таблицю**. Ось чому S3 сам по собі не дає транзакцій на рівні таблиці, і чому потрібен table format.

#### 3.6 Умовні записи: compare-and-swap на об'єктному сховищі

Довгий час у S3 не було жодного способу сказати «запиши, тільки якщо ніхто не змінив це до мене». Два процеси, що писали один ключ, обидва отримували успіх, і перемагав останній — мовчки. Саме через це кожна транзакційна надбудова над S3 змушена була виносити атомарність у зовнішній каталог.

З 2024 року S3 підтримує **умовні записи** через стандартні HTTP-заголовки:

| Заголовок | Семантика | Застосування |
|---|---|---|
| `If-None-Match: *` | Запис виконується, **тільки якщо ключа ще немає**; інакше `412 Precondition Failed` | Write-if-absent: гарантія, що два процеси не створять один об'єкт |
| `If-Match: "<etag>"` | Запис або видалення виконується, **тільки якщо поточний ETag збігається** | Повноцінний compare-and-swap: «заміни версію A на B, якщо це досі A» |

```python
try:
    s3.put_object(
        Bucket="lake", Key="catalog/v42.metadata.json",
        Body=payload, IfNoneMatch="*",
    )
except s3.exceptions.ClientError as err:
    if err.response["Error"]["Code"] == "PreconditionFailed":
        ...  # хтось нас випередив — перечитати стан і повторити
```

Це принципова зміна: **об'єктне сховище отримало примітив, на якому будується оптимістичне керування конкурентністю**. Тепер каталог table format може жити в самому S3, а не вимагати окремої бази під вказівник. Тримайте це в голові, коли дійдемо до commit protocol Iceberg (розділ 5.4) — там ця операція є центральною.

Умовні записи не роблять S3 транзакційним: вони атомарні для **одного ключа**, а не для набору об'єктів. Але одного атомарного ключа достатньо, щоб побудувати транзакцію на рівні таблиці — саме це й роблять table formats.

#### 3.7 Продуктивність і масштабування запитів

S3 автоматично масштабується до **3500 PUT/COPY/POST/DELETE та 5500 GET/HEAD запитів на секунду на префікс**. Префікс — це фактично частина ключа, за якою S3 шардує внутрішні індекси.

Практичний висновок: розкладання даних по багатьох префіксах (наприклад, `year=2024/month=01/day=15/`) дає не тільки partition pruning, а й вищий сумарний ліміт запитів. Якщо всі 10 мільйонів файлів лежать під одним префіксом, ви впираєтесь у стелю й отримуєте `503 SlowDown`.

Друга сторона медалі — **small files problem**. Читання одного файлу на 1 МБ і одного на 128 МБ коштує приблизно однакового round-trip-часу. 10 000 файлів по 1 МБ читатимуться в рази довше за 80 файлів по 128 МБ при тому самому обсязі даних. Оптимальний розмір файлу для аналітики на object storage — **128 МБ – 1 ГБ**.

#### 3.8 Події, інвентаризація та масові операції

Три механізми, без яких S3 у ролі landing zone неповноцінний.

**Event notifications** — бакет сам повідомляє про зміни, і на цьому будується завантаження, кероване подіями, замість опитування за розкладом.

```
s3:ObjectCreated:*        ──►  Amazon EventBridge  ──►  Step Functions / Lambda / Glue
s3:ObjectRemoved:*        ──►  Amazon SQS          ──►  ваш консюмер
s3:LifecycleTransition    ──►  Amazon SNS
s3:ObjectRestore:Completed
```

Приймачі: SQS, SNS, Lambda і EventBridge. **EventBridge — сучасний вибір за замовчуванням**: багатша фільтрація за вмістом події, маршрутизація в багато приймачів і повтори доставки; SQS доречний, коли потрібна черга з контролем швидкості споживання.

Два застереження, які визначають дизайн споживача:
- **Доставка «щонайменше один раз».** Дублікати трапляються — споживач має бути ідемпотентним.
- **Порядок не гарантується.** Дві події про той самий ключ можуть прийти не в тому порядку, у якому сталися.

**S3 Inventory** — регулярний (щоденний або щотижневий) звіт про всі об'єкти бакета у форматі CSV, ORC або **Parquet**: ключ, розмір, дата, клас зберігання, статус шифрування й реплікації, теги. Це пряма заміна дорогому `LIST` на масштабі: замість сотень тисяч запитів ви читаєте один Parquet-файл звичайним аналітичним движком.

```sql
-- Скільки місця й у якому класі: аналітика по інвентаризації замість LIST
SELECT storage_class,
       count(*)             AS objects,
       sum(size) / 1e12     AS tb,
       count(*) FILTER (WHERE size < 131072) AS tiny_objects
FROM s3_inventory
GROUP BY storage_class;
```

Цей запит — саме те, чим варто перевіряти гіпотези про тіринг з розділу 3.4.

**S3 Batch Operations** — виконання однієї операції над мільярдами об'єктів за маніфестом (тим самим звітом Inventory або власним CSV): змінити клас зберігання, проставити теги, запустити `RestoreObject`, викликати Lambda для кожного об'єкта. З відстеженням прогресу й звітом про помилки.

**Реплікація** — асинхронне копіювання об'єктів у інший бакет: **CRR** (крос-регіональна, для аварійного відновлення й наближення до споживача) або **SRR** (у межах регіону, для ізоляції середовищ чи агрегації логів). Вимагає ввімкненого versioning з обох боків. Опція **Replication Time Control** додає SLA на час доставки.

#### 3.9 Ціноутворення: з чого складається рахунок

1. **Зберігання** — $/ГБ/місяць за класом. Найочевидніша складова, часто не найбільша.
2. **Запити** — окремо за PUT/COPY/POST/LIST (дорожчі) і GET/HEAD (дешевші). Мільйони дрібних файлів роблять цю статтю відчутною.
3. **Переходи lifecycle** — окремий тариф за запит, окремо від зберігання (розділ 3.4).
4. **Отримання даних (retrieval)** — тільки для IA та Glacier-класів, за гігабайт.
5. **Трафік назовні (egress)** — вихід даних із регіону або в інтернет. Трафік між S3 і EC2 **у тому самому регіоні** безкоштовний. Трафік в інший регіон або в інтернет коштує помітно — це і є класичний «vendor lock-in через гравітацію даних».
6. **Моніторинг Intelligent-Tiering** — за об'єкт, незалежно від розміру.

**Незавершені multipart uploads — найтихіший витік бюджету.** Якщо процес почав багаточастинне завантаження й упав, уже залиті частини **залишаються в бакеті й тарифікуються**, але **не з'являються в `LIST Objects`**. Побачити їх можна лише через `ListMultipartUploads` або Storage Lens. У бакеті, куди пише нестабільний конвеєр, за рік так накопичуються терабайти, за які ніхто не розуміє, чому платить.

Лікується одним правилом, яке має бути в **кожному** бакеті з самого створення:

```json
{
  "Rules": [{
    "ID": "abort-incomplete-mpu",
    "Status": "Enabled",
    "Filter": {},
    "AbortIncompleteMultipartUpload": { "DaysAfterInitiation": 7 }
  }]
}
```

Друга така сама пастка — **неточні версії (noncurrent versions)** у бакеті з увімкненим versioning: старі версії живуть вічно, поки ви не додасте `NoncurrentVersionExpiration`.

#### 3.10 Безпека і керування

- **IAM policies** — права на рівні користувача/ролі: хто і які дії може виконувати над якими ARN.
- **Bucket policies** — права на рівні бакета, включно з крос-акаунтним доступом.
- **Block Public Access** — рубильник, що перекриває публічний доступ незалежно від інших політик. За замовчуванням увімкнений; більшість гучних витоків даних сталися через його вимкнення.
- **Шифрування:** SSE-S3 (ключами AWS), SSE-KMS (керовані ключі з аудитом), SSE-C (ваші ключі). Шифрування at-rest увімкнене за замовчуванням.
- **Versioning** — зберігання всіх версій об'єкта під одним ключем. Захист від випадкового видалення/перезапису. Не плутайте з time travel у table format: versioning працює на рівні окремого об'єкта, а не таблиці.
- **Object Lock (WORM)** — заборона видалення на визначений термін, для комплаєнс-вимог.
- **Access Points** — іменовані точки доступу з власною політикою на один бакет: замість однієї величезної bucket policy на всі команди — окрема точка з вузькими правами для кожної.
- **VPC Endpoint (Gateway)** — приватний маршрут до S3 без виходу в публічну мережу; заразом прибирає плату за NAT-трафік.

#### 3.11 S3-сумісні сховища

Оскільки S3 API став стандартом, існує ціла родина сумісних реалізацій:

- **MinIO** — self-hosted, легко запускається одним контейнером; типовий вибір для локальної розробки й on-premise.
- **Ceph RADOS Gateway** — object storage поверх кластера Ceph, поширений в приватних хмарах.
- **Cloudflare R2** — S3-сумісне сховище без плати за egress.
- **Google Cloud Storage** має власний API, але надає S3-сумісний режим (XML API).
- **Azure Blob Storage** — власний API, аналогічна модель (container ≈ bucket, blob ≈ object).

Практична цінність: один код і одна бібліотека (`boto3`, `s3fs`, `pyarrow.fs.S3FileSystem`) працюють і локально, і в проді — різниця лише в endpoint URL та ключах.

Застереження: **сумісність не означає ідентичність**. Умовні записи, class-и зберігання, події та Inventory реалізовані по-різному або відсутні. Код, що спирається на них, треба перевіряти на кожній реалізації окремо.

#### 3.12 HDFS проти S3: чесне порівняння

Тепер, коли розібрані обидві системи, порівняння читається як перелік свідомих компромісів:

| | HDFS | Amazon S3 |
|---|---|---|
| Модель | Розподілена файлова система | Object storage |
| Семантика | Майже POSIX: ієрархія, rename, append | Пласкі ключі, тільки перезапис об'єкта |
| Атомарний rename | Так (метадані на NameNode) | Ні |
| Атомарний compare-and-swap | Ні | Так, з 2024 (`If-Match` / `If-None-Match`) |
| Data locality | Так — головна фішка | Ні, дані завжди по мережі |
| Масштабування метаданих | Обмежене RAM NameNode | Практично необмежене |
| Storage / compute | Зв'язані (диски на тих самих вузлах) | Розділені |
| Тіринг за температурою даних | Вручну (HDFS Storage Policies) | Вбудований, за політиками |
| Ціна | Сервери + диски + адміністрування + електрика | ~$0.023/ГБ/міс, нуль адміністрування |
| Плата, коли простоює | Повна (сервери працюють) | Тільки за зберігання |
| Durability | Реплікація ×3 у межах кластера | 11 дев'яток, мультизональна |
| Latency | Низька (мс) | Висока (десятки мс); Express One Zone — одиниці мс |
| Small files | Убивчі для NameNode | Убивчі для throughput і бюджету запитів |
| Операційна складність | Висока | Мінімальна |

**Практичний висновок.** У хмарі за замовчуванням обирають object storage: не треба тримати кластер живим 24/7 лише заради того, щоб дані були доступні. HDFS залишається доречним у on-premise-датацентрах, де залізо вже куплене, а також у сценаріях, де критична latency або де потрібна POSIX-семантика.

Механізм, що зшиває обидва світи, — **S3A connector**: реалізація інтерфейсу `FileSystem` Hadoop поверх S3 API. Завдяки йому Spark, Hive і решта екосистеми звертаються до `s3a://bucket/path` тим самим кодом, що й до `hdfs://…`. Але за фасадом залишаються всі обмеження object storage — зокрема відсутність атомарного rename, через що потрібні спеціальні **committer'и** (S3A Magic/Directory committer), щоб результат job'а з'являвся атомарно.

#### 3.13 Чого object storage принципово не вміє

Підсумуємо обмеження, які нікуди не зникають і які доведеться обходити на рівні вище:

- **Немає транзакцій над набором об'єктів.** Атомарність доступна лише для одного ключа (умовний запис).
- **Немає атомарного rename/move.** Тільки copy + delete.
- **Немає append та in-place update.** Тільки перезапис цілого об'єкта.
- **Немає блокувань.** Координація можлива лише оптимістична, через `If-Match`.
- **Немає поняття «таблиця», «схема», «партиція».** Тільки байти під ключами.
- **LIST повільний і платний.**

Саме цей список і є технічним завданням для table format.

### 4. Чому «Parquet-файли на S3» — це ще не таблиця

Припустимо, дані лежать у S3 у вигляді:

```
s3://lake/trips/
    year=2024/month=01/part-00000.parquet
    year=2024/month=01/part-00001.parquet
    year=2024/month=02/part-00000.parquet
    ...
```

Поверх цього створено зовнішню таблицю в Hive Metastore. Це **Hive table format** — історично перший спосіб назвати набір файлів таблицею. Його визначення таблиці — це буквально «всі файли під цим префіксом; партиції — це піддиректорії з іменами `key=value`».

Такий підхід називають **data lake**, і в ньому є системні дефекти:

**4.1 Немає атомарності.** Job пише 500 файлів. Читач, що прийшов на 300-му файлі, побачить неповну таблицю — і не дізнається про це. Немає моменту «до» і «після», є розмазаний у часі процес.

**4.2 Немає UPDATE, DELETE, MERGE.** Parquet immutable. Щоб виправити одне значення в одному рядку, треба переписати весь файл, у якому цей рядок лежить, — а потім якось атомарно підмінити старий файл новим, чого S3 не вміє.

**4.3 Немає ізоляції та контролю конкурентності.** Два процеси пишуть в один префікс — обидва «успішні», результат непередбачуваний. Ніхто не отримає помилку конфлікту.

**4.4 Немає історії версій.** Попередній стан не зберігається. Помилковий pipeline перезаписав дані сміттям — відкотитися нема куди.

**4.5 Схема живе в кожному файлі окремо.** Немає єдиного джерела правди про поточну схему таблиці. Додали колонку — старі файли про неї не знають; движки намагаються «злити» схеми з різних файлів (schema merging) з непередбачуваними результатами. Перейменування колонки — операція, що ламає все.

**4.6 Планування запиту вимагає LIST.** Щоб дізнатися, які файли читати, движок мусить перелічити директорії. Для великих таблиць це сотні повільних платних запитів **до початку читання даних**. Плюс: статистика по файлах недоступна на етапі планування — тільки після відкриття footer кожного файлу.

**4.7 Партиціонування — це рядки в шляху.** Партиція `month=01` — просто текст у назві директорії. Щоб pruning спрацював, користувач мусить **знати** про фізичне розкладання і писати `WHERE month = '01'` замість природного `WHERE pickup_datetime >= '2024-01-01'`. Якщо він напише природно — сканується вся таблиця. А змінити схему партиціонування можна лише переписавши таблицю з нуля.

**4.8 Немає обслуговування.** Ніхто не стежить за розміром файлів, ніхто не прибирає залишки невдалих job'ів.

| Дефект | Наслідок у продакшені |
|---|---|
| Немає атомарності | Читачі бачать напівзаписані дані |
| Немає ACID | Конкурентні записи псують таблицю |
| Немає UPDATE/DELETE | GDPR «право на забуття» реалізується переписуванням терабайтів |
| Немає історії | Немає rollback і аудиту |
| Схема в кожному файлі | Крихка еволюція, ризиковані зміни |
| LIST при плануванні | Повільні й дорогі запити |
| Партиції як рядки шляху | Наївний запит сканує все |
| Немає компакції | Small files → деградація throughput |

**Table format** — це шар метаданих, який закриває саме цей список.

### 5. Apache Iceberg

![Apache Iceberg](https://iceberg.apache.org/assets/images/Iceberg-logo-wordmark.png)

#### 5.1 Що це і звідки взялося

Apache Iceberg — **відкрита специфікація формату таблиці** для аналітичних даних великого обсягу. Створений у Netflix (Раян Блю та Дан Вікс, ~2017) як пряма відповідь на болі Hive-таблиць на S3 у масштабі десятків петабайтів. У 2018 переданий до Apache Software Foundation, у 2020 став top-level проєктом.

Найважливіше для правильного розуміння:

> **Iceberg — це не база даних і не движок виконання.** Він не парсить SQL, не будує план запиту, не виконує join'и. Це **специфікація того, як розкласти метадані у файлах**, плюс бібліотеки-реалізації. Якщо і writer, і reader дотримуються специфікації, вони не зобов'язані знати нічого один про одного.

Саме тому одну й ту саму Iceberg-таблицю можуть читати й писати Spark, Trino, Flink, Athena, Snowflake, BigQuery, DuckDB, ClickHouse, PyIceberg — і ніхто нікого не блокує. Це протокол, а не продукт.

#### 5.2 Тришарова архітектура

![Архітектура метаданих Apache Iceberg](https://iceberg.apache.org/assets/images/iceberg-metadata.png)

*Дерево метаданих Iceberg: catalog → metadata file → manifest list (snapshot) → manifest files → data files. Джерело: [Apache Iceberg Spec](https://iceberg.apache.org/spec/)*

Iceberg організований у три шари:

```
┌─── CATALOG LAYER ────────────────────────────────────────┐
│  Glue / Hive Metastore / REST / JDBC / Nessie            │
│  Зберігає РІВНО ОДНЕ: вказівник на поточний              │
│  metadata-файл таблиці. Оновлення вказівника —           │
│  єдина операція, що має бути атомарною.                  │
└──────────────────────┬───────────────────────────────────┘
                       ▼
┌─── METADATA LAYER (файли в object storage) ──────────────┐
│  v3.metadata.json                                        │
│     ├─ поточна схема (+ історія схем)                    │
│     ├─ partition specs (+ історія)                       │
│     ├─ sort orders, властивості таблиці                  │
│     └─ список snapshot-ів + ID поточного                 │
│                                                          │
│  snap-8472…-1.avro   ← manifest list (один на snapshot)  │
│     └─ перелік manifest-файлів + агрегована статистика   │
│        по партиціях (partition value ranges)             │
│                                                          │
│  a3f1…-m0.avro       ← manifest file                     │
│     └─ перелік data-файлів; для кожного:                 │
│        шлях, формат, розмір, кількість рядків,           │
│        значення партиції, min/max/null-count             │
│        по кожній колонці                                 │
└──────────────────────┬───────────────────────────────────┘
                       ▼
┌─── DATA LAYER ───────────────────────────────────────────┐
│  data/…/00000-0-a1b2.parquet   ← звичайний Parquet       │
│  data/…/00001-0-c3d4.parquet                             │
│  data/…/delete-…-eq.parquet    ← delete files (v2+)      │
└──────────────────────────────────────────────────────────┘
```

**Розберемо кожен рівень.**

**Catalog** — реєстр таблиць. Його єдина принципова функція: для кожної таблиці зберігати **поточний metadata pointer** і вміти оновити його **атомарно з перевіркою** (compare-and-swap: «зміни вказівник з A на B, але тільки якщо він досі A»). Уся транзакційність Iceberg зводиться до цієї однієї атомарної операції. Каталог не зберігає ні схеми, ні статистики, ні переліку файлів.

**Metadata file (`*.metadata.json`)** — корінь опису таблиці. Містить UUID таблиці, повну історію схем із числовими ID колонок, історію partition specs, sort orders, властивості (`write.format.default`, `write.target-file-size-bytes` тощо), журнал snapshot-ів і ID поточного. Кожен commit створює **новий** metadata-файл; старі залишаються.

**Snapshot** — повний, самодостатній, незмінний опис стану таблиці в конкретний момент. Не «дельта», а саме повний стан: набір усіх файлів, які складають таблицю. Реалізований як **manifest list**.

**Manifest list (`snap-*.avro`)** — перелік manifest-файлів, що входять до snapshot. Для кожного manifest зберігається агрегована інформація: діапазони значень партицій, кількість доданих/наявних/видалених файлів. Це дозволяє відкинути цілий manifest, не читаючи його.

**Manifest file (`*.avro`)** — перелік data-файлів із детальними метаданими кожного: шлях, формат, розмір у байтах, кількість рядків, значення партиції, а головне — **колонкова статистика**: `lower_bounds`, `upper_bounds`, `null_value_counts`, `nan_value_counts` по кожній колонці.

**Data files** — звичайні Parquet (або ORC/Avro) файли. Iceberg їх не змінює і не вигадує власного бінарного формату.

#### 5.3 Як виглядає планування запиту

Порівняйте два сценарії для запиту `WHERE pickup_datetime BETWEEN '2024-01-15' AND '2024-01-16' AND fare_amount > 100`.

**Hive-таблиця:**
```
LIST s3://lake/trips/                     → 1 запит
LIST кожної з 24 партицій                 → 24+ запитів
LIST файлів у кожній партиції             → сотні запитів
відкрити footer кожного файлу зі списку   → тисячі range GET
→ і тільки тепер починається читання даних
```

**Iceberg-таблиця:**
```
catalog: дай metadata pointer             → 1 запит
GET metadata.json                         → 1 запит (KB)
GET manifest list                         → 1 запит; за діапазонами партицій
                                            відкидаємо непотрібні manifest-и
GET 1–2 manifest файли                    → за min/max статистикою
                                            відкидаємо файли, де
                                            max(fare_amount) <= 100
→ отримали точний список з 3 файлів і читаємо тільки їх
```

Планування перетворилося з тисяч запитів на одиниці. І — ключове — **жодного LIST**. Iceberg завжди знає точний перелік своїх файлів; він ніколи не питає сховище «що там лежить».

Це також вирішує проблему «сторонніх» файлів: якщо хтось скине зайвий Parquet у директорію даних, Iceberg його просто проігнорує, бо його немає в manifest. У Hive-таблиці такий файл потрапив би у вибірку.

#### 5.4 Commit protocol: як з'являються ACID на сховищі без транзакцій

Це центральний механізм, який варто зрозуміти до кінця.

```
1. Writer читає поточний metadata pointer з каталогу        → base = v3
2. Writer записує нові data-файли в object storage.
   Вони ще нікому не видимі — на них ніхто не посилається.
3. Writer записує новий manifest, новий manifest list
   (= новий snapshot) і новий metadata-файл v4.
4. Writer виконує в каталозі атомарний compare-and-swap:
      "заміни вказівник з v3 на v4"
   ├─ Успіх    → транзакція зафіксована. Усі нові читачі
   │             миттєво бачать новий стан цілком.
   └─ Невдача  → хтось інший уже змінив вказівник на v4'.
                 Writer перечитує новий стан, перевіряє,
                 чи його зміни сумісні, і повторює спробу.
```

Це **optimistic concurrency control**: писати можна паралельно без блокувань, конфлікт виявляється лише в момент фіксації. Модель ізоляції — **serializable** або **snapshot isolation** (налаштовується).

Три властивості, що звідси випливають:

- **Атомарність.** Перехід між станами таблиці — це одна зміна одного вказівника. Читач бачить або повний старий стан, або повний новий. «Половини» не існує в принципі.
- **Ізоляція.** Читач, що почав скан на snapshot v3, дочитає його до кінця на v3, навіть якщо за цей час зафіксувалося п'ять нових комітів. Файли v3 нікуди не поділись.
- **Довговічність.** Дані вже в object storage з його одинадцятьма дев'ятками.

Зверніть увагу, наскільки скромна вимога до сховища: від нього потрібен лише запис файлів. Уся транзакційність винесена в **одну атомарну операцію** — compare-and-swap над одним вказівником.

**Де саме виконується цей CAS — і чому це змінилося.** Історично об'єктні сховища такої операції не мали (розділ 3.6), тому її доводилося виносити у зовнішню систему: Hive Metastore, Glue, реляційну БД під REST-каталогом. Звідси й правило, що Hadoop Catalog не можна використовувати на S3 — він покладався на атомарний rename, якого там немає.

Після появи умовних записів (`If-None-Match`, `If-Match`) картина змінилася: сам S3 надає потрібний примітив, і каталог може зберігати вказівник як звичайний об'єкт, оновлюючи його умовним записом. Це прибирає останню технічну причину тримати окрему базу під метадані. На практиці зовнішні каталоги все одно залишаються — але тепер уже заради інших речей: авторизації, discovery, аудиту й спільної видимості таблиць між движками.

#### 5.5 Time travel і rollback

Оскільки старі snapshot-и та їхні файли не видаляються при коміті, минулі стани таблиці залишаються повністю читабельними.

```sql
-- За ідентифікатором snapshot
SELECT count(*) FROM db.trips FOR VERSION AS OF 8472936152847;

-- За часовою міткою
SELECT count(*) FROM db.trips FOR TIMESTAMP AS OF TIMESTAMP '2026-08-01 09:00:00';

-- Порівняти два стани — знайти, що змінилося
SELECT count(*) FROM db.trips FOR VERSION AS OF 8472936152847
EXCEPT
SELECT count(*) FROM db.trips FOR VERSION AS OF 9183746251938;
```

Крім читання, доступний **rollback** — повернення поточного вказівника на старий snapshot:

```sql
CALL catalog.system.rollback_to_snapshot('db.trips', 8472936152847);
CALL catalog.system.set_current_snapshot('db.trips', 8472936152847);
```

Rollback — це знову ж таки просто зміна вказівника, тобто операція за мілісекунди незалежно від обсягу таблиці.

Типові застосування: аудит («який був стан на момент побудови звіту?»), відлагодження («у якому саме коміті з'явилися некоректні значення?»), аварійне відновлення («pipeline записав сміття — відкотились, виправили код, перезапустили»), відтворюваність ML («навчи модель рівно на тих даних, що й місяць тому»).

**Обмеження:** глибина time travel визначається політикою утримання snapshot-ів (`history.expire.max-snapshot-age-ms`, за замовчуванням 5 днів). Після `expire_snapshots` старі стани зникають безповоротно.

#### 5.6 Schema evolution

Iceberg відстежує колонки за **унікальним числовим ID**, а не за іменем чи позицією в файлі. ID присвоюється при створенні колонки і ніколи не змінюється й не перевикористовується. Читаючи Parquet-файл, Iceberg зіставляє колонки за ID, а не за порядком.

З цього безпосередньо випливають гарантії:

| Операція | Підтримка | Що фізично відбувається |
|---|---|---|
| `ADD COLUMN` | Безпечна | Новий ID у метаданих. Старі файли не чіпаються; для них колонка читається як NULL |
| `DROP COLUMN` | Безпечна | ID позначається видаленим. Дані у файлах залишаються, просто не читаються |
| `RENAME COLUMN` | Безпечна | Змінюється лише ім'я в метаданих; ID той самий |
| `REORDER / MOVE` | Безпечна | Порядок — властивість схеми, не файлу |
| Розширення типу (`int`→`long`, `float`→`double`, збільшення precision у `decimal`) | Безпечна | Читач приводить тип на льоту |
| Звуження типу (`long`→`int`) | Заборонена | Втрата даних; потрібен явний перезапис |
| Несумісна зміна (`string`→`int`) | Заборонена | Потрібен явний перезапис |

Всі безпечні операції — це зміни **тільки метаданих**. Вони виконуються за мілісекунди й нічого не коштують незалежно від розміру таблиці.

Порівняйте з Hive-таблицею, де колонки зіставляються за позицією: там `DROP COLUMN` посередині схеми мовчки зсуває всі наступні колонки й перетворює дані на кашу.

Окремо: **column ID вирішують проблему повторного використання імен**. Якщо видалити колонку `status` і потім додати нову колонку з тим самим іменем `status`, Iceberg дасть їй новий ID — і старі дані не «просочаться» в нову колонку.

#### 5.7 Партиціонування: hidden partitioning і partition evolution

Це одна з найпомітніших переваг Iceberg над Hive-підходом.

**Як було в Hive.** Щоб партиціонувати по місяцях, у таблицю додавали окрему фізичну колонку `month`, яку **писач мусив заповнювати вручну**, а **читач мусив явно згадувати у WHERE**:

```sql
-- працює, сканує одну партицію
SELECT * FROM trips WHERE month = '2024-01' AND pickup_datetime > '2024-01-15';

-- логічно те саме, але сканує ВСЮ таблицю
SELECT * FROM trips WHERE pickup_datetime > '2024-01-15';
```

Користувач зобов'язаний знати фізичне розкладання даних. Забув — отримав повний скан і рахунок на $200. Плюс колонка `month` дублює інформацію з `pickup_datetime` і може з нею розійтися.

**Hidden partitioning в Iceberg.** Партиція описується як **трансформація наявної колонки**:

```sql
CREATE TABLE db.trips (
    trip_id      bigint,
    pickup_ts    timestamp,
    fare_amount  double,
    zone_id      int
)
USING iceberg
PARTITIONED BY (month(pickup_ts));
```

Ніякої додаткової колонки. Iceberg сам обчислює значення партиції при записі та сам застосовує ту саму трансформацію до предикатів при читанні. Тому природний запит:

```sql
SELECT * FROM db.trips WHERE pickup_ts >= '2024-01-15' AND pickup_ts < '2024-01-16';
```

...автоматично звужується до партиції `2024-01`. Користувачу **не треба знати** ні про партиціонування, ні про його схему.

**Доступні трансформації:**

| Трансформація | Опис | Приклад значення партиції |
|---|---|---|
| `identity(col)` | Саме значення | `zone_id=132` |
| `year(ts)` / `month(ts)` / `day(ts)` / `hour(ts)` | Обрізання дати до періоду | `pickup_ts_month=2024-01` |
| `bucket(N, col)` | Хеш за модулем N — рівномірний розподіл | `zone_id_bucket=7` |
| `truncate(W, col)` | Обрізання рядка до W символів або числа до кратності W | `name_trunc=Ann` |
| `void(col)` | Завжди NULL — використовується для «вимкнення» партиціонування | — |

`bucket` особливо цінний для колонок з високою кардинальністю (наприклад, `user_id`): identity-партиціонування дало б мільйони крихітних партицій, а `bucket(64, user_id)` дасть 64 рівномірні.

**Partition evolution** — можливість змінити схему партиціонування **без перезапису наявних даних**:

```sql
ALTER TABLE db.trips REPLACE PARTITION FIELD month(pickup_ts) WITH day(pickup_ts);
```

Iceberg зберігає **історію partition specs** і фіксує в кожному manifest, за якою специфікацією записані його файли. Старі дані залишаються розкладеними по місяцях, нові пишуться по днях, а запит коректно планується по обох наборах одночасно. У Hive така зміна означала б повне переписування таблиці.

#### 5.8 Pruning: як саме відкидаються зайві дані

Iceberg відсіює непотрібне на чотирьох рівнях, зверху вниз:

1. **Рівень manifest list** — за агрегованими діапазонами партицій відкидаються цілі manifest-и.
2. **Рівень manifest** — за значенням партиції кожного файлу відкидаються цілі файли.
3. **Рівень статистики файлу** — за `lower_bounds`/`upper_bounds` кожної колонки відкидаються файли, які не можуть містити рядків, що задовольняють предикат. Наприклад, для `WHERE fare_amount > 100` файл із `upper_bound(fare_amount) = 87` не відкривається взагалі.
4. **Рівень Parquet** — усередині файлу за статистикою row group і сторінок, а також колонковим projection pushdown, читаються тільки потрібні байти.

Кроки 1–3 виконуються **не торкаючись data-файлів** — лише за метаданими. Це принципова відмінність від Hive, де для будь-якої фільтрації за колонкою треба відкрити footer кожного файлу.

**Sort order** підсилює крок 3. Якщо таблиця відсортована за `fare_amount`, діапазони min/max по файлах не перетинаються, і pruning стає майже ідеальним. Якщо дані розкидані випадково — кожен файл має діапазон «від мінімуму до максимуму» і pruning не працює. Iceberg дозволяє задати `WRITE ORDERED BY`, у тому числі **z-order** для кількох колонок одночасно.

#### 5.9 Row-level операції: copy-on-write vs merge-on-read

Parquet immutable — але Iceberg усе одно надає `UPDATE`, `DELETE` і `MERGE INTO`. Реалізовано це двома різними стратегіями, і вибір між ними — важливе інженерне рішення.

**Copy-on-write (COW)** — стратегія за замовчуванням.
Зачеплені data-файли **перезаписуються цілком** без видалених/зі зміненими рядками; новий snapshot посилається на нові файли замість старих.
- Записи повільні: щоб видалити 10 рядків, можна переписати гігабайт.
- Читання максимально швидке: жодних додаткових файлів, звичайний Parquet.
- Доречно, коли записів мало, а читань багато (класичний batch-warehouse).

**Merge-on-read (MOR)**.
Замість перезапису пишеться маленький **delete file**, що позначає видалені рядки. При читанні движок зчитує data-файли й накладає на них delete-файли.
- Записи швидкі: пишеться кілограм замість тонни.
- Читання повільніші: треба зчитати й застосувати delete-файли.
- Доречно для частих дрібних змін, CDC, streaming upsert.

```sql
ALTER TABLE db.trips SET TBLPROPERTIES (
  'write.delete.mode'  = 'merge-on-read',
  'write.update.mode'  = 'merge-on-read',
  'write.merge.mode'   = 'merge-on-read'
);
```

Delete-файли бувають двох типів:
- **Positional deletes** — «у файлі X видалені рядки з позиціями 5, 17, 402». Швидко застосовуються.
- **Equality deletes** — «видалені всі рядки, де `trip_id = 12345`». Не треба знати, у якому файлі рядок; зручно для streaming-writer'ів, але дорожче при читанні.

У **специфікації v3** (2024–2025) positional deletes замінені на **deletion vectors** — компактне бітове представлення видалених позицій, яке швидше застосовувати й дешевше зберігати.

**Наслідок для експлуатації:** MOR накопичує delete-файли, і читання поступово деградує. Регулярна компакція обов'язкова — вона «матеріалізує» видалення у нові чисті data-файли.

#### 5.10 Обслуговування таблиці

Lakehouse — не «поставив і забув». Без регулярного обслуговування Iceberg-таблиця деградує так само, як будь-яка інша база даних без vacuum. Чотири процедури, які мають бути в розкладі:

**1. Компакція data-файлів (`rewrite_data_files`)**
```sql
CALL catalog.system.rewrite_data_files(
    table => 'db.trips',
    strategy => 'binpack',
    options => map('target-file-size-bytes', '536870912')  -- 512 МБ
);
```
Об'єднує дрібні файли у файли цільового розміру (bin-packing) або перезаписує їх у відсортованому порядку (`sort`, `zorder`), одночасно матеріалізуючи delete-файли. Лікує small files problem — головну хворобу потокових і частих записів.

**2. Видалення старих snapshot-ів (`expire_snapshots`)**
```sql
CALL catalog.system.expire_snapshots(
    table => 'db.trips',
    older_than => TIMESTAMP '2026-07-01 00:00:00',
    retain_last => 10
);
```
Видаляє snapshot-и старші за поріг **разом з їхніми файлами, на які більше ніхто не посилається**. Це те, що звільняє місце. Прямий компроміс: чим довше утримання, тим глибший time travel і тим більший рахунок за S3.

**3. Видалення файлів-сиріт (`remove_orphan_files`)**
```sql
CALL catalog.system.remove_orphan_files(
    table => 'db.trips',
    older_than => TIMESTAMP '2026-08-01 00:00:00'
);
```
Job впав посеред запису — data-файли вже в S3, але коміт не відбувся, тож у метаданих їх немає. Такі файли не видаляються ніколи, бо ніхто про них не знає. Процедура звіряє вміст сховища з метаданими і прибирає різницю. Виконувати з великим порогом часу, щоб не видалити файли активного запису.

**4. Перезапис маніфестів (`rewrite_manifests`)**
```sql
CALL catalog.system.rewrite_manifests('db.trips');
```
Після тисяч дрібних комітів манифестів стає багато й вони фрагментовані — планування запиту сповільнюється. Процедура перепаковує їх, групуючи файли за партиціями.

#### 5.11 Каталоги: варіанти реалізації

Каталог — єдиний компонент, що вимагає зовнішньої системи. Варіанти:

| Каталог | Де застосовується | Особливості |
|---|---|---|
| **Hive Metastore** | Класичні on-prem кластери | Найстаріший; вимагає RDBMS під собою |
| **AWS Glue Data Catalog** | AWS-стек | Managed, інтегрований з Athena, EMR, Redshift Spectrum |
| **REST Catalog** | Сучасний стандарт | Специфікація HTTP API; будь-яка реалізація за нею (Polaris, Lakekeeper, Unity Catalog, Gravitino) |
| **JDBC / SQL Catalog** | Розробка, невеликі інсталяції | Вказівники в PostgreSQL/MySQL/SQLite |
| **Hadoop Catalog** | Тільки для файлових систем із атомарним rename | Вказівник — файл `version-hint.text` у сховищі. **Не рекомендується на S3** |
| **Project Nessie** | Git-подібний workflow | Гілки й теги для даних, крос-табличні транзакції |
| **Amazon S3 Tables** | AWS, керований варіант | Iceberg як вбудований примітив бакета; компакція й expire автоматичні |

**Чому Hadoop Catalog небезпечний на object storage:** він покладається на атомарний rename для оновлення вказівника — тобто саме на ту операцію, якої в S3 немає. Для локальної файлової системи це прийнятно, для проду в хмарі — ні.

**REST Catalog** сьогодні є напрямком, у який рухається екосистема: він відв'язує движок від конкретної реалізації каталогу і дозволяє централізувати авторизацію й аудит.

#### 5.12 Версії специфікації

- **v1** — базовий формат: тільки додавання й повний перезапис файлів. Без row-level deletes.
- **v2** — додано delete files (positional та equality), тобто повноцінні MOR-операції `UPDATE`/`DELETE`/`MERGE`. Найпоширеніша версія в продакшені.
- **v3** — deletion vectors замість positional deletes, нові типи даних (`variant` для напівструктурованих даних, `geometry`/`geography`), row lineage (відстеження походження рядка), default-значення колонок.

Специфікація версіонується явно, і кожен движок декларує, які версії підтримує.

### 6. Iceberg, Delta Lake і Apache Hudi

Три відкриті table formats вирішують одну проблему різними шляхами.

| | **Apache Iceberg** | **Delta Lake** | **Apache Hudi** |
|---|---|---|---|
| Походження | Netflix, 2017 | Databricks, 2019 | Uber, 2016 |
| Формат даних | Parquet / ORC / Avro | Parquet | Parquet / ORC |
| Метадані | Дерево: metadata.json → manifest list → manifests (Avro) | Впорядкований лог JSON у `_delta_log/` + періодичні Parquet-checkpoint | Timeline у `.hoodie/` + індекс записів |
| Модель конкурентності | Optimistic CC через compare-and-swap у каталозі | Optimistic CC через атомарне створення наступного файлу лога | Timeline-based, підтримка блокувань |
| Сильна сторона | Мультиенджинність, partition evolution, hidden partitioning | Глибока інтеграція зі Spark/Databricks, зрілий streaming | Швидкі upsert-и та інкрементальні запити завдяки індексу |
| Row-level | COW + MOR (v2/v3) | COW + deletion vectors | COW + MOR (історично перший) |
| Каталог | Будь-який (Glue, REST, Hive, JDBC, Nessie) | Часто Unity Catalog, але працює й без каталогу | Hive Metastore / власний |
| Екосистема | Spark, Trino, Flink, Athena, Snowflake, BigQuery, DuckDB, ClickHouse, PyIceberg | Насамперед Spark; delta-rs і connector-и для інших | Насамперед Spark і Flink |

**Тенденція ринку.** Iceberg став фактичним стандартом для «нейтральних» платформ: його нативно підтримують AWS (S3 Tables, Athena, Glue), Snowflake, Google BigQuery, Confluent, Cloudera. Delta Lake домінує там, де стек побудований навколо Databricks; проєкт Delta UniForm дозволяє публікувати Delta-таблицю ще й з Iceberg-метаданими, щоб її читали сторонні движки. Hudi займає нішу з дуже інтенсивними upsert-ами.

Практичний висновок: обирайте **Iceberg**, якщо важлива незалежність від вендора і мультиенджинність; **Delta**, якщо ви живете в Databricks; **Hudi**, якщо профіль навантаження — постійні точкові оновлення.

### 7. Lakehouse як архітектурна модель

Зберемо все докупи. Історично існували дві парадигми:

**Data Warehouse** (з 1990-х): структуровані дані, жорстка схема (schema-on-write), ACID, SQL, оптимізатор, BI. Ціна — дорого, propriety-формат, дані «замкнені» всередині системи, погано працює з напівструктурованими даними й ML.

**Data Lake** (з 2010-х): будь-які дані в відкритих форматах на дешевому сховищі, schema-on-read, доступ будь-яким інструментом. Ціна — немає транзакцій, немає гарантій якості, легко перетворюється на «data swamp».

**Lakehouse** — спроба взяти сильні сторони обох:

```
┌──────────────────────────────────────────────────────────┐
│  Споживачі:  BI  │  SQL ad-hoc  │  Spark ETL  │  ML      │
├──────────────────────────────────────────────────────────┤
│  COMPUTE (незалежно масштабується, платимо за час)       │
│  Spark │ Trino │ Athena │ Flink │ DuckDB │ Snowflake     │
├──────────────────────────────────────────────────────────┤
│  CATALOG:  Glue │ REST │ Hive │ Nessie                   │
│            (метадані, авторизація, discovery)            │
├──────────────────────────────────────────────────────────┤
│  TABLE FORMAT:  Iceberg / Delta / Hudi                   │
│  ACID · snapshots · schema evolution · pruning           │
├──────────────────────────────────────────────────────────┤
│  FILE FORMAT:  Parquet / ORC / Avro                      │
├──────────────────────────────────────────────────────────┤
│  STORAGE (незалежно масштабується, платимо за обсяг)     │
│  S3 / GCS / Azure Blob / MinIO / HDFS                    │
└──────────────────────────────────────────────────────────┘
```

Кожен шар змінюється незалежно від інших. Можна замінити Spark на Trino, не торкнувшись даних. Можна перевести бакет у інший клас зберігання, не змінюючи жодного запиту. Можна дати трьом командам три різні движки над однією таблицею.

Це і є головна архітектурна цінність: **дані перестають бути заручником обчислювального движка**.

## Ключові терміни

| Термін | Визначення |
|---|---|
| **Block storage** | Сховище, що адресує дані блоками фіксованого розміру; дозволяє in-place update. EBS, SSD |
| **File storage / NAS** | Мережева файлова система з POSIX-семантикою для багатьох клієнтів. EFS, NFS, SMB |
| **Object storage** | Пласкій namespace об'єктів (ключ + байти + метадані) з HTTP API. S3, GCS, MinIO |
| **Bucket / Key / Object** | Контейнер / повний шлях-рядок / одиниця зберігання в object storage |
| **Range GET** | Читання діапазону байтів об'єкта; основа ефективної роботи з Parquet на S3 |
| **Multipart upload** | Паралельне завантаження великого об'єкта частинами |
| **Незавершений multipart upload** | Залиті частини невдалого завантаження: тарифікуються, але не видимі в `LIST`; прибираються правилом `AbortIncompleteMultipartUpload` |
| **Storage class** | Тариф зберігання з різним балансом ціни зберігання, доступу й затримки |
| **Тіринг** | Переміщення даних у дешевші класи в міру «охолодження»; вигідний для великих об'єктів із довгим життям |
| **Lifecycle policy** | Правило автоматичного переходу, видалення або прибирання версій за віком, розміром чи тегом |
| **Водоспад переходів** | Переходи між класами лише в один бік; повернення вимагає `RestoreObject` + `CopyObject` |
| **Мінімальний оплачуваний розмір** | 128 КБ для IA та Glacier Instant: менший об'єкт тарифікується як 128 КБ |
| **Мінімальний термін зберігання** | 30 днів (IA), 90 (Glacier IR/FR), 180 (Deep Archive); утримується навіть при ранньому видаленні |
| **Накладні витрати архіву** | 40 КБ метаданих на кожен об'єкт у Glacier FR / Deep Archive |
| **S3 Intelligent-Tiering** | Автоматичний тіринг за фактичним доступом без плати за отримання; об'єкти < 128 КБ не переміщуються |
| **S3 Express One Zone** | Клас із затримкою в одиниці мілісекунд у межах однієї зони; живе в directory buckets зі справжніми директоріями |
| **Storage Class Analysis / Storage Lens** | Аналіз патернів доступу / панель розподілу обсягу — інструменти, якими обґрунтовують правила тірингу |
| **Strong read-after-write consistency** | Гарантія, що читання після успішного запису бачить нові дані (для одного об'єкта) |
| **Умовні записи (`If-None-Match` / `If-Match`)** | Write-if-absent і compare-and-swap на рівні одного ключа; примітив, на якому будується оптимістична конкурентність |
| **Event notifications** | Повідомлення про зміни в бакеті у SQS / SNS / Lambda / EventBridge; доставка «щонайменше раз», порядок не гарантується |
| **S3 Inventory** | Регулярний звіт про всі об'єкти у Parquet/CSV — заміна дорогому `LIST` на масштабі |
| **S3 Batch Operations** | Виконання однієї операції над мільярдами об'єктів за маніфестом |
| **Реплікація CRR / SRR** | Асинхронне копіювання в інший регіон / у межах регіону; вимагає versioning з обох боків |
| **Access Point** | Іменована точка доступу до бакета з власною вузькою політикою |
| **Durability / Availability** | Ймовірність не втратити дані / ймовірність, що сервіс відповідає |
| **HDFS** | Розподілена файлова система Hadoop: блоки, реплікація, master/slave |
| **NameNode** | Master HDFS: тримає namespace і мапу блоків у RAM. Дані через нього не проходять |
| **DataNode** | Worker HDFS: фізично зберігає блоки, шле heartbeat і block report |
| **fsimage / edit log** | Знімок метаданих на диску / журнал змін після знімка |
| **Block (HDFS)** | Одиниця розбиття файлу, за замовчуванням 128 МБ |
| **Replication factor** | Кількість копій кожного блоку, за замовчуванням 3 |
| **Rack awareness** | Розміщення реплік із урахуванням стійок для стійкості до відмови цілої стійки |
| **Erasure coding** | Альтернатива реплікації: блоки парності замість повних копій; менший надлишок |
| **HDFS Federation / HA** | Кілька незалежних namespace / active+standby NameNode із JournalNode і ZooKeeper |
| **Data locality** | Запуск обчислення на вузлі, де фізично лежать дані |
| **S3A connector** | Реалізація Hadoop FileSystem поверх S3 API |
| **Small files problem** | Деградація через велику кількість дрібних файлів: RAM NameNode у HDFS, throughput і вартість запитів у S3 |
| **Table format** | Специфікація метаданих поверх файлів, що додає таблиці ACID, версійність, еволюцію схеми |
| **Apache Iceberg** | Відкритий table format: catalog → metadata.json → manifest list → manifest → data files |
| **Catalog** | Реєстр таблиць; зберігає атомарно оновлюваний вказівник на поточний metadata-файл |
| **Metadata file** | Корінь опису таблиці: схеми, partition specs, sort orders, журнал snapshot-ів |
| **Snapshot** | Повний незмінний стан таблиці в момент коміту; основа MVCC і time travel |
| **Manifest list** | Перелік manifest-файлів snapshot-а з агрегованою статистикою по партиціях |
| **Manifest file** | Перелік data-файлів із колонковою статистикою (min/max/null counts) |
| **Optimistic concurrency** | Паралельний запис без блокувань; конфлікт виявляється при compare-and-swap коміту |
| **Time travel** | Читання минулого стану таблиці за snapshot ID або timestamp |
| **Rollback** | Повернення поточного вказівника таблиці на попередній snapshot |
| **Schema evolution** | Зміна схеми без перезапису даних; колонки відстежуються за числовим ID |
| **Hidden partitioning** | Партиція як трансформація колонки; запит пишеться природно, pruning автоматичний |
| **Partition transform** | `identity`, `year/month/day/hour`, `bucket(N)`, `truncate(W)`, `void` |
| **Partition evolution** | Зміна схеми партиціонування без перезапису наявних даних |
| **Partition pruning / file pruning** | Відкидання партицій і окремих файлів на етапі планування за метаданими |
| **Copy-on-write (COW)** | Row-level зміни через перезапис зачеплених файлів: повільний запис, швидке читання |
| **Merge-on-read (MOR)** | Row-level зміни через delete-файли: швидкий запис, повільніше читання |
| **Delete file** | Positional або equality файл із позначками видалених рядків (Iceberg v2) |
| **Deletion vector** | Компактне бітове представлення видалених рядків (Iceberg v3, Delta) |
| **Compaction / rewrite_data_files** | Об'єднання дрібних файлів у великі й матеріалізація delete-файлів |
| **expire_snapshots** | Видалення старих snapshot-ів разом із файлами, на які ніхто не посилається |
| **remove_orphan_files** | Прибирання файлів, що залишилися від невдалих job-ів і відсутні в метаданих |
| **REST Catalog** | Стандартизований HTTP API каталогу Iceberg, незалежний від реалізації |
| **Amazon S3 Tables** | Тип S3-бакета з вбудованим керованим Iceberg і автоматичним обслуговуванням |
| **Delta Lake / Apache Hudi** | Альтернативні table formats від Databricks і Uber |
| **Lakehouse** | Архітектура: відкриті формати на object storage + table format, що дає warehouse-семантику |
| **Separation of storage and compute** | Незалежне масштабування й оплата сховища та обчислень |
