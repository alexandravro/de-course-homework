# Заняття 15. Оптимізація виконання завдань в Apache Spark

## Про що це заняття

Spark-джоб, що працює чотири години замість двадцяти хвилин, майже ніколи не «повільний взагалі». Він повільний з конкретної причини: непотрібний shuffle, перекошений розподіл ключів, дані, що не вміщаються в пам'ять і скидаються на диск, тисячі дрібних файлів, або Python-функція посеред оптимізованого плану.

Це заняття — систематичний розбір цих причин. Не набір порад «поставте ось цей параметр», а **діагностичний метод**: за яким симптомом який діагноз, як його підтвердити за фактичними метриками, і які важелі впливу існують у кожному випадку.

Структура матеріалу відповідає порядку роботи інженера: спочатку симптоми й інструменти вимірювання, потім чотири класи проблем (spill, skew, shuffle, storage), потім механізми, що частину з них розв'язують автоматично (AQE), і нарешті ручні важелі, модель пам'яті executor-а та конфігурація.

Ключовий принцип, який варто засвоїти до всього іншого: **не оптимізуйте наосліп**. Кожна зміна має спиратися на конкретну метрику, а не на припущення. Найпоширеніша помилка початківця — розставити `cache()` і збільшити `spark.executor.memory`, не подивившись, у чому насправді проблема.

**Практика:** `code/lesson_15.ipynb` — 12 прикладів, кожен параметр показано двома сусідніми клітинками з різними значеннями (клітинка → перевірка числа й вкладки Spark UI → наступна клітинка). Приклади перегукуються з розділами 4–12 нижче.

## Що треба знати заздалегідь

- Архітектура Spark: driver, executor, cluster manager, партиції.
- Модель виконання: job → stage → task, narrow і wide залежності, shuffle.
- Catalyst: логічний план, фізичний план, стратегії join.
- DataFrame API і читання `explain()`.

Модель пам'яті executor-а й конфігурація Spark докладно розібрані в розділах 11–12 — попереднього знання не потрібно.

## Основний матеріал

### 1. Метод: від симптому до діагнозу

#### 1.1 Таблиця симптомів

| Симптом | Найімовірніша причина | Де підтвердити |
|---|---|---|
| Один task працює в десятки разів довше за медіанний | **Skew** | Stage detail → розподіл Duration по task-ах |
| Ненульові Spill (memory) / Spill (disk) | **Брак execution-пам'яті** | Stage detail → колонки Spill |
| Величезні Shuffle Read / Write | **Зайвий або невиправдано широкий shuffle** | Вкладка Stages |
| Тисячі task-ів, кожен по 50 мс | **Занадто багато партицій** | Stage detail → Duration, кількість task-ів |
| Кілька task-ів по 20 хвилин, ядра простоюють | **Занадто мало партицій** | Executors → Active Tasks |
| GC Time > 10 % Task Time | **Замало пам'яті або надто великі executor-и** | Вкладка Executors |
| Довгий етап читання, малий обсяг корисних даних | **Не спрацював pruning** | SQL → метрики scan; план → `PushedFilters` |
| Job запускається кілька разів на ті самі дані | **Немає кешу там, де він потрібен** | Вкладка Jobs → кількість job-ів |
| Багато часу на «планування» до старту task-ів | **Роздутий план** (сотні `withColumn`, глибокий DAG) | Час між submit і першим task |
| Стадія запису триває довше за обчислення | **Small files problem** або `coalesce(1)` | Файловий вивід; кількість task-ів у write-stage |

#### 1.2 Порядок дій

1. **Знайти вузьке місце.** Вкладка Jobs → який job довгий; вкладка Stages → який stage у ньому довгий. Оптимізувати те, що займає 3 % часу, безглуздо.
2. **Класифікувати проблему** за таблицею вище на рівні stage.
3. **Підтвердити гіпотезу метрикою.** Не «здається, тут skew», а «медіана 4 с, максимум 27 хв».
4. **Застосувати важіль.**
5. **Виміряти повторно.** Порівняти ті самі метрики, а не тільки загальний час.

### 3. Spill: коли не вистачає пам'яті

#### 3.1 Що це

**Spill** — скидання проміжних структур обчислення на локальний диск, коли execution-пам'яті executor-а не вистачає. Job не падає, але швидкість деградує: до вартості обчислень додаються серіалізація, запис на диск і зворотне читання.

Виникає під час операцій, що вимагають накопичення стану в пам'яті: сортування, хеш-агрегація, побудова хеш-таблиці для join-у, віконні функції.

У Spark UI видно як дві метрики: **Spill (memory)** — скільки даних було в пам'яті до скидання, **Spill (disk)** — скільки фактично записано (менше через серіалізацію й стиснення).

#### 3.2 Причини та важелі

| Причина | Важіль |
|---|---|
| Партиції занадто великі | Збільшити кількість партицій: `repartition(n)` або `spark.sql.shuffle.partitions` |
| Перекіс — одна партиція гігантська | Лікувати skew (розділ 4), а не додавати пам'ять |
| Замало пам'яті на executor | Збільшити `spark.executor.memory` |
| Пам'ять з'їдена кешем | Прибрати зайві `cache()`, викликати `unpersist()` |
| Забагато ядер на executor (пам'ять ділиться між task-ами) | Зменшити `spark.executor.cores` |
| Читаються зайві колонки | Явний `select` потрібних колонок раніше в конвеєрі |

**Порядок спроб.** Спочатку зменшіть обсяг даних на партицію — фільтрацією раніше, відкиданням колонок, збільшенням кількості партицій. Збільшення `executor.memory` — останній крок: воно дорожче, має межу і часто лікує симптом замість причини.

**Невеликий spill — це нормально.** Мета не «нуль spill за будь-яку ціну», а відсутність ситуації, коли spill вимірюється десятками гігабайтів і домінує в часі виконання.

### 4. Skew: перекіс розподілу

#### 4.1 Що це

**Data skew** — нерівномірний розподіл даних по партиціях після shuffle. Оскільки stage завершується тільки тоді, коли завершився **останній** task, одна гігантська партиція визначає тривалість усього stage: 199 task-ів по 3 секунди й один на 40 хвилин дають stage на 40 хвилин.

Типові джерела перекосу:
- **NULL у ключі join-у** — усі NULL хешуються в одну партицію.
- **Дефолтні значення** — `unknown`, `-1`, `0`, `guest`.
- **Природна нерівномірність** — популярний товар, столичне місто, найбільший клієнт.
- **Технічні службові ключі** — бот-акаунт, службовий сервіс, тестовий тенант.

#### 4.2 Діагностика

**У Spark UI:** сторінка stage-а, рядок Duration у summary metrics. Медіана 2 с, max 25 хв — діагноз поставлено.

**У даних:**
```python
(df.groupBy("join_key").count()
   .orderBy(F.desc("count"))
   .show(20))
```
Якщо перше значення на два порядки більше за медіанне — це воно.

#### 4.3 Важелі

**1. Прибрати службові значення.** Найдешевше рішення: якщо перекіс дають NULL або `unknown`, які не потрібні в результаті, відфільтруйте їх до join-у.

```python
big.where(F.col("user_id").isNotNull()).join(dim, "user_id")
```

**2. Broadcast join.** Якщо перекошений join, а одна сторона мала — розсилка усуває shuffle взагалі, а разом із ним і перекіс.

**3. AQE skew join** (розділ 6) — автоматичне розбиття перекошених партицій. Перший варіант, який варто перевірити.

**4. Salting** — ручне рознесення «важкого» ключа по кількох партиціях.

#### 4.4 Salting

Ідея: додати до ключа випадковий суфікс, щоб один «важкий» ключ перетворився на N звичайних, а після агрегації прибрати суфікс.

**Для агрегації** (дворівнева схема):

```python
N = 50

# Крок 1: часткова агрегація по «посоленому» ключу
salted = (df
    .withColumn("salt", (F.rand() * N).cast("int"))
    .groupBy("zone_id", "salt")
    .agg(F.sum("amount").alias("partial_sum"),
         F.count("*").alias("partial_cnt")))

# Крок 2: фінальна агрегація по справжньому ключу
result = (salted
    .groupBy("zone_id")
    .agg(F.sum("partial_sum").alias("total"),
         F.sum("partial_cnt").alias("cnt")))
```

Перший `groupBy` розкидає навіть найпопулярніший `zone_id` по 50 партиціях. Другий працює вже з 50 рядками на ключ замість мільйонів.

**Для join-у** схема складніша: ліва (велика) сторона отримує випадкову сіль, права (мала) — **розмножується** на всі можливі значення солі.

```python
left_salted = big.withColumn("salt", (F.rand() * N).cast("int"))

right_salted = (small
    .withColumn("salt", F.explode(F.array(*[F.lit(i) for i in range(N)]))))

joined = left_salted.join(right_salted, on=["join_key", "salt"]).drop("salt")
```

Ціна: права таблиця збільшується в N разів. Тому salting виправданий тільки тоді, коли права сторона мала, а AQE не впорався.

**Порядок вибору:** прибрати службові значення → broadcast → AQE skew join → salting. Salting — останній засіб, бо він ускладнює код і вимагає підбору N.

### 5. Shuffle: головне джерело вартості

#### 5.1 Що відбувається

Shuffle — перерозподіл даних між executor-ами так, щоб рядки з однаковим ключем опинилися в одній партиції.

```
Map-сторона (кінець stage N):
  для кожного рядка обчислити partition = hash(key) % numPartitions
  згрупувати за цільовою партицією
  ЗАПИСАТИ на локальний диск (shuffle-файл + індекс)

Reduce-сторона (початок stage N+1):
  кожен task ТЯГНЕ ПО МЕРЕЖІ свої шматки з файлів усіх map-task-ів
  злити отримане, за потреби зі spill
```

Складові вартості: серіалізація, дисковий запис, мережевий обмін за схемою «всі до всіх», десеріалізація, можливий spill. Це на порядки дорожче за будь-яку локальну операцію.

Породжують shuffle: `groupBy`, `join` (крім broadcast), `distinct`, `dropDuplicates`, `orderBy`, `repartition`, віконні функції з `partitionBy`, `intersect`, `except`.

#### 5.2 Важелі

**1. Зменшити обсяг даних до shuffle.** Найефективніший важіль. Фільтруйте й відкидайте колонки **перед** агрегацією чи join-ом, а не після.

```python
# Погано: shuffle усього датасету, потім фільтр
df.groupBy("zone").agg(...).where(F.col("zone").isin(target_zones))

# Добре: shuffle тільки потрібного зрізу
df.where(F.col("zone").isin(target_zones)).groupBy("zone").agg(...)
```

**2. Усунути shuffle через broadcast.** Для join-у з довідником.

**3. Не робити зайвих shuffle-ів.** Кілька послідовних `repartition`, `orderBy` там, де достатньо `sortWithinPartitions`, `distinct` перед агрегацією, яка й так згортає дублікати.

**4. Перевикористати наявне партиціонування.** Якщо DataFrame уже розподілений за потрібним ключем, Spark пропустить `Exchange`.

```python
df2 = df.repartition("user_id")
df2.groupBy("user_id").agg(...)     # shuffle вже зроблено
df2.join(other, "user_id")          # і тут теж
```

**5. Налаштувати кількість shuffle-партицій.**

```python
spark.conf.set("spark.sql.shuffle.partitions", 400)
```

За замовчуванням — **200**. Це історична константа, не пов'язана ні з обсягом ваших даних, ні з розміром кластера. Для малих датасетів вона породжує сотні майже порожніх task-ів (накладні витрати домінують); для великих — гігантські партиції зі spill. Орієнтир: **2–4 партиції на доступне ядро**, з цільовим розміром партиції в сотні мегабайтів. AQE значною мірою знімає це питання (розділ 6).

### 6. Adaptive Query Execution

#### 6.1 Ідея

Catalyst обирає план **до** виконання на основі оцінок. Оцінки часто хибні: після кількох фільтрів і join-ів реальна кардинальність може відрізнятися на порядки. **AQE** (Spark 3.0+, увімкнений за замовчуванням) переоптимізовує план **під час виконання**, спираючись на фактичну статистику вже завершених stage-ів.

![Механізм AQE](https://www.databricks.com/wp-content/uploads/2020/05/blog-adaptive-query-execution-1.png)

*Механізм AQE: після завершення кожного stage збирається реальна статистика, і план решти запиту оптимізується заново перед виконанням наступних stage-ів. Джерело: [Databricks — Adaptive Query Execution](https://www.databricks.com/blog/2020/05/29/adaptive-query-execution-speeding-up-spark-sql-at-runtime.html)*

#### 6.2 Динамічне злиття shuffle-партицій

![Без злиття партицій](https://www.databricks.com/wp-content/uploads/2020/05/blog-adaptive-query-execution-2.png)

*Без AQE: фіксована кількість shuffle-партицій породжує окремі task-и навіть для крихітних партицій. Джерело: [Databricks](https://www.databricks.com/blog/2020/05/29/adaptive-query-execution-speeding-up-spark-sql-at-runtime.html)*

![Зі злиттям партицій](https://www.databricks.com/wp-content/uploads/2020/05/blog-adaptive-query-execution-3.png)

*З AQE: дрібні сусідні партиції зливаються в одну, кількість task-ів зменшується, накладні витрати падають. Джерело: [Databricks](https://www.databricks.com/blog/2020/05/29/adaptive-query-execution-speeding-up-spark-sql-at-runtime.html)*

```python
spark.conf.set("spark.sql.adaptive.enabled", True)
spark.conf.set("spark.sql.adaptive.coalescePartitions.enabled", True)
spark.conf.set("spark.sql.adaptive.advisoryPartitionSizeInBytes", "128MB")
```

Це знімає необхідність вручну підбирати `spark.sql.shuffle.partitions` під кожен датасет: можна поставити свідомо велике значення, а AQE зіллє надлишок.

#### 6.3 Динамічна зміна стратегії join

![Перемикання стратегії join під час виконання](https://www.databricks.com/wp-content/uploads/2020/05/blog-adaptive-query-execution-4.png)

*AQE замінює sort-merge join на broadcast hash join після того, як з'ясувалося, що одна зі сторін після фільтрації вміщається в пам'ять. Джерело: [Databricks](https://www.databricks.com/blog/2020/05/29/adaptive-query-execution-speeding-up-spark-sql-at-runtime.html)*

Класичний сценарій: таблиця на 2 ГБ, але після фільтра залишається 8 МБ. Статичний планувальник цього не знає й обирає sort-merge join із двома shuffle. AQE бачить фактичний розмір і перемикається на broadcast.

#### 6.4 Оптимізація перекошених join-ів

![Join із перекосом без оптимізації](https://www.databricks.com/wp-content/uploads/2020/05/blog-adaptive-query-execution-5.png)

*Без оптимізації: одна партиція значно більша за решту, і відповідний task визначає тривалість усього stage. Джерело: [Databricks](https://www.databricks.com/blog/2020/05/29/adaptive-query-execution-speeding-up-spark-sql-at-runtime.html)*

![Join із перекосом після оптимізації AQE](https://www.databricks.com/wp-content/uploads/2020/05/blog-adaptive-query-execution-6.png)

*З AQE: перекошена партиція розбивається на кілька підпартицій, відповідна частина другої сторони дублюється, і навантаження вирівнюється. Джерело: [Databricks](https://www.databricks.com/blog/2020/05/29/adaptive-query-execution-speeding-up-spark-sql-at-runtime.html)*

```python
spark.conf.set("spark.sql.adaptive.skewJoin.enabled", True)
spark.conf.set("spark.sql.adaptive.skewJoin.skewedPartitionFactor", 5)
spark.conf.set("spark.sql.adaptive.skewJoin.skewedPartitionThresholdInBytes", "256MB")
```

Партиція вважається перекошеною, якщо вона одночасно **більша за медіану в `skewedPartitionFactor` разів** і **перевищує поріг у байтах**. Обидві умови обов'язкові — інакше на маленьких датасетах спрацьовувало б постійно.

#### 6.5 Обмеження AQE

AQE діє **на межах shuffle** — саме там доступна фактична статистика. Він не допоможе, якщо:
- у плані взагалі немає shuffle;
- проблема в читанні джерела (не спрацював pruning);
- перекіс усередині однієї партиції джерела до першого shuffle;
- вузьке місце — Python UDF або дискові операції.

Суміжна оптимізація — **Dynamic Partition Pruning** (`spark.sql.optimizer.dynamicPartitionPruning.enabled`): при join-і партиційованого факту з відфільтрованим виміром Spark під час виконання визначає, які партиції факту взагалі потрібні, і не читає решту.

### 7. Проблеми зберігання

#### 7.1 Small files problem

Тисячі дрібних файлів шкодять двічі: **при читанні** (кожен файл — окремий запит до сховища, окремий footer, окремий task із накладними витратами) і **на рівні планування** (перелічення файлів займає більше часу, ніж їх читання).

Джерела появи:
- Часті інкрементальні записи (щохвилинні або потокові батчі).
- `partitionBy` без узгодженого `repartition` — кожна партиція DataFrame пише свій шматок у кожну директорію.
- Занадто велике `spark.sql.shuffle.partitions` перед записом.

Важелі:
```python
# Узгодити партиціонування в пам'яті з партиціонуванням на диску
(df.repartition("event_date")
   .write.partitionBy("event_date")
   .parquet(out))

# Зменшити кількість вихідних файлів
df.coalesce(20).write.parquet(out)
```

Для транзакційних table format-ів існує окрема процедура компакції:
```sql
CALL system.rewrite_data_files(table => 'db.events', strategy => 'binpack');
```

Цільовий розмір файлу — **128 МБ – 1 ГБ**.

#### 7.2 Партиціонування на диску

Партиціонування дає **partition pruning** — відсічення цілих директорій на етапі планування. У плані це видно як `PartitionFilters`.

Правила вибору колонки:
- **Низька кардинальність.** Дата, регіон, тип події — так. `user_id`, `session_id` — ні.
- **Часте використання у фільтрах.** Партиціонування за колонкою, за якою ніхто не фільтрує, дає тільки накладні витрати.
- **Розумний розмір партиції.** Орієнтир — щонайменше кількасот мегабайтів на партицію.

**Over-partitioning** — окрема хвороба: партиціонування за днем + годиною + регіоном дає десятки тисяч директорій із файлами по кілька кілобайтів. Планування такого запиту триває довше за саме читання.

#### 7.3 Формат і стиснення

- **Колонкові формати (Parquet, ORC) замість рядкових (CSV, JSON).** Це дає projection pushdown, predicate pushdown за статистикою row group і в рази краще стиснення.
- **Кодек стиснення.** `snappy` (за замовчуванням) — швидкий, помірне стиснення. `zstd` — краще стиснення при співмірній швидкості, розумний вибір для холодних даних. `gzip` — сильне стиснення, але **не подільний** на блоки, тобто один файл читається одним task-ом.
- **Сортування всередині файлів.** `sortWithinPartitions` за колонкою, за якою часто фільтрують, звужує діапазони min/max у статистиці й різко покращує пропуск row group.

### 8. Серіалізація та UDF

#### 8.1 Чому Python UDF дорога

```
Executor JVM ──серіалізація──► Python worker ──обробка──► ──десеріалізація──► JVM
```

До вартості серіалізації додається головне: **Catalyst не бачить середини UDF**. Через неї не протягується фільтр, не працює column pruning, не генерується код. Оптимізований план розривається чорною скринькою.

#### 8.2 Ієрархія вибору

```python
# 1. Вбудована функція — нативно в JVM, потрапляє в codegen
df.withColumn("fee", F.col("fare") * 0.15)

# 2. SQL-вираз
df.withColumn("fee", F.expr("fare * 0.15"))

# 3. pandas UDF — пачками через Arrow, у 10–100 разів швидше за звичайну UDF
@F.pandas_udf("double")
def zscore(s: pd.Series) -> pd.Series:
    return (s - s.mean()) / s.std()

# 4. Звичайна Python UDF — останній засіб
@F.udf("double")
def slow(x):
    return complex_python_logic(x)
```

Перед тим як писати UDF, варто перевірити, чи немає готової функції: `pyspark.sql.functions` містить кілька сотень, включно з роботою з масивами (`transform`, `filter`, `aggregate`), JSON, регулярними виразами й датами.

#### 8.3 Серіалізатор

Для RDD-операцій і кешування має значення серіалізатор. **Kryo** компактніший і швидший за стандартний Java-серіалізатор:

```python
spark.conf.set("spark.serializer", "org.apache.spark.serializer.KryoSerializer")
```

Для DataFrame-операцій це майже не важливо: Tungsten використовує власний бінарний формат `UnsafeRow`.

### 9. Кешування

#### 9.1 Коли воно допомагає

Кешування вигідне рівно в одному випадку: **той самий проміжний результат використовується кількома діями**.

```python
clean = df.where(...).join(dim, ...).withColumn(...)
clean.cache()

clean.groupBy("a").count().write...     # матеріалізація + кеш
clean.groupBy("b").count().write...     # з кешу
clean.unpersist()
```

#### 9.2 Коли воно шкодить

- **Одноразове використання.** `df.cache().write.parquet(...)` — витрачає пам'ять і час на матеріалізацію без жодної користі.
- **Витіснення execution-пам'яті.** Storage і execution ділять спільний пул; execution має пріоритет, тому надлишковий кеш просто витісниться, а час на його створення пропаде.
- **Кешування занадто рано.** Кешувати сирий DataFrame до фільтрації означає зберігати в пам'яті дані, 90 % яких буде відкинуто.
- **Забутий `unpersist()`.** Кеш живе до завершення застосунку.

#### 9.3 Перевірка

![Стан кешу у Spark UI](https://spark.apache.org/docs/latest/img/webui-storage-tab.png)

*Вкладка Storage: рівень зберігання, частка закешованих партицій, обсяг у пам'яті та на диску. Джерело: [Spark Web UI](https://spark.apache.org/docs/latest/web-ui.html)*

Якщо «Fraction Cached» помітно менша за 100 %, кеш не працює так, як ви припускаєте: частина партицій перераховується щоразу. Варіанти — серіалізований рівень (`MEMORY_ONLY_SER`), зменшення обсягу перед кешуванням або відмова від кешу.

### 10. Ручні важелі

#### 10.1 Broadcast join

```python
from pyspark.sql.functions import broadcast
fact.join(broadcast(dim), on="zone_id", how="left")

spark.conf.set("spark.sql.autoBroadcastJoinThreshold", 50 * 1024 * 1024)   # 50 МБ
spark.conf.set("spark.sql.autoBroadcastJoinThreshold", -1)                 # вимкнути
```

Явна підказка потрібна, коли Spark не має статистики розміру або оцінка помилкова. Обмеження: таблиця має вміститися і в пам'ять driver-а (він її збирає), і в пам'ять кожного executor-а. Спроба розіслати кілька гігабайтів кладе застосунок.

Альтернативна форма — підказки у SQL:
```sql
SELECT /*+ BROADCAST(d) */ * FROM fact f JOIN dim d ON f.id = d.id
-- також: MERGE, SHUFFLE_HASH, SHUFFLE_REPLICATE_NL
```

#### 10.2 repartition і coalesce

| | `repartition(n)` | `coalesce(n)` |
|---|---|---|
| Shuffle | Так | Ні |
| Напрямок | Збільшити або зменшити | Тільки зменшити |
| Рівномірність | Рівномірно | Може бути нерівномірно |
| Вплив на попередній stage | Ставить межу stage | **Знижує паралелізм усього попереднього stage** |

Останній рядок — головна пастка. `df.map(...).coalesce(1)` виконає **весь** stage в одному task-і, бо `coalesce` не створює межу. Якщо потрібно і зберегти паралелізм обчислень, і отримати мало файлів — `repartition`.

#### 10.3 Accumulator

Лічильник, який executor-и інкрементують, а driver читає. Використовується для збору діагностики без додаткової дії:

```python
bad_rows = spark.sparkContext.accumulator(0)

def check(row):
    if row.fare_amount < 0:
        bad_rows.add(1)
    return row

df.rdd.map(check).count()
print(bad_rows.value)
```

Гарантії слабкі: при повторному виконанні task-а (retry, speculative execution) значення може бути пораховане двічі. Accumulator придатний для приблизної діагностики, **не для бізнес-метрик**.

#### 10.4 Конфігурація ресурсів

Параметри executor-а й driver-а, кількість партицій, AQE, dynamic allocation — окремий розділ 12. Головна теза: `spark.executor.memory` і кількість executor-ів крутять **останніми**, коли з метрик уже видно, що проблема саме в пам'яті чи в паралелізмі, а не в зайвому shuffle чи skew.

### 11. Модель пам'яті executor-а

#### 11.1 Регіони JVM-heap

Heap executor-а (розмір задає `spark.executor.memory`) ділиться так (Unified Memory Manager, Spark 1.6+):

```
├─ Reserved Memory — 300 MB, хардкод, службова
└─ (heap − 300 MB) ділиться так:
     ├─ Unified (Spark) Memory — 60% (spark.memory.fraction)
     │    ├─ Execution — буфери shuffle, sort, hash-агрегації, hash-таблиці join, віконні функції
     │    └─ Storage   — cache / persist, broadcast-змінні
     │       Межа між Execution і Storage рухома. Execution витісняє Storage
     │       аж до spark.memory.storageFraction (0.5 × Unified) — це гарантований
     │       мінімум Storage. Назад Storage витіснити Execution не може.
     └─ User Memory — 40% — структури даних коду, метадані, обʼєкти UDF,
                            усе поза Spark-операціями
```

**Off-heap** (`spark.memory.offHeap.enabled`, `spark.memory.offHeap.size`) — Tungsten може тримати частину Execution/Storage поза heap: менший тиск на GC, але памʼять треба виділити явно.

#### 11.2 PySpark: памʼять поза heap

Python-worker — **окремий процес**, його памʼять **не входить у JVM-heap**. Її покриває `spark.executor.memoryOverhead` (за замовчуванням `max(384 MB, 0.1 × executor.memory)`), який також вміщає netty-буфери shuffle й Arrow.

Повний обсяг контейнера (YARN / k8s) = `executor.memory + memoryOverhead (+ offHeap.size + pyspark.memory)`. Якщо процес виходить за цю межу, його **вбиває OOM killer операційної системи — exit code 137**, без Spark-стектрейсу. Це найчастіша причина «джоб упав і в логах нічого» у PySpark з важкими `pandas_udf`, `toPandas()` або великим Arrow-батчем.

#### 11.3 Симптом → регіон → важіль

| Симптом | Регіон | Важіль (у порядку спроб) |
|---|---|---|
| Ненульовий Spill (memory / disk) | брак **Execution** | більше партицій → менше `executor.cores` (памʼять ділиться між task-ами) → `spark.memory.fraction`↑ → в останню чергу `executor.memory`↑ |
| `java.lang.OutOfMemoryError` у JVM | User Memory / `collect()` на driver / завелика broadcast | не збирати на driver; `driver.memory`↑; `autoBroadcastJoinThreshold`↓ |
| Контейнер killed, exit **137** | overhead (Python / Arrow / netty) | `spark.executor.memoryOverhead`↑; `spark.executor.pyspark.memory`↑; менше рядків на Arrow-батч |
| GC Time > 10 % Task Time | heap замалий або кеш з'їв Storage | прибрати зайві `cache()` / `unpersist()`; `MEMORY_ONLY_SER`; `executor.memory`↑ |

Де дивитися: **Spark UI → Executors** — `Storage Memory`, пікові `Execution` / `Storage`, `GC Time` відносно `Task Time`.

### 12. Конфігурація Spark: рівні, параметри, паралелізм

#### 12.1 Три рівні та мутабельність

| Рівень | Де | Що можна задати |
|---|---|---|
| `spark-defaults.conf` | кластер | дефолти для всіх джобів |
| `spark-submit --conf k=v` / `PYSPARK_SUBMIT_ARGS` | джоб, **до** старту JVM | `spark.executor.*`, `spark.driver.*`, `*.memoryOverhead`, `spark.serializer` — **лише тут** |
| `spark.conf.set("k", v)` | жива сесія | `spark.sql.*` (`shuffle.partitions`, `adaptive.*`, `autoBroadcastJoinThreshold`, `files.maxPartitionBytes`) і частина рантайму |

`spark.conf.get("k")` — подивитися поточне значення. У local-режимі `spark.driver.memory` через `.config()` не діє (JVM уже піднята) — тільки через `PYSPARK_SUBMIT_ARGS` / `--driver-memory`.

#### 12.2 Партиції, задачі, ядра

Три різні речі:

- **Партиція** — шматок даних. **Задача (task)** — обробка однієї партиції в межах одного stage. Stage із N партиціями → рівно N задач. Після кожного `Exchange` — новий stage зі своєю кількістю партицій і задач.
- **Ядро / слот** — одиниця паралелізму: скільки задач їде **одночасно**. `slots = spark.executor.instances × spark.executor.cores` (або `local[k]` = k). 200 задач на 4 слотах — ~50 «хвиль».
- Партиції задають, **скільки** роботи; ядра — **як швидко** вона проходить.

`getNumPartitions()` показує заплановану кількість задач; кількість задач із ненульовим Input у Spark UI → скільки партицій реально містять дані (для Parquet стеля — кількість row group-ів у файлах).

**Орієнтир розміру:** цільова партиція — сотні MB (`partitions ≈ обсяг / 128–200 MB`); і кратність слотам — **2–4× сумарних ядер**. Менше за слоти — ядра простоюють; рівно = слотам — погано переживає skew і straggler-ів; сотні× — накладні на планування домінують. Кількість executor-ів у формулу входить лише через сумарні ядра: 4×4 і 8×2 дають однаковий орієнтир.

#### 12.3 Каталог параметрів

**Обовʼязково торкатися на кожному джобі:**

| Параметр | Дефолт / орієнтир |
|---|---|
| `spark.sql.shuffle.partitions` | 200; 2–4× ядер або довірити AQE |
| `spark.sql.adaptive.enabled` + `.coalescePartitions.enabled` | true у 3.2+; лишати ввімкненим |
| `spark.sql.adaptive.advisoryPartitionSizeInBytes` | 64 MB — цільовий розмір партиції для AQE |
| `spark.sql.adaptive.skewJoin.enabled` (+ `.skewedPartitionFactor` 5, `.skewedPartitionThresholdInBytes` 256 MB) | автолікування перекошених join-ів |
| `spark.sql.autoBroadcastJoinThreshold` | 10 MB; `-1` вимикає |
| `spark.executor.memory` / `spark.executor.cores` | 16–32 GB / 4–5 |
| `spark.executor.memoryOverhead` | `max(384 MB, 0.1×memory)`; підіймати для PySpark |

**Знати, що існують; крутити за симптомом:**

| Параметр | Коли |
|---|---|
| `spark.sql.files.maxPartitionBytes` (128 MB) | паралелізм на читанні |
| `spark.driver.memory` / `spark.driver.maxResultSize` | broadcast будується на driver; `collect()` / `toPandas()` |
| `spark.memory.fraction` (0.6) / `spark.memory.storageFraction` (0.5) | розподіл heap (розділ 11) |
| `spark.sql.execution.arrow.pyspark.enabled` | `pandas_udf`, `toPandas()` |
| `spark.dynamicAllocation.enabled` + `spark.shuffle.service.enabled` | еластичність, стійкість до втрати executor-а |
| `spark.serializer=KryoSerializer` | RDD / кеш; для DataFrame майже не важить |

#### 12.4 `FetchFailedException` і довгий DAG

`FetchFailedException` (reduce-задача не змогла забрати shuffle-блок: executor загинув, диск заповнився, мережа) або дуже глибокий DAG (десятки послідовних `join` / `withColumn`) — окремий клас проблем, який **не лікується конфігом пам'яті чи партицій**. Важіль — обірвати лінію обчислень: `df.checkpoint()` матеріалізує проміжний результат на надійне сховище й відкидає lineage, тож повторний збій не тягне перерахунок з нуля. Суміжне — `spark.shuffle.service.enabled` (external shuffle service зберігає shuffle-файли після смерті executor-а).

### 13. Чек-лист оптимізації

**Спочатку виміряти:**
1. Який job і який stage займають більшість часу?
2. Медіана й максимум тривалості task-а в цьому stage — чи є перекіс?
3. Ненульовий spill?
4. Обсяг Shuffle Read/Write?
5. GC Time відносно Task Time?
6. У плані: скільки `Exchange`, чи є `PushedFilters`, скільки колонок у `ReadSchema`, яка стратегія join?

**Потім діяти, у порядку спадання ефекту:**
1. Читати менше — pruning партицій, projection, фільтр якнайраніше.
2. Прибрати зайві shuffle-и й зменшити обсяг того, що залишився.
3. Замінити sort-merge join на broadcast там, де сторона мала.
4. Полагодити skew — фільтром службових значень, AQE або salting.
5. Виправити кількість партицій під розмір даних і кластера.
6. Прибрати UDF або замінити на pandas UDF.
7. Кешувати те, що справді читається кількома діями.
8. Полагодити розмір файлів на виході.
9. І лише потім — крутити пам'ять і кількість executor-ів.

## Ключові терміни

| Термін | Визначення |
|---|---|
| **Spill** | Скидання проміжних структур обчислення на локальний диск через брак execution-пам'яті |
| **Data skew** | Нерівномірний розподіл даних по партиціях; stage триває стільки, скільки найдовший task |
| **Salting** | Додавання випадкового суфікса до ключа для розбиття перекошеної партиції |
| **Shuffle** | Перерозподіл даних між executor-ами: запис на диск + мережевий обмін «всі до всіх» |
| **`Exchange`** | Позначення shuffle у фізичному плані; `hashpartitioning`, `rangepartitioning`, `SinglePartition` |
| **`spark.sql.shuffle.partitions`** | Кількість партицій після shuffle; за замовчуванням 200 |
| **AQE** | Adaptive Query Execution: переоптимізація плану під час виконання за фактичною статистикою |
| **Coalesce partitions (AQE)** | Автоматичне злиття дрібних shuffle-партицій |
| **Skew join optimization (AQE)** | Автоматичне розбиття перекошеної партиції з дублюванням відповідної частини другої сторони |
| **Dynamic Partition Pruning** | Відсічення партицій факту за результатом фільтра на вимірі під час виконання |
| **Broadcast join** | Розсилка малої сторони на всі executor-и; join без shuffle великої таблиці |
| **`autoBroadcastJoinThreshold`** | Поріг автоматичного broadcast, за замовчуванням 10 МБ |
| **Join hints** | `BROADCAST`, `MERGE`, `SHUFFLE_HASH`, `SHUFFLE_REPLICATE_NL` |
| **Partition pruning** | Відсічення партицій на диску; у плані — `PartitionFilters` |
| **Predicate pushdown** | Передача фільтра в reader джерела; у плані — `PushedFilters` |
| **Projection pruning** | Читання лише потрібних колонок; у плані — `ReadSchema` |
| **Small files problem** | Деградація через тисячі дрібних файлів на читанні й на плануванні |
| **Over-partitioning** | Занадто дрібне партиціонування на диску; планування дорожче за читання |
| **Compaction** | Об'єднання дрібних файлів у файли цільового розміру |
| **Whole-stage codegen (`*(N)`)** | Компіляція групи операторів у один блок Java-коду |
| **`repartition` / `coalesce`** | Зміна кількості партицій із shuffle / без; `coalesce` знижує паралелізм попереднього stage |
| **`cache()` / `persist()` / `unpersist()`** | Матеріалізація результату для повторного використання й звільнення пам'яті |
| **StorageLevel** | Рівень кешування: пам'ять/диск, серіалізація, реплікація |
| **pandas UDF** | Векторизована UDF: дані передаються пачками через Arrow |
| **Kryo** | Компактніший серіалізатор для RDD-операцій і кешу |
| **Accumulator** | Лічильник, який інкрементують executor-и; не гарантує рівно-одноразовий підрахунок |
| **`memoryOverhead`** | Позаheapова пам'ять executor-а; критична для PySpark |
| **Dynamic allocation** | Автоматичне додавання й прибирання executor-ів за навантаженням |
| **GC Time** | Час збирача сміття; понад 10 % Task Time — ознака проблеми з пам'яттю |
| **Unified Memory Manager** | Рухома межа між Execution і Storage у heap; Execution витісняє Storage до `storageFraction` |
| **`spark.memory.fraction`** | Частка (heap − 300 MB), віддана під Unified Memory; за замовчуванням 0.6 |
| **User Memory** | Частина heap (~40%) поза Unified: обʼєкти коду, метадані, стан UDF |
| **exit 137** | OOM killer ОС убив контейнер за перевищення `memory + memoryOverhead`; типово — Python/Arrow |
| **Task / партиція / слот** | Задача = обробка 1 партиції в stage; слот (= ядро) = скільки задач одночасно |
| **Task slots** | `executor.instances × executor.cores` (або `local[k]`); визначають паралелізм |
| **`PYSPARK_SUBMIT_ARGS`** | Змінна для параметрів, що задаються до старту JVM (`--driver-memory` у local) |
| **`spark.conf.set` / `--conf`** | Рантайм-параметри `spark.sql.*` у сесії / параметри ресурсів до старту |
| **`FetchFailedException`** | Reduce-задача не забрала shuffle-блок (смерть executor-а, диск, мережа); лікується checkpoint / shuffle service |
| **`checkpoint()`** | Матеріалізація на надійне сховище з обривом lineage; проти довгого DAG і повторних збоїв |
| **`advisoryPartitionSizeInBytes`** | Цільовий розмір shuffle-партиції для AQE coalesce; за замовчуванням 64 MB |
